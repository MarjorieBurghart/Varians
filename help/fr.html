1. Projets et démarrage

Au premier lancement, Varians n’ouvre aucun projet. Par la suite, il peut rouvrir le projet qui était encore actif lors de la fermeture précédente. Fichier → Fermer le projet (Ctrl+W) revient à l’écran d’accueil sans quitter Varians et empêche cette réouverture automatique pour le projet fermé.

Créer un projet

Fichier → Nouveau projet… permet soit d’utiliser une TEI existante, soit de commencer une nouvelle transcription. Dans ce second cas, Varians crée une TEI minimale dans xml/edition.xml et construit un <listWit> à partir des témoins du projet.

<listWit>
  <witness xml:id="A1">Assisi, Sacro convento, 541</witness>
</listWit>

Un témoin peut être créé sans image, sans ALTO et sans synchronisation. Ces ressources peuvent être ajoutées plus tard dans n’importe quel ordre.

Structure habituelle

project.xml
xml/edition.xml
images/
alto/
alignments/
rendering/
i18n/
web_output/

Les anciens projets dont edition.xml se trouve à la racine restent lisibles.

2. Édition XML et aperçu XSLT/CSS

L’onglet XML source contient la TEI. Le retour automatique à la ligne est purement visuel : il ne modifie ni le XML ni ses numéros de lignes logiques.

L’onglet XSLT / CSS fournit un aperçu éditorial. Les sélections entre source XML et aperçu sont synchronisées lorsque cela est possible. Varians distingue les occurrences répétées d’un même mot à l’intérieur d’un passage afin d’éviter de sélectionner systématiquement la première occurrence.

L’éditeur de fragment permet de travailler sur un passage restreint puis de réinjecter sa modification dans le document principal.

Sélections partagées avec l’éditeur de fragment. Le crayon ✎ placé au début d’un paragraphe de l’aperçu ouvre ce paragraphe dans l’éditeur de fragment, sans déplacer les images des témoins ; un clic sur le texte de l’aperçu les synchronise toujours. Quand l’éditeur est ouvert, une chaîne sélectionnée dans ce paragraphe de l’aperçu (en glissant la souris ou par un double-clic) est aussi sélectionnée dans l’éditeur de fragment, qui prend le focus : le passage à corriger est trouvé tout de suite. Inversement, une sélection faite dans l’éditeur de fragment est sélectionnée dans l’aperçu, qui défile jusqu’à elle ; le focus reste dans l’éditeur. La même occurrence d’un mot répété est retrouvée, y compris un mot coupé par un <lb break="no"/>. Une sélection dans un autre paragraphe ne change pas l’éditeur de fragment : ouvrez ce paragraphe par son crayon. Un texte tapé dans le fragment n’apparaît dans l’aperçu qu’après Appliquer au XML.

3. Aide au balisage, RNG et custom-elements.xml

Ctrl+E

Ctrl+E entoure la sélection avec un élément ou insère un nouvel élément au curseur. Les éléments autorisés par le RELAX NG à la position courante sont proposés en priorité.

Ctrl+Espace

Ctrl+Espace complète les noms d’éléments, attributs et certaines valeurs d’attributs. Les propositions peuvent venir du schéma RNG, du fichier custom-elements.xml, ou des deux. Leur provenance est indiquée dans l’interface.

Pour les pointeurs tels que @wit, Varians sait compléter une liste séparée par des espaces et éviter les témoins déjà présents. Une source dynamique witnesses permet de produire les identifiants du projet sous la forme #A1, #B1, etc.

Important : custom-elements.xml fournit des aides de saisie et de présentation. Il ne modifie jamais la validité RELAX NG du document.

Validation RELAX NG

Valider RNG ou F8 lance la validation complète. Les erreurs sont listées dans un panneau inférieur ; un clic conduit à la zone concernée. Le panneau est réinitialisé au changement de projet afin d’éviter de conserver les diagnostics d’un document précédent.

4. Recherche XPath

XPath (Ctrl+Shift+F) exécute une expression XPath 1.0 sur la TEI. Par exemple //note recherche les éléments <note>. Dans une TEI utilisant l’espace de noms standard, les requêtes simples non préfixées sont automatiquement réessayées avec le préfixe tei:.

Les résultats indiquent la ligne, l’élément, son chemin et un aperçu. À partir de la version 0.8.4.2, cliquer sur un résultat sélectionne l’élément XML complet, de la balise ouvrante à la balise fermante, y compris lorsque l’élément s’étend sur plusieurs lignes. Un élément autofermant est sélectionné en entier.

Les XPath qui renvoient une valeur scalaire, par exemple count(//tei:note), affichent cette valeur au lieu d’une liste d’éléments.

Pour contrôler l’apparat critique, Aide → Débugger l’apparat… propose des requêtes toutes prêtes : voir Débugger l’apparat.

5. Paires de balises et indentation sûre

Varians reconnaît les paires de balises XML. Lorsque le curseur se trouve dans une balise ouvrante, la fermeture correspondante est mise en évidence. Le renommage du QName ouvrant peut être répercuté sur la fermeture, et la suppression complète de l’ouverture peut retirer la fermeture associée tout en conservant le contenu.

Indenter

Le bouton Indenter applique un formatage conservateur : il indente les zones structurelles sans modifier le contenu textuel mixte.

Les protections sont prioritaires :

  • aucun blanc nouveau autour de <lb/> ;
  • respect de xml:space="preserve" ;
  • abstention dans les contenus mixtes ou ambigus ;
  • prise en compte du RNG quand il indique qu’un élément accepte du texte.

custom-elements.xml peut préciser formatting="inline", formatting="block" ou formatting="preserve". Les protections absolues restent toutefois prioritaires.

6. Témoins, images, fac-similé et pages

Chaque témoin déclaré dans le projet peut utiliser :

  • aucune image ;
  • des images locales (JPEG, PNG, TIFF, BMP, WebP) ;
  • un Manifest IIIF Presentation 2 ou 3.

Les images locales peuvent être copiées dans le projet ou référencées à leur emplacement d’origine. Le mode copie est recommandé pour obtenir un projet portable.

Folio/page et <facsimile>

Pour les images locales, la liste permet de renseigner un libellé de folio/page et un identifiant stable de surface. Varians peut compléter la TEI de manière incrémentale :

<facsimile>
  <surface xml:id="A1-p0002" n="1v">
    <graphic url="../images/A1/002.jpg"/>
  </surface>
</facsimile>
Garde-fou : Varians ne reconstruit pas brutalement un <facsimile> existant. Les surfaces, zones et enrichissements éditoriaux déjà présents sont conservés ; les ajouts sont incrémentaux.

Marquer la page

Dans le panneau d’un témoin, Marquer la page insère au curseur un changement de page associé au témoin et à la surface :

<pb n="1v" edRef="#A1" facs="#A1-p0002"/>

@n reprend le libellé de folio/page, @edRef l’identifiant du témoin et @facs la surface TEI. Si le curseur se trouve à l’intérieur d’une balise XML, aucune insertion n’est effectuée : il faut le placer dans le texte ou entre deux balises.

En l’absence de synchronisation ligne à ligne, le dernier <pb edRef="…" facs="…"/> précédant la position courante détermine la page affichée pour chaque témoin.

7. ALTO et synchronisation ligne à ligne

L’ALTO est facultatif et indépendant de l’image. Il fournit notamment le texte OCR et les coordonnées des lignes sur la page. Un témoin peut donc avoir des images sans ALTO, de l’ALTO sans synchronisation, ou les deux.

ALTO ne signifie pas synchronisation. Tant qu’aucune correspondance ligne TEI ↔ ligne de manuscrit n’existe, Varians reste en mode page et affiche la page entière. Les cadres ALTO peuvent être visibles, mais aucune ligne n’est privilégiée.

Le mode ligne n’est activé que lorsqu’un alignement exploitable existe : de vraies lignes de référence pour le témoin pivot et de vrais base_keys pour les témoins secondaires. Un JSON vide ou provisoire n’active pas le mode ligne.

8. Affichage des témoins

Le menu Affichage contient notamment Recharger les images, Choisir les témoins affichés… et le choix de langue.

Choisir les témoins affichés… permet de cocher de 0 à n témoins. Ce choix est mémorisé localement pour chaque projet et ne modifie pas project.xml. Si aucun témoin n’est affiché, la zone d’images disparaît.

Les panneaux des témoins sont séparés par un splitter vertical : leur hauteur peut être ajustée. Un double-clic sur l’en-tête d’un témoin le maximise temporairement ; un second double-clic restaure la répartition précédente.

V0.8.5.16 — Visibilité et ordre. Dans Affichage → Choisir les témoins affichés…, cochez les manuscrits souhaités, puis sélectionnez une ligne et cliquez sur Monter ou Descendre pour organiser les panneaux de haut en bas. Un témoin masqué conserve sa position dans la liste. Le choix est mémorisé localement pour ce projet, y compris après fermeture de Varians ; les témoins ajoutés ultérieurement sont placés à la fin. Cela ne modifie ni le témoin pivot, ni les alignements, ni le fichier project.xml, ni l’ordre du viewer web généré.

9. Viewer web

Générer viewer web crée un viewer autonome dans web_output/ (ou le dossier configuré). Les images locales nécessaires sont copiées dans le paquet de sortie.

Sans synchronisation ligne à ligne, le viewer fonctionne en mode page : les boutons deviennent ← page et page →. Un clic dans le texte détermine, pour chaque témoin, le dernier <pb> pertinent et affiche la page correspondante. Avec une vraie synchronisation, la navigation passe au mode ligne.

Un projet sans aucune image est exporté sans colonne de fac-similé inutile.

Comme dans la fenêtre, les flèches ← → de tout panneau mènent le texte : le témoin avance dans son propre ordre, et le texte va à la ligne du pivot que désigne sa ligne, ou à son <pb> pour un témoin suivi par pages, dont la liste des folios mène aussi le texte ; ⤺ ramène le panneau sur la ligne reliée. Les lacunes des témoins ont leurs bandeaux. Pour une édition en parties, voir Export web de l’édition assemblée.

10. Sauvegarde et sécurité

Ctrl+S enregistre l’édition. La bonne formation XML est surveillée automatiquement. Les schémas RNG compilés sont mis en cache et invalidés lorsque leurs fichiers changent.

Les écritures importantes utilisent autant que possible des remplacements atomiques et des fichiers .bak. Varians privilégie la conservation du travail éditorial : lorsqu’une opération automatique est ambiguë, il doit s’abstenir plutôt que réécrire silencieusement la TEI.

ALTO, PAGE XML et copies IIIF locales (0.8.5)

Formats de segmentation des témoins

Dans Paramètres du projet → Témoins → Modifier, ouvrez la section Transcription géométrique (ALTO / PAGE). Ajoutez les fichiers XML dans l’ordre des folios. Varians détecte chaque fichier séparément : des témoins ALTO et PAGE peuvent coexister, et un témoin peut même combiner des fichiers des deux formats. Vous pouvez les copier dans le projet pour le rendre portable.

Les lignes ALTO possèdent habituellement un rectangle ; les lignes PAGE conservent leur polygone Coords/@points et, lorsqu’elle existe, leur ligne de base Baseline/@points. Dans le viewer, activez Cadres pour afficher les contours. Le texte des lignes PAGE provient du TextEquiv/Unicode de chaque TextLine, ou des mots si ce texte manque. L’importation de PAGE ne crée pas, à elle seule, de synchronisation avec les <lb> TEI : celle-ci reste une ressource distincte.

Gestionnaire de téléchargements IIIF

Dans Paramètres du projet → Témoins → Modifier, activez la copie locale de travail et choisissez Toutes les pages du manifeste ou Uniquement les pages associées à un ALTO ou PAGE. La sélection est propre à chaque témoin. Pour le mode sélectif, déclarez d’abord les fichiers ALTO/PAGE du témoin : Varians rapproche leurs noms d’image, noms de page ou numéros de folio des pages IIIF. Aucun rapprochement n’est effectué sur la seule position dans les listes. Une page ambiguë ou introuvable est exclue et signalée, jamais substituée silencieusement.

Le téléchargement démarre dans une fenêtre séparée après l’enregistrement des paramètres, sans bloquer l’édition. Rouvrez-la à tout moment par Fichier → Gestionnaire de téléchargements IIIF…. Elle indique le nombre de pages du manifeste, sélectionnées, présentes en local, manquantes et exclues. Télécharger les manquantes reprend sans retélécharger les images déjà reçues ; Actualiser la sélection force un nouveau téléchargement. Pause, Reprendre et Arrêter prennent effet entre les images. Une requête en cours peut prendre jusqu’à expiration du délai réseau. Fermer la fenêtre la masque sans arrêter le travail.

Les fichiers reçus sont conservés dans iiif/local/<témoin>/ et deviennent accessibles dans l’éditeur sans réouvrir le projet à la fin d’une opération. Les pages non copiées continuent à utiliser les URL distantes : une copie sélective ne rend donc pas tout le manuscrit consultable hors ligne. Le réglage de l’export web reste indépendant ; seules les images réellement en cache peuvent y être intégrées.

Viewer web : choix indépendant

Dans les paramètres du même témoin, cochez ou décochez Utiliser la copie locale lors de la génération du viewer web. Si la case est cochée, Varians intègre les images locales disponibles au dossier web_output/images/ et les chemins relatifs sont utilisables hors ligne. Si elle est décochée, le viewer reste connecté aux serveurs IIIF d’origine, même quand l’éditeur utilise sa copie locale. Les pages encore absentes de la copie peuvent rester dépendantes du réseau dans le viewer exporté. Vérifiez les autorisations de reproduction et les licences des établissements avant de redistribuer les images.

Sélection explicite des images IIIF et association des OCR (0.8.5.4)

Dans Paramètres du projet → Témoins → Modifier, choisissez « Uniquement les images choisies pour l’édition », puis « Choisir les images et associer les OCR… ». Le manifeste demeure une liste de référence ; seules les lignes cochées font partie du corpus d’images de ce témoin. Filtrez les folios, cochez les lignes visibles ou retirez-les de la sélection. L’aperçu ouvre la ressource IIIF dans le navigateur.

Varians propose automatiquement l'association entre un canvas IIIF et un fichier ALTO/PAGE lorsque leurs noms d'image (sans extension) sont identiques. Il examine aussi le nom de l'image déclaré dans le XML : renommer un fichier OCR n'empêche donc pas la détection. Les correspondances ambiguës ne sont pas appliquées. Les liens déjà choisis restent prioritaires. Le bouton « Associer automatiquement (noms exacts) » permet de compléter les cases vides ; l'utilisateur peut toujours modifier ou retirer une association. Aucun rapprochement approximatif ou fondé sur l'ordre des fichiers n'est effectué.

Après avoir ajouté les fichiers ALTO/PAGE locaux, choisissez dans la dernière colonne celui qui correspond à chaque canvas retenu. Cette association explicite fonctionne même lorsque le nom de l’image locale diffère complètement du manifeste. Un même fichier OCR ne peut pas correspondre à plusieurs canvases ; pour l’instant, l’association manuelle suppose un fichier OCR par image.

Dans le gestionnaire IIIF, « Toutes les pages » signifie maintenant toutes les pages retenues pour l’édition lorsque cette sélection explicite est active ; « Pages avec ALTO/PAGE » restreint encore le téléchargement aux pages associées à un OCR. Les autres pages du manifeste ne sont ni téléchargées ni ajoutées à la liste des surfaces TEI. Les identifiants des surfaces conservent la position d’origine du canvas afin de rester stables.

Les anciennes surfaces TEI déjà créées ne sont jamais supprimées automatiquement : elles peuvent être référencées ou annotées. Il faut examiner les surfaces inutilisées avant toute suppression manuelle dans le document. Les copies IIIF déjà présentes dans le cache local restent également conservées.

À l’import, les images locales et les fichiers ALTO/PAGE sont désormais triés naturellement : img_1r, img_1v, img_2r, etc. Pour une liste existante, utilisez « Trier naturellement » ; le déplacement manuel ↑/↓ reste possible.

Pages synchronisées et Canvas IIIF (0.8.5.6)

Pour un témoin IIIF, importez le JSON produit par Varians-Synchro, puis ouvrez Choisir les images et associer les OCR…. Le JSON conserve les identifiants de ses propres pages et de ses lignes ; la sélection IIIF définit seulement les images à afficher, même si le manifeste compte plusieurs centaines de canvases.

Varians résout chaque page par l'identifiant exact du Canvas, le service IIIF Image, l'URL normalisée de l'image, une association ALTO/PAGE fiable ou un libellé de folio non ambigu. Les noms de fichiers identiques sont associés automatiquement. Pour les cas restant sans solution, utilisez la nouvelle colonne Page synchronisée pour choisir explicitement la page JSON correspondant au Canvas. La position d'une page dans la liste ne sert jamais à l'identifier. Un choix manuel est prioritaire et conservé dans project.xml.

Les colonnes Copie locale et État de l'association indiquent la disponibilité d'un fichier téléchargé, l'origine de la correspondance et la source préférée pour l'affichage. Le travail hors ligne exige une copie locale présente ; sinon le service IIIF reste la source de secours. Une ambiguïté n'entraîne aucune association arbitraire. Seuls les canvases retenus pour l'édition servent à créer de nouvelles surfaces TEI ; les surfaces antérieures ne sont jamais supprimées sans intervention.

Préparer une transcription TEI vide depuis le témoin pivot

Dans Nouveau projet ou Paramètres du projet, activez la préparation des <pb/> du témoin pivot et, si souhaité, celle des <lb/>. Seules les pages sélectionnées reçoivent un <pb/> : son @facs désigne la <surface> et @edRef le témoin. Les <lb/> portent seulement @edRef, sans @n ni lien automatique aux zones. Varians utilise d’abord les lignes ALTO/PAGE associées avec certitude ; à défaut, il compte les lignes effectivement décrites dans le JSON, y compris lorsque la première est numérotée 41 ou davantage. Les lacunes sont signalées, jamais comblées artificiellement. Une page sélectionnée sans ligne connue conserve son <pb/>. L’aperçu, la confirmation et une sauvegarde datée protègent le texte ; aucune transcription OCR n’est importée.

Préparation TEI depuis le témoin pivot (0.8.5.7)

Dans Fichier → Nouveau projet, choisissez Commencer une nouvelle transcription. L’encadré « Préparation de la transcription du témoin pivot » se trouve immédiatement sous « Point de départ », avant le tableau des témoins. Cochez la génération des <pb/> ; l’option <lb/> est alors disponible et initialement cochée. Dans les paramètres d’un projet existant, l’encadré se trouve avant la liste des témoins. Les fenêtres sont défilables sur les petits écrans. Le titre « Varians 0.8.5.7 » permet de vérifier que la bonne version est lancée.

Varians 0.8.5.8 — Correction des lignes partielles

Correction 0.8.5.8 : un extrait de folio commençant à la ligne 41 produit autant de <lb/> qu’il contient de lignes répertoriées (par exemple 28 pour les lignes 41 à 68), et non zéro ni 68. Le <lb/> généré n’a plus de @n. Une page du JSON avec une liste de lignes vide reçoit néanmoins un <pb/> si son image fait partie de la sélection éditoriale ; sinon, Varians signale l’absence d’image ou de surface associée.

Recadrage aux changements de colonne et de page (0.8.5.9)

Lorsque la synchronisation place le curseur sur une ligne proche d’un changement de colonne ou de folio, Varians n’englobe plus automatiquement les lignes voisines appartenant à une autre colonne ou page. Le cadrage reste centré sur les lignes physiques réellement voisines ; les numéros de lignes, les correspondances JSON et les clés de synchronisation ne sont pas modifiés. Le bouton « Page ↗ » permet toujours d’ouvrir l’image complète.

Cadres des lignes synchronisées (0.8.5.10)

Le bouton « Cadres » s’active indépendamment dans chaque témoin et son état actif est désormais clairement visible. Les contours orange signalent les lignes reliées par la synchronisation ; le contour bleu indique une ligne consultée manuellement, sans lui attribuer de lien éditorial. Si une ligne de base correspond à plusieurs lignes distinctes dans un autre témoin, Varians centre toujours la vue sur une ligne réellement reliée, même à un changement de colonne. Les polygones PAGE sont tracés comme des polygones ; les lignes ALTO sont généralement rectangulaires. Si la géométrie fait défaut, un diagnostic s’affiche. Le viewer web conserve actuellement des surlignages rectangulaires.

Navigation mixte : pages et lignes par témoin (0.8.5.11)

Lorsqu’une édition comporte des témoins synchronisés par lignes et un témoin ne disposant que d’images, chaque panneau suit désormais son propre niveau de correspondance. Les témoins munis d’un JSON de synchronisation exploitable continuent à suivre les <lb/> du pivot et les liens base_keys ; le témoin sans synchronisation suit les <pb/> portant son @edRef et pointant par @facs vers une <surface>. En l’absence de @facs, un @n correspondant exactement et sans ambiguïté à une page du témoin suffit ; le rang de l’image n’est jamais utilisé. Les autres témoins ne sont pas déplacés par ces <pb/>. La navigation depuis la transcription, la vue mise en forme et les panneaux de lignes conserve ce fonctionnement mixte. Le visualiseur web généré applique la même logique lors de la sélection des lignes ou du texte.

V0.8.5.12 — Navigation avec plusieurs témoins. Les panneaux d’images sont désormais défilables verticalement, sans comprimer le quatrième témoin. Le rôle « témoin pivot » désigne uniquement la référence technique de synchronisation, et ne préjuge pas du manuscrit de base que l’éditeur pourra choisir. Pour les <pb/> sans @facs, la recherche utilise la combinaison @edRef + @n : deux manuscrits peuvent porter le même numéro de folio.

Complétion des balises fermantes

Dans l’éditeur XML source et l’éditeur de fragments, taper </ fait apparaître la fermeture de l’élément ouvert le plus proche. Ainsi, après <div><p>…</p></, Varians propose div> : appuyez sur Entrée ou Tabulation pour obtenir </div>. Vous pouvez aussi commencer à saisir le nom, par exemple </di. Échap ferme la liste sans modifier le texte. Ctrl+Espace la rouvre à cet emplacement. La complétion respecte les noms qualifiés tels que tei:div, ignore les éléments vides (<lb/>), les commentaires, les CDATA et les attributs inachevés. Si l’imbrication est ambiguë, aucune fermeture n’est inventée.

Images IIIF et ALTO/PAGE ajoutés ultérieurement (0.8.5.14)

Ajouter des fichiers ALTO ou PAGE à un témoin IIIF non synchronisé ne retire plus ses images : la sélection des canvases demeure la référence, y compris avec des copies locales. La géométrie est associée uniquement lorsqu’un identifiant de canvas, un lien manuel, un libellé de folio non ambigu ou l’image locale exacte permet de prouver la correspondance. Les pages OCR non associées restent consultables dans le cache dérivé et leur nombre est indiqué dans l’infobulle du témoin ; elles ne donnent pas lieu à un recadrage ou à une image arbitraire. Pour les associer, ouvrez les paramètres du témoin, puis « Choisir les images et associer les OCR… ». Le JSON de synchronisation et la TEI ne sont pas modifiés.

Références entre documents

Un attribut pointeur (@ref, @corresp, @target, @who, @wit, @edRef, @sameAs, @ana, @resp, @source, @hand, @facs, @prev, @next, @synch, @copyOf) désigne un élément par son @xml:id. Comme en TEI standard, et donc pour tous les outils XML, la forme courte #bernard désigne un élément du document lui-même. Pour viser un autre document du projet (voir Documents XML auxiliaires), on écrit personnes.xml#bernard, avec un chemin relatif au document qui contient la référence. Les adresses web (https://…) et les valeurs sans « # » ne sont pas traitées. Une valeur peut contenir plusieurs pointeurs séparés par des espaces : wit="#T1 #T2".

Saisie. Dans la valeur d’un tel attribut, tapez # : la liste des identifiants s’ouvre d’elle-même, avec le texte de chaque entrée et son fichier, par exemple « personnes.xml#bernard — Bernardus ». Les lettres suivantes filtrent la liste ; Entrée ou Tab insère la valeur ; Échap ferme la liste. Pour @wit et @edRef, la liste propose les témoins décrits dans la TEI (<witness> du <listWit>). Ctrl+Espace ouvre les mêmes valeurs dans une boîte (« Identifiants du projet ») où le filtre porte aussi sur les descriptions : « Bern » trouve personnes.xml#bernard. Les identifiants proposés dépendent de l’élément : persName/@ref propose les person, personGrp et persona ; placeName/@ref les place ; orgName/@ref les org ; @who les personnes. Ailleurs, tous les identifiants sont proposés. Dans custom-elements.xml, <values source="ids" elements="person personGrp" prefix="#"/> fixe cette liste pour un attribut. Un identifiant d’un autre document est inséré sous la forme fichier.xml#id, un identifiant du document lui-même sous la forme #id.

Navigation. Sur une référence, appuyez sur F12, faites Ctrl+clic ou choisissez Aller à la cible dans le menu du clic droit : le document qui contient la cible est affiché, l’élément sélectionné. Si l’identifiant est défini plusieurs fois, Varians demande quelle cible afficher. Alt+← (ou Revenir dans le menu du clic droit) ramène au point de départ, même depuis un autre document. Une cible introuvable est signalée dans la barre d’état. Sur une forme courte dont la cible n’est que dans un autre document, Varians y mène aussi et indique la forme à écrire.

Vérification. Le bouton Références de la barre d’outils vérifie les références de tous les documents du projet. Le panneau qui s’ouvre sous la source indique leur nombre et liste celles qui posent un problème : cible introuvable, forme courte dont la cible est dans un autre document (avec la forme à écrire), cible ambiguë (identifiant défini plusieurs fois dans le document visé) ou fichier introuvable, avec les colonnes Document, Ligne, Attribut, Valeur et Problème. Un double-clic mène à la référence. Après une correction, Vérifier à nouveau relance la vérification. Cette vérification est une aide : elle n’empêche jamais d’enregistrer et ne modifie aucun fichier.

Lacunes des témoins

Le passage qu’un témoin n’a pas (feuillet perdu, texte interrompu) s’encadre, en TEI, par <lacunaStart/> et <lacunaEnd/>. La TEI place ces balises dans une leçon : le témoin est celui du <rdg> (ou du <lem>) qui les contient, ou, dans une leçon de plusieurs témoins, celui de leur propre @wit :

<app><lem wit="#T1 #P"/><rdg wit="#T2"><lacunaStart/></rdg></app>
…
<app><lem wit="#T1 #P"/><rdg wit="#T2"><lacunaEnd/></rdg></app>

<rdg wit="#T2 #P">… <lacunaStart wit="#P"/></rdg>

Varians reconnaît aussi ces balises hors d’une leçon, avec @wit, mais la validation TEI les y signale comme erreurs.

Dans les panneaux. Quand le curseur est dans une lacune d’un témoin, son panneau garde la ligne (ou, pour un témoin suivi par pages, la page) où son texte s’interrompt, avec le bandeau « Lacune de ce témoin : son texte s’interrompt ici. ». Quand le curseur est dans une lacune du témoin pivot, les témoins synchronisés par lignes restent sur la dernière ligne du pivot, avec le bandeau « Lacune du témoin pivot : les lignes ne sont plus synchronisées dans ce passage. » ; la barre d’état le signale aussi. Les témoins suivis par pages continuent de suivre leurs <pb>, qui ne dépendent pas du pivot.

Débugger l’apparat. Le contrôle « <app> incomplets (un témoin n’y a pas de leçon) » n’attend pas de leçon d’un témoin dans sa lacune.

Une lacune sans <lacunaEnd/> court jusqu’à la fin du texte. Dans une édition en parties, une lacune peut commencer dans une partie et finir dans une autre ; dans un texte synchronisé à part, seules comptent les lacunes de ce texte. Le viewer web montre les mêmes bandeaux.

Suivre un manuscrit dans son propre ordre

Les flèches ← et → de chaque panneau de témoin mènent l’édition : le témoin avance ou recule dans son propre ordre, et le curseur de l’édition va au passage correspondant, en affichant au besoin la partie ou le texte qui le contient. Les autres témoins suivent le pivot, comme lorsque le curseur bouge. Quand un document auxiliaire est affiché, les flèches feuillettent seulement le témoin.

Témoin synchronisé par lignes. Le panneau passe à la ligne suivante du témoin ; l’édition va à la ligne du pivot que cette ligne désigne. Une ligne non reliée au pivot laisse l’édition sur la ligne reliée qui la précède, et la barre d’état le dit. Le bouton ⤺ ramène le panneau sur la ligne reliée à celle du pivot.

Témoin suivi par pages. Les flèches et la liste des folios mènent l’édition à la page choisie : à la première ligne du témoin sur cette page dans un de ses JSON, sinon à la fin de son <pb edRef="#M" n="45v"/>, sinon au début du texte dont le <locus from> du témoin est cette page. Sans aucun de ces repères, l’édition ne bouge pas et la barre d’état le dit.

D’un texte à l’autre. Au bout d’un texte, les flèches passent au texte suivant dans le manuscrit, qu’il suive la numérotation continue ou qu’il soit synchronisé à part. Le panneau du pivot fait de même : un pivot commun à plusieurs textes se parcourt d’un seul tenant. Une page qui porte la fin d’un texte et le début d’un autre reste affichée. Le panneau d’un témoin absent du texte affiché (« Pas d’alignement de ce témoin pour ce texte. ») mène, par ses flèches, au texte suivant ou précédent qui a ce témoin, dans l’ordre de l’édition.

Ordre des textes dans un manuscrit. Varians le déduit des pages du témoin :

  • la place des pages dans la liste d’images déclarée du témoin (manifeste IIIF ou fichiers, dans Fichier → Paramètres du projet…) ;
  • sinon, les pages communes à ses JSON : chaque JSON est déjà dans l’ordre du manuscrit, et une page qui porte la fin d’un texte et le début d’un autre les relie ;
  • sinon, le <locus from> du témoin pour le texte, ou la foliotation de la première page du texte (un numéro suivi de r ou v), comparée à celle des autres pages ;
  • sinon, le texte garde sa place dans l’ordre de l’édition, et Varians le signale.

Affichage → État des témoins… donne l’ordre des textes dans chaque manuscrit présent dans plusieurs textes, et signale une place incertaine. Pour la rendre sûre, déclarez les images du témoin, ou ajoutez dans son <witness> un <locus from="80r" target="#s04">.

Éditions assemblées (XInclude)

Pour mettre en place un tel projet pas à pas, voir le mode d’emploi.

Une édition peut inclure ses parties, par exemple un fichier par sermon, selon la norme XInclude. L’édition déclarée dans project.xml reste le document maître ; ses parties se déduisent de ses xi:include, sans autre déclaration :

<TEI xmlns="http://www.tei-c.org/ns/1.0"
     xmlns:xi="http://www.w3.org/2001/XInclude">
  …
  <body>
    <xi:include href="sermons/s01.xml"/>
    <xi:include href="sermons/s02.xml" xpointer="s02"/>
    <xi:include href="sermons/s03.xml" xpointer="element(/1/2/1/1)"/>
  </body>

Une partie est soit un fragment (le fichier entier, dont la racine est par exemple le <div> du sermon), soit un élément d’un document TEI complet, désigné par xpointer : son identifiant (s02 ou element(s02)) ou son chemin (element(/1/2/1/1) : TEI, puis son 2ᵉ enfant text, puis body, puis le premier div). Une partie peut elle-même en inclure d’autres. Les chemins relatifs écrits dans une partie partent du dossier de la partie.

Parties et onglets

Chaque partie a son onglet, nommé d’après son fichier, après celui de l’édition et dans l’ordre d’inclusion. Elle s’édite et s’enregistre seule (Ctrl+S), avec son propre historique d’annulation ; avant de quitter, Varians propose d’enregistrer les parties modifiées. La liste des parties est relue à chaque enregistrement de l’édition ou d’une partie. « Renommer l’onglet… » et « Retirer le document du projet » ne concernent que les documents auxiliaires. La Vue XSLT / CSS reste ouverte quand une partie est affichée : elle montre toute l’édition (voir Vue XSLT / CSS de l’édition assemblée) ; les témoins restent eux aussi affichés (voir ci-dessous). Enregistrer l’édition dans un autre dossier romprait les chemins de ses xi:include : Varians le signale avant.

Validation

L’édition et chacune de ses parties font valider l’édition assemblée, avec le schéma de l’édition et en tenant compte des modifications non enregistrées des parties. Le panneau RELAX NG ajoute alors une colonne Document ; un double-clic sur une erreur ouvre la bonne partie à la bonne ligne. L’onglet de chaque partie prend la couleur de ses propres erreurs. Une partie absente ou mal formée, une inclusion circulaire ou une forme non prise en charge (parse="text", xi:fallback, autre schéma xpointer) est signalée à la ligne de son xi:include.

Références et témoins

L’édition et ses parties forment un seul document : un #id se cherche d’abord dans le fichier qui le contient (en-tête compris), puis dans les autres parties. F12, la commande Références et la complétion en tiennent compte. Seuls les identifiants de l’élément inclus d’une partie appartiennent à l’édition assemblée : un témoin déclaré seulement dans le <teiHeader> d’un sermon inclus par xpointer est trouvé par Varians dans ce sermon, mais un outil qui ne lit que l’édition assemblée ne le verra pas. Dans une partie, Aide → Débugger l’apparat… prend les témoins propres à la partie : son <listWit>, sinon les témoins de l’édition dont un <locus target="#s01"> vise la partie, sinon ceux que citent ses @wit.

Synchronisation des témoins

Quand l’édition est découpée en fichiers par commodité (une collection dont les textes se suivent comme dans le témoin pivot), les témoins se synchronisent comme pour une édition en un seul fichier : les lignes du pivot (<lb edRef="#A"/>) sont comptées dans l’ordre de l’édition assemblée, d’une partie à l’autre, et les fichiers d’alignement restent ceux d’aujourd’hui, un par témoin pour toute l’édition. Le curseur de l’édition ou d’une partie fait suivre les témoins ; un clic ou un défilement dans le pivot place le curseur dans la partie qui contient la ligne et ouvre son onglet, même après « Masquer l’onglet ». L’état de structure (barre d’état) compte les lignes du pivot dans toute l’édition assemblée, et l’enregistrement de l’édition ou d’une partie avertit si ce nombre diffère de celui de l’alignement du pivot. Un <lb/> placé dans un commentaire ou hors de l’élément inclus d’une partie ne compte pas, comme dans les autres outils XML.

Condition : le pivot doit contenir ces textes dans l’ordre de l’édition. Varians vérifie le nombre de lignes, pas leur ordre. Les autres témoins peuvent avoir un autre ordre, ou ne pas avoir un texte : leur alignement désigne déjà des lignes du pivot. Un témoin synchronisé par pages suit le dernier <pb> qui le concerne, dans l’ordre de l’édition, même dans une partie précédente : si ce témoin a les textes dans un autre ordre, marquez sa page au début de chaque texte.

Depuis une partie, « Marquer la page » insère le <pb> dans la partie, au curseur, et complète le <facsimile> de l’édition ; « Double page… » écrit ses zones dans le <facsimile> de l’édition. L’édition est alors modifiée sans être affichée : son onglet porte « * ». Annuler dans la partie retire le <pb>, pas les ajouts au <facsimile>.

Textes synchronisés à part

Dans un corpus dont les textes ne sont pas transmis par les mêmes témoins, ni dans le même ordre, un texte peut avoir ses propres alignements : un JSON par témoin, au format habituel, dans un dossier qui porte le nom du fichier du texte, sans extension (alignments/s02/B.json pour xml/sermons/s02.xml). Rien n’est à déclarer : un texte qui a son dossier est synchronisé à part ; les autres suivent la numérotation continue. Le pivot d’un texte est celui du projet, sauf exception déclarée dans project.xml : <part name="s02" base="B"/>.

Quand un tel texte est affiché, les panneaux des témoins prennent ses alignements et son pivot ; la disposition, le zoom et les fenêtres détachées ne changent pas. Un témoin sans JSON pour ce texte garde son panneau, qui indique « Pas d’alignement de ce témoin pour ce texte. ». Les lignes sont comptées dans le texte seul (par exemple « B : 8 lignes ✓ ») ; un clic dans le pivot reste dans le texte. Le diagnostic des témoins et l’actualisation des synchronisations portent sur le texte affiché.

Témoins suivis par pages. Un témoin qui n’a pas de JSON pour ce texte, mais qui l’a — un <pb edRef="#C"/> dans le texte, ou un <locus target="#s04"> dans son <witness> du <listWit> —, y suit ses pages. Avant son premier <pb> dans le texte, il montre sa page de départ : le @from de ce locus (<locus from="13r" to="14r" target="#s04">), sinon la page qui précède celle de ce premier <pb>, dans l’ordre des pages du témoin. « Marquer la page » y fonctionne aussi. Le diagnostic des témoins nomme, pour chaque texte, ses témoins suivis par pages. Les autres témoins sans JSON gardent le message d’absence.

Vue XSLT / CSS de l’édition assemblée

La Vue XSLT / CSS montre toute l’édition, parties comprises, quel que soit le document affiché, et s’utilise comme pour une édition en un seul fichier. Passer de l’édition à une partie ne la quitte pas ; seul l’affichage d’un document auxiliaire la referme.

  • Édition par fragment. Le crayon ✎ d’un paragraphe l’ouvre dans l’éditeur de fragment, tel qu’il est écrit dans le fichier qui le contient ; l’étiquette nomme ce fichier, par exemple « Fragment TEI · paragraphe 7/12 · s03.xml ». Le fragment appliqué est écrit dans ce fichier, même s’il n’est pas affiché ou n’a jamais été ouvert : son onglet porte alors « * », et une seule annulation, dans la partie, retire la modification. Le fichier doit rester bien formé. Ctrl+S dans l’éditeur de fragment enregistre ce fichier, puis le document affiché s’il est modifié ; avant de quitter, Varians propose d’enregistrer un fragment non appliqué avec son fichier.
  • Clic, table des matières, recherche. Un clic sur une ligne place le curseur à cette ligne, dans le fichier qui la contient, dont l’onglet s’ouvre, sans quitter l’aperçu ; les témoins suivent, avec la numérotation propre d’un texte synchronisé à part. La table des matières et la recherche dans l’aperçu font de même.
  • Sélections. Une chaîne sélectionnée dans l’aperçu est sélectionnée, en revenant à l’onglet XML source, dans le fichier qui contient le texte (une partie, ou l’édition), à la même occurrence du même paragraphe ; sans sélection, le curseur va à la ligne affichée. Inversement, la sélection ou la position d’une partie est retrouvée dans l’aperçu. Entre l’aperçu et l’éditeur de fragment, les sélections se répondent comme pour une édition en un seul fichier.
  • Limites. Un paragraphe qui contient lui-même un xi:include s’édite dans le fichier de sa balise ; le texte inclus s’édite dans sa partie. Comme pour une édition en un seul fichier, un paragraphe ou une ligne que la XSLT ne rend pas décale les crayons ou les repères de ligne qui le suivent.

Export web de l’édition assemblée

Générer viewer web exporte toute l’édition, parties comprises, avec les continuités de la fenêtre.

  • Texte et lignes. Le texte des parties est dans le viewer, et les lignes du pivot y sont comptées d’une partie à l’autre, comme dans la fenêtre. Un texte synchronisé à part garde son pivot et ses JSON (alignments/s02/) : quand la ligne choisie y passe, chaque panneau montre son témoin dans ce texte, par ses lignes, par ses pages depuis sa page de départ, ou par « Pas d’alignement de ce témoin pour ce texte. ». Le zoom et les cadres de chaque panneau restent d’un texte à l’autre. Les boutons de l’en-tête parcourent toutes les lignes dans l’ordre de lecture, d’un texte à l’autre.
  • Flèches des panneaux. Comme dans la fenêtre, les flèches ← → de tout panneau mènent le texte dans l’ordre propre du manuscrit, d’une partie ou d’un texte à l’autre, et la liste des folios d’un témoin suivi par pages aussi ; ⤺ ramène le panneau sur la ligne reliée. Les messages de la barre d’état de la fenêtre (début ou fin du manuscrit, ligne non reliée, page non située, place incertaine) s’affichent sous le titre du viewer.
  • Lacunes. Les bandeaux sont ceux de la fenêtre (voir Lacunes des témoins) : une lacune continue d’une partie à l’autre, et un texte synchronisé à part repart sans lacune.
  • Enregistrement. L’export lit les fichiers enregistrés : Varians enregistre d’abord l’édition, chaque partie modifiée et le fragment non appliqué d’une partie ; si l’un d’eux ne peut l’être, l’export est annulé. Une partie introuvable, ou une inclusion non prise en charge (parse="text", xi:fallback), est signalée dans le compte rendu de l’export : le texte concerné manque dans le viewer.
  • Limites. La position retenue est celle du fragment de texte cliqué. Un <pb> ou un <lb> placé dans une leçon non retenue ou dans une note n’est pas vu par le viewer. « État des témoins… », « Actualiser les synchronisations… », « Marquer la page » et « Double page… » restent propres à la fenêtre. Régénérez le viewer après une modification de l’édition.

Limites de cette version

L’ordre des textes dans un manuscrit est déduit de ses pages ; un texte qui ne s’y rattache pas garde sa place dans l’ordre de l’édition (voir Suivre un manuscrit dans son propre ordre). L’export web a ses propres limites : voir Export web de l’édition assemblée. Un projet sans xi:include n’est pas concerné.

Mettre en place une édition en parties (XInclude) : mode d’emploi

Ce mode d’emploi décrit, pas à pas, comment organiser un projet dont l’édition est découpée en plusieurs fichiers, par exemple un fichier par sermon. Le détail de chaque fonction se trouve dans Éditions assemblées (XInclude).

1. Organiser les fichiers

Gardez un seul fichier d’édition, celui que déclare project.xml (par exemple xml/edition.xml) : c’est le document maître, avec l’en-tête, la liste des témoins et l’ordre des textes. Rangez les textes dans un dossier voisin, un fichier par texte. Donnez à chaque fichier un nom unique dans tout le projet : ce nom, sans extension, sert aussi au dossier d’alignements d’un texte synchronisé à part (étape 4). Les chemins sont relatifs au fichier qui les contient : sermons/s01.xml depuis l’édition, ../personnes.xml#augustinus depuis un sermon.

project.xml
alignments/T1.json, T2.json …
alignments/s02/B.json, D.json
xml/edition.xml
xml/sermons/s01.xml, s02.xml, s03.xml …

2. Écrire les xi:include

Déclarez l’espace de noms XInclude sur l’élément racine de l’édition, puis placez un xi:include à l’endroit de chaque texte :

<TEI xmlns="http://www.tei-c.org/ns/1.0" xmlns:xi="http://www.w3.org/2001/XInclude">
  …
  <body>
    <xi:include href="sermons/s01.xml"/>
    <xi:include href="sermons/s02.xml" xpointer="s02"/>
  </body>
</TEI>

Un texte est soit un fragment : le fichier entier, dont la racine est l’élément inclus et porte l’espace de noms TEI (<div xmlns="http://www.tei-c.org/ns/1.0" xml:id="s01">) ; soit un document TEI complet, dont on n’inclut qu’un élément, par son identifiant (xpointer="s02") ou par son chemin (xpointer="element(/1/2/1/1)"). Un document complet peut aussi être validé seul ; son en-tête n’entre pas dans l’édition. Un texte peut lui-même en inclure un autre. N’utilisez ni parse="text" ni xi:fallback : Varians les signale sans les prendre en charge. Enregistrez l’édition : chaque texte reçoit son onglet.

3. Déclarer les témoins

Déclarez chaque manuscrit une seule fois, dans Fichier → Paramètres du projet…, avec un sigle commun à toute la collection. Dans le TEI, déclarez les témoins dans le <listWit> de l’édition, dans celui de chaque texte (document TEI complet), ou dans les deux. Un témoin déclaré seulement dans l’en-tête d’un texte inclus par xpointer est trouvé par Varians, mais un outil qui ne lit que l’édition assemblée ne le voit pas.

4. Choisir la synchronisation de chaque texte

  • Les textes se suivent comme dans le pivot, avec les mêmes témoins (une collection découpée par commodité) : numérotation continue. Un JSON par témoin pour toute l’édition, comme pour une édition en un seul fichier, déclaré dans les paramètres du projet. Les lignes du pivot sont comptées d’un texte à l’autre, dans l’ordre de l’édition ; le pivot doit contenir les textes dans cet ordre.
  • Les témoins changent d’un texte à l’autre (un corpus) : texte synchronisé à part. Créez le dossier alignments/<nom du fichier du texte>/ et placez-y un JSON par témoin pour ce texte, au format habituel : alignments/s02/B.json, alignments/s02/D.json. Produisez ces JSON avec VariansSynchro sur le fichier du texte. Il n’y a rien à déclarer : le dossier suffit. Un témoin sans JSON pour ce texte, mais qui y a ses <pb edRef> ou un <locus target> dans son <witness>, y suit ses pages : voir Textes synchronisés à part.
  • Les deux peuvent se mêler : les textes qui ont leur dossier sont synchronisés à part ; les autres suivent la numérotation continue, et le JSON global de chaque témoin ne contient que leurs lignes.

5. Déclarer un pivot propre à un texte

Le pivot d’un texte synchronisé à part est celui du projet. Si le pivot du projet n’a pas ce texte, ou si un autre témoin doit servir de référence, écrivez l’exception à la main dans project.xml, avant </teiManuscriptProject>, puis rouvrez le projet :

<parts>
  <part name="s02" base="B"/>
</parts>

name est le nom du fichier du texte, sans extension ; base, le sigle du pivot. Les lignes de ce texte sont alors ses <lb edRef="#B"/>, et son dossier doit contenir B.json. Varians garde cet élément quand on enregistre les paramètres du projet.

6. Vérifier

  • Affichez chaque texte : l’état de structure, dans la barre d’état, doit être juste, par exemple « B : 8 lignes ✓ » ; sa bulle d’aide dit si le compte porte sur l’édition assemblée ou sur un texte synchronisé à part.
  • Affichage → État des témoins… indique la portée (l’édition ou le texte affiché), les textes synchronisés à part avec leur pivot et leurs témoins, et les problèmes : JSON d’un témoin non déclaré, pivot inconnu, JSON du pivot manquant…
  • La validation RELAX NG porte sur l’édition assemblée ; la colonne Document indique le fichier de chaque erreur.
  • La commande Références vérifie les renvois d’un texte à l’autre.
  • Un autre outil XML assemble le projet sans Varians : xmllint --xinclude --noout xml/edition.xml, ou oXygen avec XInclude activé dans les préférences du validateur.
  • Affichage → État des témoins… donne aussi l’ordre des textes dans chaque manuscrit ; une place incertaine y est signalée : voir Suivre un manuscrit dans son propre ordre.

7. Au quotidien

  • Chaque texte s’édite dans son onglet et s’enregistre seul (Ctrl+S) ; avant de quitter, Varians propose d’enregistrer les textes modifiés.
  • Pour ajouter un texte : créez son fichier, ajoutez son xi:include dans l’édition, enregistrez l’édition ; son onglet apparaît. Pour un texte synchronisé à part, ajoutez aussi son dossier d’alignements, puis Affichage → Actualiser les synchronisations….
  • S’il y a beaucoup d’onglets : clic droit sur un onglet → Masquer l’onglet ; un clic dans le pivot fait réapparaître l’onglet du texte voulu.
  • Enregistrer l’édition dans un autre dossier romprait ses xi:include : Varians le signale avant.
  • La Vue XSLT / CSS montre toute l’édition : le crayon ✎ y ouvre un paragraphe de n’importe quel texte, et un clic y mène au texte qui contient la ligne ; voir Vue XSLT / CSS de l’édition assemblée. L’export web contient toute l’édition ; voir Export web de l’édition assemblée.
  • Pour lire un manuscrit d’un texte à l’autre, utilisez les flèches de son panneau : l’édition affiche le bon texte.

Scénarios de transformation XSLT

Un scénario de transformation applique une feuille XSLT à l’édition ou à un autre document du projet, et écrit le résultat dans un fichier : édition HTML, index, liste de citations, XML transformé… Il est nommé, enregistré dans le projet, et se rejoue à l’identique. Le viewer web reste une publication à part, qu’un scénario ne modifie pas.

Fichier → Scénarios de transformation… montre deux groupes :

  • Scénarios du projet, enregistrés dans project.xml (élément <transformations>) : Ajouter…, Modifier…, Dupliquer… et Supprimer les gèrent.
  • Scénarios prédéfinis, fournis par Varians : pour l’instant Édition HTML (feuille de Varians), qui publie l’édition avec la feuille et la CSS de l’aperçu de Varians dans publications/edition.html. On peut l’exécuter tel quel, ou le dupliquer dans le projet pour l’adapter.

Chaque ligne indique la source, le moteur et, en rouge, ce qui empêche le scénario de s’exécuter (feuille introuvable, Saxon non installé…). Exécuter lance le scénario choisi ; Aperçu l’exécute dans un dossier temporaire et ouvre le résultat, sans toucher au fichier du scénario.

Un scénario

  • Source : Édition (l’édition du projet, assemblée si elle a des parties : chaque partie garde son emplacement, et un document() relatif y trouve ses fichiers), Document affiché (le document de l’onglet courant, par exemple un document auxiliaire, voir Documents XML auxiliaires ; l’édition assemblée si c’est elle) ou Fichier (un fichier lu tel quel).
  • Moteur : XSLT 1.0 (lxml), ou XSLT 3.0 (Saxon) pour les feuilles en XSLT 2.0 ou 3.0. Saxon-HE (paquet saxonche) s’installe avec Varians : installer_dependances.bat, ou pip install -r requirements.txt.
  • Feuille XSLT et CSS facultative : chemins relatifs au projet ; ${varians}/ désigne les feuilles fournies avec Varians. La CSS est copiée à côté du résultat, et son nom est passé à la feuille par le paramètre css (la feuille de Varians le met dans son <link>). Un nouveau scénario propose la feuille et la CSS de l’aperçu.
  • Résultat : le fichier écrit, remplacé à chaque exécution (publications/<nom>.html est proposé). Il ne peut pas être une source du projet (project.xml, l’édition et ses parties, un document, une feuille, un schéma, un JSON d’alignement). Avec Saxon, une feuille peut écrire d’autres fichiers par xsl:result-document (une page par sermon, par exemple), dans le dossier du résultat et ses sous-dossiers seulement ; ailleurs, l’exécution est refusée.
  • Paramètres : des paires nom / valeur, passées à la feuille comme chaînes de caractères (<xsl:param name="titre"/>).

Exécution

Le bouton Transformer, à côté de Générer viewer web, relance le dernier scénario exécuté dans le projet (aussi Ctrl+Shift+T) ; sa flèche donne la liste des scénarios. Avant l’exécution, Varians enregistre ce que le scénario lit : l’édition, ses parties modifiées et le fragment non appliqué, comme pour l’export web, ainsi que le document source, la feuille et la CSS s’ils sont ouverts et modifiés. La transformation tourne dans un processus à part : Varians reste utilisable, et Annuler l’arrête.

Le compte rendu donne les fichiers écrits et la durée ; Ouvrir ouvre le résultat dans l’application par défaut (le navigateur, pour du HTML). Ses détails donnent le journal : moteur et version, paramètres, xsl:message, lectures réseau (avec lxml), écritures refusées. En cas d’erreur, le message indique le fichier et la ligne en cause, et le résultat précédent reste intact.

Sécurité : une feuille peut lire tout fichier local, et des adresses http ou https (le résultat peut alors dépendre d’un serveur) ; elle n’écrit que son résultat (et, avec Saxon, des fichiers de son dossier). Les entités externes des sources ne sont pas lues.

Éditer une feuille XSLT

Une feuille XSLT est un document XML : Varians l’ouvre comme un document du projet, dans son propre onglet (voir Documents XML auxiliaires), la vérifie et aide à l’écrire, sans outil extérieur.

  • Ajouter une feuille : Fichier → Documents XML du projet → Ajouter un document XML ou XSLT… accepte les fichiers .xsl et .xslt. Une feuille située hors du dossier du projet y est copiée, dans le dossier xslt/ (au même niveau que xml/), sans jamais remplacer un fichier existant ; une feuille déjà dans le projet reste où elle est.
  • Nouvelle feuille XSLT… (même menu) crée une feuille minimale, en XSLT 1.0 (lxml) ou en XSLT 3.0 (Saxon), proposée dans xslt/ : espace de noms TEI déclaré, sortie HTML, un modèle pour la racine du document.
  • Depuis les scénarios (voir Scénarios de transformation XSLT) : Ouvrir la feuille, dans la liste des scénarios ou dans la boîte d’un scénario (qui est alors enregistré), affiche la feuille d’un scénario du projet. Une feuille fournie avec Varians (${varians}/…) est d’abord copiée dans xslt/ ; une feuille hors du projet peut l’être aussi, ou s’ouvrir sans copie. Après une copie, le scénario emploie la copie. Pour un scénario prédéfini, utilisez d’abord Dupliquer….

Vérification. Pour une feuille, Vérifier la feuille XSLT (F8, à la place de Valider RNG) la compile sans l’exécuter, avec le moteur des scénarios du projet qui l’emploient (les deux s’ils diffèrent) ; une feuille qu’aucun scénario n’emploie est vérifiée d’après sa version : version="1.0" par lxml, une autre par Saxon. Comme pour la validation RELAX NG, la feuille est vérifiée à son premier affichage, après chaque modification une fois F8 utilisé, et à l’enregistrement, qui demande confirmation si elle a des erreurs. Le panneau de validation donne chaque erreur avec sa ligne ; un double-clic y mène. Une erreur dans une feuille importée (xsl:import) ou incluse (xsl:include) nomme son fichier dans la colonne Document, et le double-clic mène à cette feuille si elle fait partie du projet. La barre d’état indique le résultat, et l’onglet de la feuille se colore comme celui d’un document non valide.

Complétion. Ctrl+Espace propose les éléments et attributs XSLT permis à cet endroit, avec le préfixe de la feuille (xsl:), et la liste des attributs s’ouvre pendant la frappe. Dans un élément du résultat (<div>, <tei:p>…), ce sont les instructions XSLT et les attributs xsl:*. Une feuille version="1.0" ne reçoit que les éléments et attributs d’XSLT 1.0. Les propositions viennent du schéma RELAX NG d’XSLT 3.0 du W3C, fourni avec Varians (licence BSD) ; les éléments personnalisés du projet (custom-elements.xml) ne sont pas proposés dans une feuille.

Fichiers annexes. Varians ne copie que la feuille elle-même. Les fichiers dont elle a besoin pour que le résultat soit complet (feuilles importées par xsl:import ou incluses par xsl:include, images, CSS, JavaScript…) sont à placer vous-même dans le dossier xslt/ du projet, en gardant les chemins relatifs qu’emploie la feuille. La vérification signale une feuille importée ou incluse introuvable. La CSS d’un scénario, elle, est copiée automatiquement à côté du résultat.

Limites : une feuille faite pour être importée ou incluse est vérifiée seule, et ses renvois à des déclarations de la feuille principale peuvent être signalés comme erreurs ; une feuille XSLT 2.0 reçoit les propositions d’XSLT 3.0 ; les noms déclarés dans la feuille (modèles, modes, clés) et les expressions XPath ne sont pas complétés.

Version 0.9.0.0 — éditions assemblées (XInclude)

Une édition peut inclure ses parties par XInclude : chaque partie a son onglet, la validation porte sur l’édition assemblée et indique le fichier de chaque erreur, les références et la complétion vont d’une partie à l’autre ; voir Éditions assemblées (XInclude). La synchronisation des témoins est suspendue pour une telle édition. Un projet sans xi:include, ses données et le format de project.xml sont inchangés.

Version 0.9.1.0 — synchronisation des témoins à travers les parties

Pour une édition assemblée par XInclude, les témoins se synchronisent de nouveau : les lignes du pivot sont comptées dans l’ordre de l’édition assemblée, le curseur d’une partie fait suivre les témoins, et le pivot ouvre la partie qui contient une ligne ; les témoins restent affichés sur une partie, où « Marquer la page » et « Double page… » sont disponibles ; voir Éditions assemblées (XInclude). Un projet sans xi:include, ses données et le format de project.xml sont inchangés.

Version 0.9.1.1 — textes synchronisés à part

Dans une édition en parties, un texte qui a son dossier d’alignements (alignments/s02/, un JSON par témoin) est synchronisé à part, avec son propre pivot si project.xml le déclare (<part name="s02" base="B"/>) ; un témoin sans JSON pour ce texte l’indique dans son panneau. Un mode d’emploi décrit la mise en place d’une édition en parties : voir Mettre en place une édition en parties. Un projet sans dossier par texte est inchangé.

Version 0.9.1.2 — sélections partagées entre l’aperçu et l’éditeur de fragment

Dans la Vue XSLT / CSS, le crayon ✎ ouvre un paragraphe dans l’éditeur de fragment sans déplacer les images des témoins. Une chaîne sélectionnée dans l’aperçu est sélectionnée dans l’éditeur de fragment ouvert, et inversement : voir Édition XML et aperçu XSLT/CSS. Le report d’une sélection entre la source XML et l’aperçu reste inchangé (édition sans parties). Les lacunes, les témoins synchronisés par pages dans un texte synchronisé à part et le parcours d’un manuscrit dans son propre ordre viendront en version 0.9.1.3.

Version 0.9.1.3 — lacunes, témoins suivis par pages dans un texte synchronisé à part

Les lacunes des témoins (<lacunaStart/> … <lacunaEnd/>) sont reconnues : le panneau d’un témoin en lacune garde la ligne ou la page où son texte s’interrompt, avec un bandeau ; pendant une lacune du pivot, les lignes ne sont plus synchronisées ; voir Lacunes des témoins. Dans un texte synchronisé à part, un témoin qui a le texte sans en avoir de JSON y suit ses pages, depuis sa page de départ (<locus from>). Le parcours d’un manuscrit dans son propre ordre viendra en version 0.9.1.4.

Version 0.9.1.4 — suivre un manuscrit dans son propre ordre

Les flèches de tout panneau de témoin mènent désormais l’édition, et non plus seulement celles du pivot : le témoin est suivi dans son propre ordre, d’une partie ou d’un texte à l’autre, y compris un témoin suivi par pages (flèches et liste des folios) ; le pivot passe d’un texte synchronisé à part au suivant. L’ordre des textes dans chaque manuscrit est déduit de ses pages et figure dans « État des témoins… » ; voir Suivre un manuscrit dans son propre ordre. Feuilleter un témoin sans déplacer l’édition n’est plus possible que lorsqu’un document auxiliaire est affiché.

Version 0.9.1.5 — Vue XSLT / CSS d’une édition assemblée

Dans une édition en parties, la Vue XSLT / CSS n’est plus en lecture seule : le crayon ✎ ouvre un paragraphe dans le fichier qui le contient et y écrit le fragment appliqué, un clic sur une ligne mène au bon fichier et fait suivre les témoins, et les sélections passent de l’aperçu à la partie qui contient le texte, et inversement ; voir Vue XSLT / CSS de l’édition assemblée. L’aperçu reste ouvert quand une partie est affichée. L’export web de l’édition assemblée viendra dans une prochaine version. Une édition en un seul fichier est inchangée.

Version 0.9.1.6 — export web d’une édition assemblée

Le viewer web d’une édition en parties contient désormais toute l’édition, avec les continuités de la fenêtre : le texte des parties, la numérotation continue des lignes, les textes synchronisés à part, les lacunes et le parcours de chaque manuscrit dans son propre ordre ; voir Export web de l’édition assemblée. Avant l’export, l’édition, ses parties modifiées et le fragment non appliqué d’une partie sont enregistrés, sans autre question. Pour une édition en un seul fichier aussi, les flèches de tout panneau et la liste des folios mènent désormais le texte, et les lacunes ont leurs bandeaux ; voir Viewer web. Régénérez le viewer pour en bénéficier.

Version 0.9.1.7 — onglets des documents

L’onglet du document affiché se distingue nettement des autres : fond blanc, filet bleu en haut, nom en gras ; les autres onglets sont en retrait, sur un fond plus sombre. La couleur d’un document mal formé (rouge) ou non valide (orange) reste visible, même sur l’onglet courant ; voir Documents XML auxiliaires.

Version 0.9.2.0 — scénarios de transformation XSLT

Des scénarios de transformation nommés, enregistrés dans le projet, appliquent une feuille XSLT 1.0 (lxml) ou 3.0 (Saxon) à l’édition, au document affiché ou à un fichier, et écrivent le résultat : Fichier → Scénarios de transformation…, bouton Transformer, Ctrl+Shift+T ; voir Scénarios de transformation XSLT. Saxon s’installe désormais avec Varians (installer_dependances.bat).

Version 0.9.2.1 — éditer les feuilles XSLT

Les feuilles XSLT s’ajoutent au projet, dans le dossier xslt/, se créent (Nouvelle feuille XSLT…) et s’ouvrent depuis leurs scénarios (Ouvrir la feuille) ; Varians les vérifie en les compilant (F8) et complète leurs éléments et attributs (Ctrl+Espace) ; voir Éditer une feuille XSLT. Ctrl+Espace complète aussi, dans tout document, un nom d’élément tapé juste devant une autre balise (<h devant </p>). Le format de project.xml est inchangé.
