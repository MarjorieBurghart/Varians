Varians — Éditeur XML TEI pour l’ecdotique

Varians est un éditeur XML pour l’édition critique de textes transmis par des manuscrits ou éditions anciennes, encodés en TEI. Il réunit dans une même interface la transcription, les images des témoins et une vue de lecture, et permet de transformer l’édition au format web.

1. Présentation

Ce que Varians permet de faire

  • Éditer la TEI. Un éditeur XML qui complète les éléments et les attributs d’après le schéma, aide au balisage, cherche dans le texte (expressions régulières, XPath), suit les références entre documents, replie et indente sans abîmer le texte.
  • Valider le XML. RELAX NG et règles Schematron, pendant la frappe, sans figer la fenêtre.
  • Lire ce qu’on édite. La Vue XSLT / CSS montre l’édition mise en forme ; chaque bloc s’y ouvre pour être corrigé dans un éditeur de fragment. L’onglet XML source, ouvert par défaut, donne toujours accès au code XML brut.
  • Voir les manuscrits. Les images de chaque témoin (fichiers locaux ou IIIF), avec éventuellement leurs lignes (ALTO, PAGE XML), sont alignées avec la transcription, page par page ou ligne par ligne selon les données disponibles.
  • Contrôler l’apparat. Des requêtes prêtes à l’emploi trouvent les erreurs fréquentes d’un apparat critique (témoin oublié ou redondant par exemple) ; les lacunes des témoins sont reconnues.
  • Publier. Un viewer web autonome, où le texte et les fac-similés restent synchronisés ; une édition critique HTML avec son apparat ; du DOCX, de l’ODT, de l’EPUB, du HTML, du LaTeX… par les TEI Stylesheets, fournies avec Varians ; et toute feuille XSLT de votre choix.

Ce qui le distingue d’un éditeur XML généraliste

Un éditeur XML généraliste traite tout document XML de la même façon. Varians part du travail de l’éditeur de textes :

  • Les manuscrits à côté du texte. Chaque témoin a son panneau. Quand le curseur bouge dans la transcription, chaque panneau montre la page, ou la ligne, correspondante de son manuscrit. Inversement, on peut lire l’édition selon l’ordre d’un manuscrit particulier : les flèches de son panneau mènent l’édition au passage correspondant.
  • Un témoin pivot. La synchronisation repose sur les lignes d’un témoin de référence, appelé ici le pivot ; chaque autre témoin peut aligner ses propres lignes sur celles du pivot, visuellement, avant même d’avoir commencé à transcrire. Le choix d’un témoin pivot est technique, pour l’alignement : il ne préjuge ni du stemma ni du manuscrit de base qui sera retenu.
  • L’apparat au centre. Complétion des @wit d’après la liste des témoins, contrôles de l’apparat, lacunes, et, à la publication, choix entre le texte établi et la transcription d’un témoin particulier ; les leçons qui ne viennent pas encore d’un <lem> peuvent être surlignées.
  • Une vue de lecture qui s’édite. On corrige l’édition là où on la lit, bloc par bloc, sans perdre sa place dans le XML.
  • Une édition possible en plusieurs fichiers (un fichier par texte, assemblés par XInclude) est traitée comme un seul document : validation, références, synchronisation des témoins, publication.
  • Une publication web intégrée. Le viewer web, une XSLT paramétrable reprenant les codes de l’édition critique, et les formats des TEI Stylesheets sont disponibles dans Varians, sans serveur ni réseau.
  • Une TEI standard. Varians n’écrit dans vos fichiers que de la TEI ordinaire (<pb/>, <lb/>, <facsimile>…). Ce qui ne concerne que le projet (témoins, images, alignements, scénarios) est dans un fichier distinct project.xml ; vos préférences d’affichage restent sur votre ordinateur. Tout autre outil XML peut lire votre édition.
  • La prudence. Varians ne devine pas : une correspondance douteuse entre une ligne et une image, une fermeture de balise ambiguë, une page introuvable ne sont jamais inventées, mais signalées. Les écritures importantes gardent une copie .bak.
  • Sept langues d’interface : français, anglais, allemand, japonais, tchèque, italien et russe (Affichage → Langue).

Ce que Varians ne fait pas

  • Il n’aligne pas lui-même les lignes des manuscrits : les fichiers d’alignement (JSON) viennent de Varians-Synchro, un outil à part.
  • Il ne reconnaît pas les lignes sur les images (segmentation) : les lignes ALTO ou PAGE XML viennent d’un logiciel de reconnaissance (eScriptorium, Transkribus, PERO OCR…).
  • Il ne collationne pas : l’apparat est encodé dans la TEI par vos soins ; Varians aide à le saisir et à le vérifier.
  • Ce n’est pas un traitement de texte : on édite le XML ; la Vue XSLT / CSS sert à lire et à corriger un bloc à la fois.

2. Démarrage rapide

Ce parcours mène d’un dossier vide à une première publication. Chaque étape renvoie au chapitre qui la détaille.

  1. Installer et lancer. Varians requiert Python 3 et trois bibliothèques (PySide6, lxml et Saxon). Sous Windows, exécutez une fois installer_dependances.bat, puis lancez Varians par lancer_editeur.bat. Ailleurs : pip install -r requirements.txt, puis python editeur_tei.py.
  2. Créer le projet. Fichier → Nouveau projet… : choisissez un dossier vide, puis le Point de départ, Partir d’une édition TEI existante (votre fichier est copié dans le projet) ou Commencer une nouvelle transcription (Varians crée une TEI minimale). Voir Projets.
  3. Déclarer les témoins. Sous Témoins et ressources, Ajouter… chaque manuscrit : son Sigle, son Nom affiché, la Source des images (vous avez le choix entre : aucune pour le moment, des images locales ou un Manifest IIIF). Désignez le pivot : Définir comme témoin pivot. Le reste peut venir plus tard. Voir Notions clés et Témoins et fac-similés.
  4. Transcrire et baliser. Dans l’onglet XML source, Ctrl+E entoure la sélection d’un élément, Ctrl+Espace complète un nom d’élément ou d’attribut, F8 valide le document. Dans l’onglet Vue XSLT / CSS, cliquez sur le crayon ✎ d’un bloc, ou sélectionnez un passage à modifier et tapez F2, pour ouvrir ce passage dans l’éditeur de fragment ; Appliquer au XML met la source à jour. Voir Éditer le XML et Valider.
  5. Relier le texte aux images. Placez le curseur, dans le texte, au début d’une page (par ex. f. 1v) d’un témoin (par ex. A1), et cliquez Marquer la page dans le panneau de ce témoin : Varians insère un <pb n="1v" edRef="#A1" facs="#A1-p0002"/>. Le panneau suit désormais le texte, page par page. Pour le suivre ligne par ligne, déclarez le fichier d’alignement (JSON) du témoin dans Fichier → Paramètres du projet…. Voir Témoins et fac-similés.
  6. Encoder et vérifier l’apparat. Dans un @wit, tapez # pour choisir un témoin dans la liste. Aide → Débugger l’apparat… trouve les témoins sans leçon ou cités deux fois. Voir Apparat critique.
  7. Relire. L’onglet Vue XSLT / CSS montre l’édition mise en forme ; le crayon ✎ ouvre un bloc pour le corriger. Voir Vue XSLT / CSS et éditeur de fragment.
  8. Format web. Générer viewer web crée un site autonome dans web_output/, texte et images synchronisés. Le bouton Transformer exécute un scénario : Édition critique (HTML), TEI : DOCX (Word)… Voir Viewer web et Publier avec XSLT.
  9. Enregistrer. Ctrl+S enregistre le document affiché ; avant de quitter ou de changer de projet, Varians propose d’enregistrer chaque document modifié.

3. Notions clés

Le projet

Un projet est un dossier qui contient un fichier project.xml. Celui-ci nomme l’édition, ses témoins et leurs ressources (images, lignes, alignements), la feuille de l’aperçu, les scénarios de publication. L’édition elle-même est un fichier TEI, xml/edition.xml, qui peut être découpé en parties (voir Éditions en parties). D’autres documents peuvent s’y ajouter : autorités, notes, feuilles XSLT, règles Schematron.

Trois sortes de données, trois lieux. Ce qui relève du texte est dans la TEI : pages, lignes, apparat, fac-similé. Ce qui relève du projet est dans project.xml : témoins, images, alignements, scénarios, requêtes enregistrées. Vos préférences de travail (témoins affichés et leur disposition, onglets visibles…) restent sur votre ordinateur, propres à chaque projet, sans modifier aucun fichier du projet.

Témoins, sigles et témoin pivot

Un témoin est un manuscrit, ou un imprimé, qui transmet le texte. Son sigle (A, T1, P…) le désigne partout. Dans la TEI, c’est l’identifiant de son <witness> dans la <listWit>, que citent @wit (dans l’apparat) et @edRef (pages et lignes propres à ce témoin) ; voir Sigle et identifiant d’un témoin.

Le témoin pivot est la référence de la synchronisation : ses lignes (<lb edRef="#A"/>) marquent les limites dans le texte, et chaque autre témoin relie ses propres lignes à celles du pivot. Ce choix est technique : il ne préjuge ni de la place du témoin dans le stemma, ni du manuscrit qui sera retenu comme manuscrit de base par l’édition. Dans une édition en parties, une partie peut avoir son propre pivot.

Suivre un témoin par pages ou par lignes

Le panneau d’un témoin suit la transcription de l’une de deux façons :

  • par pages : un <pb edRef="#B" .../> marque le début de chaque page du témoin B dans la transcription ; le panneau montre la page du dernier <pb> de B avant le curseur. Des images et des <pb> avec le bon @edRef suffisent ;
  • par lignes : un fichier d’alignement (JSON), produit par Varians-Synchro, relie chaque ligne du manuscrit, repérée sur l’image par ALTO ou PAGE XML, à une ligne du pivot. Le panneau montre alors la ligne correspondante, recadrée. Pour voir l’édition alignée sur les images des manuscrits, il faut avoir inséré les <lb/> du témoin pivot, et seulement les siens : les autres témoins sont alignés grâce à eux, sans que leurs propres <lb/> soient insérés dans l’édition.

Chaque témoin a son propre mode : dans une même édition, certains peuvent être suivis par lignes, d’autres par pages. D’autres peuvent ne pas avoir encore d’images numériques.

L’apparat critique

Varians attend un apparat en parallel segmentation : chaque lieu variant est, dans le texte, un <app> qui réunit la leçon retenue (<lem>) et les variantes (<rdg>), chacune avec les témoins qui la portent :

<app><lem wit="#A">dixit</lem><rdg wit="#B #C">ait</rdg></app>

Il est normal de procéder par étapes lors d’un travail d’édition : on enregistre souvent d’abord les variantes de manière neutre, pour décider ensuite, lorsqu’on aura une meilleure vision de la tradition, ce que l’on va retenir comme lemme :

<app><rdg wit="#A">dixit</rdg><rdg wit="#B #C">ait</rdg></app>

Varians permet de visualiser le travail avant même d’avoir choisi tous les lemmes. Ainsi, le texte établi de l’Édition critique (HTML) et du viewer web est fait en priorité des <lem> ; là où il n’y en a pas, de la leçon d’un témoin choisi, par défaut le pivot. L’une et l’autre peuvent surligner en jaune les leçons qui ne viennent pas d’un <lem>, celles qui restent à trancher (voir Choix du texte et Édition critique).

4. Projets

Créer, ouvrir, fermer

Au premier lancement, Varians n’ouvre aucun projet ; ensuite, il rouvre celui qui était ouvert à la fermeture. Le menu Fichier propose Nouveau projet… (Ctrl+N), Ouvrir un projet… (Ctrl+O) et Réouvrir un projet récent…. Fichier → Fermer le projet (Ctrl+W) revient à l’écran d’accueil sans quitter Varians ; le projet fermé n’est pas rouvert au lancement suivant.

Nouveau projet… demande un dossier vide, puis le Point de départ : Partir d’une édition TEI existante, dont le fichier est copié dans xml/edition.xml, ou Commencer une nouvelle transcription : Varians crée une TEI minimale, avec la <listWit> des témoins du projet.

<listWit>
  <witness xml:id="A1">Assisi, Sacro convento, 541</witness>
</listWit>

Un témoin peut être déclaré sans image, sans ALTO et sans synchronisation : ces ressources s’ajoutent éventuellement plus tard, dans n’importe quel ordre, dans Fichier → Paramètres du projet…. La même boîte règle le schéma RELAX NG (détecté d’après le <?xml-model?> du document, choisi dans le projet, ou aucun), la feuille XSLT et la CSS de l’aperçu, la configuration de Ctrl+E (custom-elements.xml), le dossier et le nom du fichier du viewer web.

Structure d’un projet

project.xml        le projet
xml/edition.xml    l’édition (ses parties et les autres documents XML, à côté)
xslt/              les feuilles XSLT du projet
images/  alto/     images locales, lignes ALTO ou PAGE XML copiées dans le projet
alignments/        fichiers d’alignement (JSON)
iiif/local/        copies locales des images IIIF
rendering/         CSS de l’aperçu, custom-elements.xml
i18n/              traductions de l’interface
publications/      résultats des scénarios de transformation
web_output/        viewer web

Le dossier i18n/ d’un projet contient une copie des traductions de l’interface, qui l’emporte sur celle de Varians : pour adopter les textes d’une nouvelle version de Varians, remplacez ses fichiers par ceux du dossier i18n/ de Varians.

Sigle et identifiant d’un témoin. Le sigle d’un témoin, saisi dans Fichier → Paramètres du projet…, lui sert aussi d’identifiant XML : xml:id de son <witness>, cible de @wit et de @edRef. Un identifiant XML commence par une lettre ou « _ » et ne contient ni espace ni signe comme « / » ou « : ». Si le sigle saisi ne respecte pas ces règles (« 1760 », « T 2 »), Varians en tire un identifiant valide, montré sous le champ : chaque caractère interdit devient « _ », et un « _ » est ajouté devant un sigle qui ne commence pas par une lettre ; « 1760 » donne _1760, « T 2 » donne T_2. Dans la TEI, on écrit alors wit="#_1760". Le sigle reste ce que Varians affiche partout où il nomme le témoin ; il est gardé dans project.xml (attribut siglum du <witness>) et, dans la TEI créée avec le projet, dans un <idno type="siglum"> :

<witness xml:id="_1760"><idno type="siglum">1760</idno>Troyes, BM, ms. 1760</witness>

Les feuilles livrées avec Varians (aperçu, Édition critique, apparat en notes) et le viewer web montrent ce sigle à la place de l’identifiant. Un témoin ajouté plus tard, dans Fichier → Paramètres du projet…, reçoit un <witness> de la même forme à la fin de la <listWit> de l’édition, si elle existe : Varians n’en crée pas. La boîte qui confirme l’enregistrement des paramètres dit ce qui a été ajouté. Deux sigles qui donneraient le même identifiant (« T 2 » et « T/2 ») ne peuvent pas coexister.

Préparer une transcription vide d’après le témoin pivot

Pour commencer une transcription, Varians peut pré-renseigner les pages (<pb/>) et les lignes (<lb/>) du témoin pivot. Dans Fichier → Nouveau projet… (avec Commencer une nouvelle transcription) ou dans Fichier → Paramètres du projet…, l’encadré Préparation de la transcription du témoin pivot propose Préparer les <pb/> du témoin pivot dans la TEI vide, puis Générer aussi les <lb/> depuis ALTO, PAGE ou la synchronisation.

Seules les pages retenues pour l’édition reçoivent un <pb/> : son @facs désigne la <surface>, son @edRef le témoin. Les <lb/> ne portent que @edRef. Varians prend les lignes ALTO ou PAGE associées avec certitude à la page, sinon les lignes décrites dans le fichier d’alignement : un extrait de folio qui va de la ligne 41 à la ligne 68 donne 28 <lb/>. Une page sans ligne connue garde son <pb/> ; les lacunes sont signalées, jamais comblées. Un aperçu, une confirmation et une sauvegarde datée protègent le texte ; aucune transcription automatique n’est importée.

Documents du projet et onglets

Un projet peut réunir, à côté de l’édition, d’autres documents XML : fichier d’autorités (personnes, lieux), notes, etc. Utilisez Fichier → Documents XML / XSLT du projet…. Ajouter un document XML, XSLT ou Schematron… déclare un fichier existant ; un fichier situé hors du dossier du projet y est copié, dans xml/, sans jamais remplacer un fichier existant. Nouveau document XML… crée un document vide dont vous choisissez l’élément racine. Retirer le document du projet retire le document affiché, sans supprimer son fichier.

Dès qu’un document auxiliaire existe, une rangée d’onglets apparaît au-dessus de la source XML : Édition, puis un onglet par document. Chaque document conserve son historique d’annulation, sa position et son état ; un astérisque signale des modifications non enregistrées, et la couleur du nom un XML mal formé ou invalide. La validation RELAX NG et la complétion suivent le <?xml-model?> du document affiché. Les manuscrits, la vue XSLT / CSS et les commandes des témoins ne concernent que l’édition : ils sont masqués pendant l’affichage d’un autre document, puis retrouvés tels quels. Ctrl+S enregistre le document affiché ; avant de quitter ou de changer de projet, Varians propose d’enregistrer tous les documents modifiés. L’export web n’utilise que l’édition.

Onglets affichés. Affichage → Choisir les documents affichés… permet de choisir les documents qui ont un onglet, et l’ordre des onglets. Le clic droit sur un onglet propose Masquer l’onglet, Renommer l’onglet…, Choisir les documents affichés… et Retirer le document du projet, pour le document de cet onglet, même s’il n’est pas affiché. Un document masqué reste dans le projet : ses modifications sont conservées et Varians propose de les enregistrer avant de quitter. Son onglet réapparaît quand une référence y mène (F12, Ctrl+clic, double-clic dans le panneau Références). Le dernier onglet visible ne peut pas être masqué ; à l’ouverture du projet, l’édition est affichée, avec son onglet. Ces choix sont enregistrés localement pour le projet, sans modifier project.xml. En revanche, le nom donné par Renommer l’onglet… est écrit dans l’attribut label du <document>, dans project.xml ; un nom vide rétablit le nom du fichier. Quand les onglets ne tiennent plus dans leur rangée, une flèche ▾ (« Tous les onglets ») s’affiche à sa droite : elle déroule la liste de tous les onglets, celui du document affiché coché ; un clic affiche le document choisi. La liste se termine par Choisir les documents affichés….

Les documents sont déclarés dans project.xml par un élément <documents>.

Enregistrer

Fichier → Enregistrer l’édition (Ctrl+S) enregistre le document affiché : l’édition, une de ses parties ou un autre document du projet. Enregistrer l’édition sous… (Ctrl+Maj+S) l’écrit ailleurs. Avant de quitter ou de changer de projet, Varians propose d’enregistrer chaque document modifié. Un document mal formé ou non valide peut être enregistré, après confirmation.

Les écritures importantes se font par remplacement atomique et gardent une copie .bak. Quand une opération automatique serait ambiguë, Varians s’abstient plutôt que de réécrire la TEI en silence.

5. Éditer le XML

L’éditeur

L’onglet XML source (Ctrl+1) montre le document affiché ; l’onglet Vue XSLT / CSS (Ctrl+2), l’édition mise en forme (voir Vue XSLT / CSS et éditeur de fragment). Le Retour automatique à la ligne est purement visuel : il ne change ni le XML ni la numérotation des lignes.

Paires de balises. Le curseur placé dans une balise ouvrante ou fermante colore en bleu pâle les deux balises de la paire, de <app> comme de </app>, en respectant l’imbrication, les préfixes (tei:div) et les éléments vides ; commentaires, CDATA et instructions de traitement n’en forment pas. Renommer une balise ouvrante renomme sa balise fermante ; supprimer toute la balise ouvrante retire la fermante en gardant le contenu. Un balisage croisé ou incertain ne donne aucune paire.

Balises fermantes. Dans l’éditeur XML comme dans l’éditeur de fragment, taper </ propose la fermeture de l’élément ouvert le plus proche : après <div><p>…</p></, Varians propose div> ; Entrée ou Tab l’insère. On peut aussi commencer le nom, par exemple </di. Échap ferme la liste, Ctrl+Espace la rouvre. Les éléments vides (<lb/>), les commentaires, les CDATA et les attributs inachevés sont ignorés ; si l’imbrication est ambiguë, aucune fermeture n’est inventée.

Repliage. Affichage → Repliage XML : Replier / déplier l’élément (Ctrl+Alt+F), Replier les éléments structurels, Tout déplier (Ctrl+Alt+Maj+F) ; les chevrons ▾ / ▸ de la marge replient ou déplient un élément. Seuls les éléments répartis sur plusieurs lignes, dont les balises sont sur leurs propres lignes, se replient. Le repliage ne change ni le XML ni l’historique d’annulation ; une modification du texte déplie tout, et le curseur amené sur une ligne cachée la rend visible.

Indenter. Éditer → Indenter le XML indente les zones structurelles du document, avec prudence :

  • aucun blanc n’est ajouté autour d’un <lb/> ;
  • xml:space="preserve" est respecté ;
  • les contenus mixtes ou ambigus ne sont pas touchés ;
  • un élément qui, d’après le schéma, accepte du texte est traité comme du texte.

custom-elements.xml peut préciser formatting="inline", formatting="block" ou formatting="preserve" ; les protections ci-dessus restent prioritaires.

Aide au balisage

Ctrl+E entoure la sélection avec un élément ou insère un nouvel élément au curseur. Dans la liste, une entrée n’est surlignée que si vous la choisissez (clic, flèches, ou Tab / ↓ depuis le champ, qui sélectionnent la première) : Entrée insère l’entrée surlignée, sinon le texte saisi dans le champ ; retaper dans le champ efface le choix. Les éléments que le schéma RELAX NG permet à cet endroit sont proposés en premier.

Ctrl+Espace complète les noms d’éléments et d’attributs, et certaines valeurs d’attributs, y compris un nom d’élément tapé juste devant une autre balise (<h devant </p>). Les propositions viennent du schéma RELAX NG, du fichier custom-elements.xml, ou des deux, et leur provenance est indiquée. Dans une balise ouvrante, le début d’un attribut permis ouvre de lui-même la liste filtrée ; Entrée ou Tab insère l’attribut et ses guillemets.

Dans un attribut pointeur comme @wit, taper # ouvre la liste des témoins ou des identifiants du projet (voir Références entre documents) ; Varians complète une liste de valeurs séparées par des espaces sans reproposer celles qui y sont déjà.

Configuration de Ctrl+E. Fichier → Configuration Ctrl+E… ouvre le fichier custom-elements.xml du projet : éléments proposés par Ctrl+E, attributs et valeurs proposés par Ctrl+Espace (une source witnesses donne les témoins du projet sous la forme #A1, #B1…), règles d’indentation. Ce fichier aide à la saisie ; il ne change jamais la validité du document. Son format est décrit dans CUSTOM_ELEMENTS.md.

Dictionnaire. Ctrl+? (ou Aide → Dictionnaire de Latin) cherche le texte sélectionné dans le dictionnaire latin Vocabula, dans le navigateur.

Références entre documents

Un attribut pointeur (@ref, @corresp, @target, @who, @wit, @edRef, @sameAs, @ana, @resp, @source, @hand, @facs, @prev, @next, @synch, @copyOf) désigne un élément par son @xml:id. Comme en TEI standard, et donc pour tous les outils XML, la forme courte #bernard désigne un élément du document lui-même. Pour viser un autre document du projet (voir Documents XML auxiliaires), on écrit personnes.xml#bernard, avec un chemin relatif au document qui contient la référence. Les adresses web (https://…) et les valeurs sans « # » ne sont pas traitées. Une valeur peut contenir plusieurs pointeurs séparés par des espaces : wit="#T1 #T2".

Saisie. Dans la valeur d’un tel attribut, tapez # : la liste des identifiants s’ouvre d’elle-même, avec le texte de chaque entrée et son fichier, par exemple « personnes.xml#bernard — Bernardus ». Les lettres suivantes filtrent la liste ; Entrée ou Tab insère la valeur ; Échap ferme la liste. Pour @wit et @edRef, la liste propose les témoins décrits dans la TEI (<witness> du <listWit>). Ctrl+Espace ouvre les mêmes valeurs dans une boîte (« Identifiants du projet ») où le filtre porte aussi sur les descriptions : « Bern » trouve personnes.xml#bernard. Les identifiants proposés dépendent de l’élément : persName/@ref propose les person, personGrp et persona ; placeName/@ref les place ; orgName/@ref les org ; @who les personnes. Ailleurs, tous les identifiants sont proposés. Dans custom-elements.xml, <values source="ids" elements="person personGrp" prefix="#"/> fixe cette liste pour un attribut. Un identifiant d’un autre document est inséré sous la forme fichier.xml#id, un identifiant du document lui-même sous la forme #id.

Navigation. Sur une référence, appuyez sur F12, faites Ctrl+clic ou choisissez Aller à la cible dans le menu du clic droit : le document qui contient la cible est affiché, l’élément sélectionné. Si l’identifiant est défini plusieurs fois, Varians demande quelle cible afficher. Alt+← (ou Revenir dans le menu du clic droit) ramène au point de départ, même depuis un autre document. Une cible introuvable est signalée dans la barre d’état. Sur une forme courte dont la cible n’est que dans un autre document, Varians y mène aussi et indique la forme à écrire.

Vérification. La commande Éditer → Références vérifie les références de tous les documents du projet. Le panneau qui s’ouvre sous la source indique leur nombre et liste celles qui posent un problème : cible introuvable, forme courte dont la cible est dans un autre document (avec la forme à écrire), cible ambiguë (identifiant défini plusieurs fois dans le document visé) ou fichier introuvable, avec les colonnes Document, Ligne, Attribut, Valeur et Problème. Un double-clic mène à la référence. Après une correction, Vérifier à nouveau relance la vérification. Cette vérification est une aide : elle n’empêche jamais d’enregistrer et ne modifie aucun fichier.

Rechercher et remplacer

Le menu Rechercher réunit les recherches dans le XML et dans le fragment ; la recherche XPath a sa propre section.

  • Recherche simple (Ctrl+F) : le champ de la barre d’outils pour le XML, la barre de recherche du fragment quand le focus est dans le fragment ; F3 et Maj+F3 passent à l’occurrence suivante ou précédente.
  • Tout lister (Rechercher → Lister toutes les occurrences, Ctrl+Maj+L), bouton à côté du champ de recherche : un panneau sous l’éditeur liste toutes les occurrences de la recherche du XML, avec les mêmes options (casse, expressions régulières). Chaque ligne donne le numéro de ligne et l’occurrence dans son contexte, surlignée et centrée entre le texte qui la précède et celui qui la suit (présentation KWIC). Un clic mène à l’occurrence. Case Tout le projet cochée, la liste couvre tous les documents du projet, avec une colonne Document ; un clic sur une occurrence d’un autre document affiche ce document. Le panneau ouvert suit les nouvelles recherches, les options, les modifications du texte et le document affiché ; au-delà de 2 000 occurrences, seules les premières sont listées. × le ferme.
  • Respecter la casse et Expressions régulières : deux options à cocher du menu Rechercher, reprises par les boutons Aa et .* près des champs de recherche. Elles valent pour le XML et le fragment (la recherche de la Vue XSLT / CSS reste littérale) et sont retenues d’une session à l’autre. Les expressions régulières sont celles de Python (module re) : ^ et $ valent pour chaque ligne, \b marque une limite de mot ; une expression incorrecte est signalée dans la barre d’état.
  • Chercher et remplacer (Ctrl+H) ouvre une barre sous l’éditeur XML ou, le focus dans le fragment, la ligne Remplacer par sous sa recherche. Remplacer change l’occurrence surlignée puis passe à la suivante ; Tout remplacer change tout le document (ou tout le fragment) et s’annule d’un seul Ctrl+Z. Le texte cherché est pris tel quel, espaces compris. On remplace ce qu’on a trouvé, rien de plus : remplacer une balise ouvrante ne renomme ni ne supprime sa balise fermante. Échap ferme la barre.
  • Avec une expression régulière, le texte de remplacement reprend les groupes entre parenthèses : \1, \2…, ou \g<nom> pour un groupe nommé (?P<nom>…) ; \n passe à la ligne. Exemples : wit="#(\w+)" remplacé par wit="#\1 #T3" ajoute T3 à chaque leçon d’un seul témoin ; <(rdg|lem)\b trouve les deux éléments ; <lb n="\d+"/> trouve les sauts de ligne numérotés.
  • Recherche XPath (Ctrl+Maj+F) : voir Recherche XPath. Le bouton XPath de la barre d’outils l’ouvre aussi.
  • Recherche dans l’aide : dans cette fenêtre d’aide, le champ du haut (Ctrl+F) cherche dans toute l’aide, sans tenir compte des accents ni de la casse ; plusieurs mots : les sections qui les contiennent tous, dans n’importe quel ordre ; entre guillemets, l’expression exacte ("tout remplacer"). À gauche, la liste des sections trouvées, avec un extrait ; un clic mène à la section. Les occurrences sont surlignées ; Entrée, F3 et Maj+F3, ou ◀ ▶, les parcourent.

Recherche XPath

Rechercher → Recherche XPath (bouton XPath, Ctrl+Shift+F) ouvre un panneau sous l’éditeur : une expression XPath 1.0 y cherche dans le document affiché, par exemple //note pour les éléments <note>. 6. Valider

Varians vérifie le document affiché contre son schéma RELAX NG et ses règles Schematron. Une feuille XSLT ou un fichier de règles Schematron sont eux aussi vérifiés quand ils sont affichés : voir Éditer une feuille XSLT et Règles Schematron.

Validation RELAX NG

Le schéma d’un document est celui que déclare son <?xml-model?>, ou celui que fixe Fichier → Paramètres du projet… (qui peut aussi désactiver la validation). Varians valide le document à l’ouverture, à l’enregistrement et à la demande : Valider RNG (F8). Les erreurs sont listées dans le panneau Validation RELAX NG et Schematron, sous l’éditeur, avec leur niveau, leur ligne et leur colonne ; un double-clic mène à l’erreur. Une fois ce panneau employé, la validation se refait d’elle-même après une courte pause de frappe, et une erreur corrigée disparaît de la liste. La barre d’état résume le résultat ; le nom de l’onglet d’un document mal formé se colore en rouge, celui d’un document non valide en orange.

Un schéma distant (adresse http) est téléchargé à sa première utilisation, puis gardé dans le cache des schémas ; le bouton Actualiser le schéma distant puis revalider du panneau le télécharge de nouveau.

Sans figer la fenêtre. La validation se fait dans un processus séparé, que Varians lance au premier besoin. La première compilation d’un gros schéma comme TEI_ALL prend une dizaine de secondes ; pendant ce temps, la fenêtre reste utilisable et une petite lueur tourne à côté de l’état RNG : validation en cours… dans la barre d’état. Le schéma compilé est ensuite gardé pour toute la session, même si l’on ouvre un autre projet. La validation automatique n’interrompt jamais le travail ; Valider RNG (F8) et l’enregistrement attendent en revanche le résultat : la fenêtre reste affichée, mais les clics et les frappes sont ignorés jusqu’à la réponse. Si le processus de validation ne peut pas être lancé, Varians valide lui-même et l’indique dans la barre d’état ; la fenêtre peut alors se figer pendant la compilation.

Règles Schematron

Un schéma RELAX NG dit quels éléments et attributs sont permis, et où. Des règles Schematron vérifient ce qu’il ne peut pas exprimer : par exemple, dans la TEI, qu’un <lg> contient au moins un vers, ou que @target et @cRef ne sont pas employés ensemble. Varians les applique en même temps que le RNG : à l’ouverture, pendant la frappe, avec Valider RNG (F8) et à l’enregistrement, dans le même processus séparé (voir Validation RELAX NG).

Quelles règles. D’abord celles qui sont intégrées au schéma RELAX NG employé, qu’il soit déclaré par le document ou choisi dans les paramètres du projet : tei_all.rng en contient 91 groupes, une personnalisation ODD les siennes. Ensuite celles de chaque déclaration Schematron du document, vers un fichier .sch ou un RNG :

<?xml-model href="regles.sch" type="application/xml"
    schematypens="http://purl.oclc.org/dsdl/schematron"?>

Une adresse relative part du document ; une adresse http est téléchargée une fois, puis gardée dans le cache des schémas. Les mêmes règles ne sont jamais vérifiées deux fois : la déclaration Schematron des documents TEI désigne le même tei_all.rng que leur RNG. Les nouveaux projets reçoivent les deux déclarations. Pour une édition en parties, les règles portent sur l’édition assemblée, comme le RNG.

Schéma XSD. Un schéma XSD déclaré comme Schematron (même schematypens) donne les règles qu’il intègre dans ses xs:appinfo, y compris celles des fichiers qu’il inclut ou importe (xs:include, xs:import). Varians ne valide pas le document contre le XSD lui-même.

Phases. Un fichier Schematron peut réunir ses groupes de règles (sch:pattern) en phases (sch:phase). Sans autre indication, Varians vérifie la phase par défaut du fichier (defaultPhase), sinon toutes ses règles. Pour choisir une phase, ajoutez à la déclaration l’attribut standard phase, comme dans Oxygen :

<?xml-model href="regles.sch" type="application/xml"
    schematypens="http://purl.oclc.org/dsdl/schematron" phase="lecons"?>

#ALL vérifie toutes les règles, #DEFAULT la phase par défaut. Une phase qui n’existe pas dans le fichier est une règle incorrecte (voir plus bas), donnée avec la liste des phases du fichier. Sans écrire la déclaration vous-même : un clic sur l’étiquette Schematron de la barre d’état, ou le bouton Règles… du panneau de validation, ouvre la boîte Règles Schematron du document. Pour chaque fichier de règles déclaré, elle propose la phase dans une liste (la phase par défaut, toutes les règles, les phases du fichier) ; elle ajoute ou retire aussi une déclaration. Les changements sont écrits dans les <?xml-model?> du document, et Ctrl+Z les défait.

Messages. Ils s’ajoutent à ceux du RNG dans le panneau Validation RELAX NG et Schematron : la colonne Origine indique Schematron, et le double-clic mène à la ligne de l’élément concerné (pour une règle sur un attribut, celle de son élément), dans son document. Le niveau vient de @severity, sinon de @role : warning, warn ou nonfatal donnent un Avertissement, info une Information, tout le reste une erreur. Une erreur rend le document invalide, comme une erreur RELAX NG : nom de l’onglet en orange, et question Document non valide avant d’enregistrer (Enregistrer quand même). Un avertissement ou une information restent dans la liste, sans rendre le document invalide.

Barre d’état. À côté de l’état RNG, l’étiquette Schematron résume le résultat : Schematron : ✓, le nombre d’erreurs ou de messages, ou Schematron : non vérifié quand la validation est désactivée pour le projet. Son info-bulle nomme les fichiers des règles appliquées, avec leur phase : « apparat.sch (phase lecons) ». Un clic sur l’étiquette ouvre la boîte Règles Schematron du document.

Règles incorrectes. Une expression XPath fautive, une phase inconnue, ou un fichier de règles introuvable ou mal formé, donnent Schematron : règles incorrectes. Chaque règle incorrecte a sa ligne dans le panneau, après les messages du document : origine Schematron (règles) et, dans la colonne Document, le fichier des règles. Le double-clic affiche ce fichier à la ligne de la règle ; un fichier du dossier du projet qui n’est pas encore un document du projet peut y être ajouté (Varians le propose) ; un fichier hors du projet, comme la copie d’un fichier distant dans le cache, ne s’ouvre pas, et la barre d’état le dit. C’est le schéma qui est en faute : le document n’en devient pas invalide, et les autres règles sont appliquées. Quand un fichier de règles a été modifié et enregistré, le document est validé de nouveau dès qu’on revient à lui.

Écrire les règles dans Varians. Fichier → Documents XML / XSLT du projet… → Ajouter un document XML, XSLT ou Schematron… accepte les fichiers .sch ; un fichier situé hors du projet est copié dans son dossier xml/. Nouveau fichier Schematron… crée un fichier minimal (xml/regles.sch est proposé), qui déclare le préfixe tei et contient une règle d’exemple ; ajoutez ensuite sa déclaration au document. Un fichier Schematron affiché est vérifié à la place de la validation RELAX NG : Vérifier les règles Schematron (F8), à l’affichage, pendant la frappe une fois F8 employé, et à l’enregistrement. La vérification porte sur le texte affiché, même non enregistré : bonne formation, structure d’après le schéma ISO Schematron (livré avec Varians), fichiers inclus, puis compilation par Saxon de toutes les phases ; chaque erreur est donnée à sa ligne, et le double-clic y mène. Ctrl+Espace et la liste automatique des attributs proposent les éléments et attributs Schematron, avec le préfixe du fichier, et des valeurs courantes pour severity, role et queryBinding. Le document est validé avec le texte affiché d’un fichier de règles ouvert, même non enregistré : revenir au document après avoir modifié ses règles le fait valider de nouveau, et l’info-bulle de l’étiquette Schematron le signale (« regles.sch, non enregistré »). Il en va de même pour un fichier qu’il inclut (sch:include, sch:extends), ouvert et modifié : l’info-bulle le nomme (« regles.sch (non enregistré : motifs.sch) »), et la vérification du fichier de règles en tient compte, de nouveau quand on revient à ce fichier. Les nouveautés des éditions 2020 et 2025 de la norme, que SchXslt2 applique, sont acceptées et proposées par la complétion : sch:group, sch:rules, sch:library, sch:param au niveau du schéma, @visit-each, @from et @when des phases.

Moteur. Varians emploie SchXslt2 (David Maus, licence MIT), livré avec lui, et Saxon (paquet saxonche, installé par installer_dependances.bat, comme pour les scénarios de transformation). Sans Saxon, l’étiquette indique Schematron : Saxon manquant et seule la validation RELAX NG est faite. Les règles sont préparées en moins d’une seconde à leur première vérification, puis gardées pour la session, et préparées de nouveau si leur fichier change.

Limites. Les règles sont évaluées en XPath 3.1, quel que soit leur queryBinding : une règle écrite pour XPath 1.0 se comporte presque toujours de même. Pour les éditions 2020 et 2025, dont le schéma n’est pas en accès libre, la vérification d’un fichier .sch suit ce qu’accepte SchXslt2. L’ancien Schematron 1.5 n’est pas pris en charge, ni la validation par un XSD.

7. Vue XSLT / CSS et éditeur de fragment

L’aperçu

L’onglet Vue XSLT / CSS montre l’édition mise en forme par une feuille XSLT et une CSS : celles de Varians, ou celles du projet (Fichier → Paramètres du projet…, Source de la XSLT : XSLT par défaut de l’éditeur, qui suit les corrections de Varians, ou XSLT personnalisée, un fichier du projet) ; la ligne Mise en forme de la vue permet d’essayer une autre feuille XSLT ou CSS. L’aperçu se met à jour quand on y revient après une modification ; Aperçu auto le met à jour à chaque pause de la frappe, Actualiser à la demande ; Taille agrandit ou réduit le texte. Un sommaire donne accès aux divisions titrées ; le champ Rechercher dans l’aperçu y cherche un mot ou une expression.

Un clic sur le texte de l’aperçu place le curseur de la source au même endroit et fait suivre les témoins. Une chaîne sélectionnée dans l’aperçu est sélectionnée dans la source quand on revient à l’onglet XML source, à la même occurrence du même passage (même un mot coupé par un <lb break="no"/>) ; inversement, la sélection de la source, par exemple un résultat XPath, est retrouvée dans l’aperçu. Revenir à la source sans avoir changé la sélection de l’aperçu rend la sélection de départ.

Une transformation peut lire des fichiers locaux (un fichier d’autorités, par exemple), mais ni écrire de fichier ni accéder au réseau. Une erreur de la feuille est signalée telle quelle, avec son fichier et sa ligne.

L’éditeur de fragment

Le crayon ✎ placé au début d’un bloc de l’aperçu ouvre ce bloc, tel qu’il est écrit dans le XML, dans l’éditeur de fragment, sous l’aperçu. On le corrige comme dans la source (complétion, Ctrl+E, recherche et remplacement), puis Appliquer au XML l’écrit dans le document, à sa place ; Appliquer et continuer l’écrit sans fermer l’éditeur ; Recharger le fragment reprend le texte du document. Le fragment doit rester bien formé. Avant de quitter, Varians propose d’appliquer un fragment modifié.

Sélections partagées avec l’éditeur de fragment. Le crayon ✎ placé au début d’un élément de l’aperçu (paragraphe, strophe, titre… : voir Éléments modifiables) ouvre cet élément dans l’éditeur de fragment, sans déplacer les images des témoins ; un clic sur le texte de l’aperçu les synchronise toujours. Quand l’éditeur est ouvert, une chaîne sélectionnée dans cet élément de l’aperçu (en glissant la souris ou par un double-clic) est aussi sélectionnée dans l’éditeur de fragment, qui prend le focus : le passage à corriger est trouvé tout de suite. Inversement, une sélection faite dans l’éditeur de fragment est sélectionnée dans l’aperçu, qui défile jusqu’à elle ; le focus reste dans l’éditeur. La même occurrence d’un mot répété est retrouvée, y compris un mot coupé par un <lb break="no"/>. Une sélection dans un autre élément ne change pas l’éditeur de fragment : ouvrez cet élément par son crayon. Un texte tapé dans le fragment n’apparaît dans l’aperçu qu’après Appliquer au XML. Le clic sur le crayon garde la sélection en cours de l’aperçu : si elle est dans cet élément, elle est aussi sélectionnée dans l’éditeur de fragment. Dans l’aperçu, F2 ouvre dans l’éditeur de fragment l’élément de la sélection (ou du curseur), avec la sélection. Un élément déjà ouvert dont les corrections ne sont pas appliquées n’est pas rechargé.

Éléments modifiables. Le crayon ✎ ouvre chaque bloc posé dans une division du <body> : tout élément des classes TEI model.divPart (<p>, <ab>, <lg>, <l>, <sp>…) et model.inter (<list>, <table>, <quote>, <cit>, <stage>…), ainsi que <head>, <figure> et <note>. Un élément contenu dans un autre élément de cet ensemble n’a pas son propre crayon : il s’ouvre avec lui. Un <lg> a donc son crayon, ses <l> non ; un <p> a le sien, la <quote> ou la <note> qu’il contient non ; une réplique (<sp>) a le sien, posé sur son locuteur ; une <note> placée entre deux paragraphes a le sien. Les classes sont lues dans le schéma RELAX NG du projet, tel que la validation l’a trouvé : un élément ajouté à ces classes par une personnalisation ODD est modifiable. Sans schéma, ou si le schéma ne définit pas ces classes, Varians prend la liste de TEI P5 4.10.2. Les crayons sont placés par Varians, quelle que soit la feuille XSLT de la vue : elle n’a rien à prévoir pour eux, et un élément qu’elle n’affiche pas n’a pas de crayon. L’étiquette de l’éditeur nomme l’élément ouvert, par exemple « Fragment TEI · <lg> 3/40 ».

La feuille de Varians

La feuille livrée avec Varians (tei-to-html.xsl, celle aussi du scénario Édition HTML (feuille de Varians)) rend :

  • la structure : une division est titrée par son premier <head>, sinon par son @n (jamais par son @xml:id), et le sommaire liste les divisions titrées, par niveaux ; chaque strophe (<lg>) est un bloc en retrait, chaque vers (<l>) sur sa ligne ; une liste est numérotée si elle porte @rend="numbered" ou @type="ordered" (ou numbered), et son titre la précède ; un <table> est un tableau, avec sa légende, ses en-têtes (@role="label") et ses cellules fusionnées (@cols, @rows) ; une figure est un bloc, avec sa légende ;
  • le théâtre : chaque réplique (<sp>) est un bloc, son locuteur (<speaker>) en tête, en petites capitales ; une didascalie (<stage>) est entre parenthèses, en italique : un bloc en retrait entre deux répliques ou deux paragraphes, une ligne dans une strophe, et dans la phrase quand elle est dans un paragraphe ;
  • les phénomènes éditoriaux, comme « Édition critique (HTML) » : un <choice> montre une forme (<corr>, <reg>, <expan>, sinon <sic>, <orig>, <abbr>), les autres en infobulle ; <sic> est signalé ; <del> et <surplus> sont barrés, <add> souligné ; <supplied> est entre crochets ; <gap> donne « [lacune] » ; <hi> rend le gras, le souligné, l’exposant, l’indice et les petites capitales ; <emph>, <title> et <foreign> sont en italique ;
  • les citations : le <ref> d’une <cit> suit la citation, entre chevrons et en gris.

La CSS du projet (rendering/tei.css) règle l’apparence ; Varians donne d’office le retrait des strophes et l’allure des répliques, que la CSS du projet peut remplacer. L’aperçu (Qt) comprend un sous-ensemble de CSS : une règle placée après un @media y est ignorée.

8. Témoins et fac-similés

Chaque témoin du projet a son panneau, à côté de l’éditeur. Ses ressources se déclarent dans Fichier → Paramètres du projet…, sous Témoins et ressources (Ajouter…, Modifier…) : les images, les lignes (ALTO ou PAGE XML), le fichier d’alignement. Toutes sont facultatives et s’ajoutent dans n’importe quel ordre.

Images

La Source des images d’un témoin est l’une de trois :

  • Aucune image pour le moment ;
  • Images locales (JPEG, PNG, TIFF, BMP, WebP) : Ajouter des images… ; Copier les images dans le projet rend le projet portable. Chaque image reçoit un libellé de folio ou de page (Folio / page) et l’identifiant de sa surface TEI (Surface TEI). Les fichiers ajoutés sont triés dans l’ordre naturel (img_1r, img_1v, img_2r…) ; Trier naturellement trie une liste existante, et ↑ / ↓ déplacent une image ;
  • Manifest IIIF (IIIF Presentation 2 ou 3) : collez l’adresse du manifeste, puis Charger / actualiser.

Varians complète le <facsimile> de l’édition d’une <surface> par image retenue, sans jamais reconstruire un <facsimile> existant : les surfaces, les zones et ce qu’on y a ajouté sont gardés, et une surface devenue inutile n’est jamais supprimée sans vous.

<facsimile>
  <surface xml:id="A1-p0002" n="1v">
    <graphic url="../images/A1/002.jpg"/>
  </surface>
</facsimile>

Images IIIF retenues pour l’édition

Un manifeste compte souvent bien plus de pages que l’édition n’en emploie. Choisissez Uniquement les images choisies pour l’édition, puis Choisir les images et associer les OCR… : filtrez les folios, cochez les pages utiles ; l’aperçu ouvre une page dans le navigateur. Seules les pages cochées forment le corpus d’images du témoin et reçoivent une surface TEI, dont l’identifiant garde la position de la page dans le manifeste.

La même boîte associe chaque page à ses lignes et à sa page synchronisée :

  • OCR (ALTO ou PAGE XML). Varians associe d’office une page IIIF et un fichier dont le nom d’image (sans extension) est le même, y compris le nom d’image déclaré dans le fichier ; une correspondance ambiguë n’est pas appliquée. Associer automatiquement (noms exacts) complète les cases vides ; la dernière colonne permet de choisir le fichier de chaque page, même quand les noms diffèrent tout à fait. Un fichier ne correspond qu’à une page.
  • Page synchronisée. Pour un témoin synchronisé par lignes, Varians retrouve la page du fichier d’alignement qui correspond à chaque page IIIF par l’identifiant du Canvas, le service d’images, l’adresse de l’image, une association OCR sûre ou un libellé de folio sans ambiguïté. Sinon, la colonne Page synchronisée permet de la choisir ; ce choix est gardé dans project.xml.
  • Les colonnes Copie locale et État de l'association disent si une copie de la page est présente, d’où vient l’association et quelle source sera affichée.

La place d’une page dans une liste ne sert jamais à l’identifier : sans preuve, Varians n’associe rien.

Copies locales des images IIIF

Utiliser une copie de travail locale des images IIIF dans Varians télécharge les pages, au choix (Pages à télécharger :) Tout le corpus d’images retenu ou Uniquement les pages associées à un ALTO ou PAGE. Le téléchargement commence après l’enregistrement des paramètres, dans une fenêtre à part, sans bloquer l’édition ; Fichier → Gestionnaire de téléchargements IIIF… la rouvre à tout moment. Elle donne le nombre de pages du manifeste, retenues, présentes, manquantes et exclues ; Télécharger les manquantes reprend sans retélécharger les pages reçues, Actualiser la sélection retélécharge tout ; Pause, Reprendre et Arrêter agissent entre deux images. Fermer la fenêtre la masque sans arrêter le travail. Les copies sont rangées dans iiif/local/<témoin>/ ; une page non copiée reste lue sur le serveur.

Utiliser la copie locale lors de la génération du viewer web est un choix à part : coché, le viewer web emporte les copies présentes et fonctionne hors ligne pour ces pages ; décoché, il lit les images sur les serveurs d’origine. Vérifiez les droits de reproduction des établissements avant de diffuser des images.

Quand le serveur offre un service d’images IIIF, Varians affiche l’image en pleine résolution, et se replie sur l’image d’aperçu du manifeste en cas d’échec. Le pourcentage du zoom est relatif au cadrage automatique, non à la résolution du fichier.

Lignes : ALTO et PAGE XML

Les lignes d’un témoin (leur place sur l’image et leur texte) viennent d’un fichier ALTO ou PAGE XML par page, produit par un logiciel de reconnaissance. Dans la boîte du témoin, la section Transcription géométrique (ALTO / PAGE) propose, pour la Source ALTO / PAGE, Automatique / données du fichier de synchronisation ou Fichiers ALTO ou PAGE indépendants : Ajouter des fichiers ALTO / PAGE…, dans l’ordre des folios, et Copier les fichiers ALTO / PAGE dans le projet. Chaque fichier est reconnu séparément : un témoin peut mêler les deux formats. Une ligne ALTO est d’ordinaire un rectangle ; une ligne PAGE garde son polygone (Coords/@points) et sa ligne de base (Baseline/@points) ; son texte vient de son TextEquiv/Unicode, ou de ses mots.

Ajouter des lignes à un témoin IIIF ne change pas ses images. Une page OCR n’est associée à une image que si l’association est prouvée ; les autres sont comptées dans l’infobulle du témoin.

Des lignes ne sont pas une synchronisation. Tant qu’aucun alignement ne relie les lignes du manuscrit à celles du pivot, le témoin est suivi par pages et le panneau montre la page entière ; les cadres des lignes peuvent être affichés, mais aucune n’est désignée.

Synchronisation par lignes

Le fichier d’alignement d’un témoin (Synchronisation JSON (facultative), et Copier la synchronisation dans le projet) est produit par Varians-Synchro. Celui du pivot décrit ses lignes physiques, page par page ; celui de chaque autre témoin relie ses lignes à celles du pivot (base_keys). Le format est décrit dans ALIGNMENT_FORMAT.md.

Dans la TEI, le premier <lb edRef="#A"/> du pivot A correspond à la première ligne de son fichier d’alignement, le suivant à la suivante, et ainsi de suite ; les <pb> repèrent les pages sans renuméroter les lignes. La barre d’état compte les lignes du pivot (par exemple « A : 3599 lignes ✓ ») et signale un nombre différent de celui de l’alignement ; l’enregistrement le rappelle. Une modification à l’intérieur d’une balise, comme edRef="#T" complété en edRef="#T1", est aussitôt prise en compte.

Un témoin n’est suivi par lignes que si son alignement est exploitable : de vraies lignes pour le pivot, de vrais liens vers le pivot pour les autres. Un fichier vide ou provisoire, sans lien vers le pivot, ou dont les liens ne désignent aucune ligne du pivot laisse le témoin suivi par pages, et Varians le signale.

Après avoir réexporté des alignements, Affichage → Actualiser les synchronisations… (Ctrl+Maj+R) les relit sans rouvrir le projet : les fichiers sont vérifiés, la liste des changements est soumise à confirmation, et un fichier incorrect ne remplace jamais ce qui est chargé. La transcription et son historique d’annulation ne changent pas ; les panneaux gardent, autant que possible, leur page, leur zoom et leurs cadres.

Le panneau d’un témoin

L’en-tête du panneau nomme le témoin et la position affichée (page et ligne). Ses commandes :

  • ← → passent à la ligne (ou à la page) précédente ou suivante du manuscrit ; ⤺ revient à la correspondance du passage de l’édition ; le bouton au livre ouvert décide si ces flèches mènent l’édition (voir Suivre un manuscrit dans son propre ordre) ;
  • − et + règlent le zoom, le bouton qui les sépare le remet à 100 % ; la molette zoome aussi, et un double-clic sur l’image revient à 100 % ;
  • Cadres montre les contours des lignes de ce témoin : en orange les lignes synchronisées, en bleu la ligne consultée ; les polygones PAGE sont tracés tels quels ; sans géométrie, un message le dit ;
  • Page ↗ ouvre l’image entière de la page dans l’application ou le navigateur par défaut ;
  • Marquer la page et Double page…, puis la liste Folios :, pour un témoin suivi par pages ;
  • ↗ détache le panneau dans sa propre fenêtre (voir Disposition des panneaux).

Dans un panneau étroit, Cadres, Page ↗, Marquer la page et Double page… se réduisent à ▣, □, pb et ↔ ; leur infobulle les nomme.

Le cadrage d’une ligne montre ses voisines, mais pas celles d’une autre colonne ou d’une autre page. Si une ligne du pivot correspond à plusieurs lignes d’un témoin, le panneau se centre sur une ligne réellement reliée.

Marquer la page insère au curseur le début de la page affichée :

<pb n="1v" edRef="#A1" facs="#A1-p0002"/>

@n reprend le libellé du folio, @edRef le témoin, @facs la surface (ou la zone) TEI. Le curseur doit être dans le texte ou entre deux balises, non dans une balise. Un témoin suivi par pages montre la page de son dernier <pb> avant le curseur : son @facs désigne la page ; à défaut, un @n qui ne désigne qu’une page du témoin. Deux témoins peuvent avoir le même numéro de folio : le @edRef les distingue.

Double page… décrit une image qui montre deux folios ou deux pages : la boîte montre une vignette de l’image, avec une barre rouge à placer à la séparation, et demande le libellé de la Partie gauche : et de la Partie droite :. Varians écrit deux <zone> dans la surface de l’image, sans toucher à l’image. Marquer la page vise ensuite la partie qui contient la ligne affichée, ou demande laquelle choisir ; la liste Folios : et les flèches passent d’une partie à l’autre ; Image entière montre l’image complète. Annuler la boîte n’ajoute rien.

Suivre un manuscrit dans son propre ordre

Les flèches ← et → de chaque panneau de témoin mènent l’édition : le témoin avance ou recule dans son propre ordre, et le curseur de l’édition va au passage correspondant, en affichant au besoin la partie ou le texte qui le contient. Les autres témoins suivent le pivot, comme lorsque le curseur bouge. Quand un document auxiliaire est affiché, les flèches feuillettent seulement le témoin.

Témoin synchronisé par lignes. Le panneau passe à la ligne suivante du témoin ; l’édition va à la ligne du pivot que cette ligne désigne. Une ligne non reliée au pivot laisse l’édition sur la ligne reliée qui la précède, et la barre d’état le dit. Le bouton ⤺ ramène le panneau sur la ligne reliée à celle du pivot.

Témoin suivi par pages. Les flèches et la liste des folios mènent l’édition à la page choisie : à la première ligne du témoin sur cette page dans un de ses JSON, sinon à la fin de son <pb edRef="#M" n="45v"/>, sinon au début du texte dont le <locus from> du témoin est cette page. Sans aucun de ces repères, l’édition ne bouge pas et la barre d’état le dit.

D’un texte à l’autre. Au bout d’un texte, les flèches passent au texte suivant dans le manuscrit, qu’il suive la numérotation continue ou qu’il soit synchronisé à part. Le panneau du pivot fait de même : un pivot commun à plusieurs textes se parcourt d’un seul tenant. Une page qui porte la fin d’un texte et le début d’un autre reste affichée. Le panneau d’un témoin absent du texte affiché (« Pas d’alignement de ce témoin pour ce texte. ») mène, par ses flèches, au texte suivant ou précédent qui a ce témoin, dans l’ordre de l’édition.

Ordre des textes dans un manuscrit. Varians le déduit des pages du témoin :

  • la place des pages dans la liste d’images déclarée du témoin (manifeste IIIF ou fichiers, dans Fichier → Paramètres du projet…) ;
  • sinon, les pages communes à ses JSON : chaque JSON est déjà dans l’ordre du manuscrit, et une page qui porte la fin d’un texte et le début d’un autre les relie ;
  • sinon, le <locus from> du témoin pour le texte, ou la foliotation de la première page du texte (un numéro suivi de r ou v), comparée à celle des autres pages ;
  • sinon, le texte garde sa place dans l’ordre de l’édition, et Varians le signale.

Affichage → État des témoins… donne l’ordre des textes dans chaque manuscrit présent dans plusieurs textes, et signale une place incertaine. Pour la rendre sûre, déclarez les images du témoin, ou ajoutez dans son <witness> un <locus from="80r" target="#s04">.

Mener l’édition ou feuilleter. Le bouton au livre ouvert, juste après ← → ⤺, décide si les flèches d’un manuscrit mènent l’édition. Enfoncé (fond bleu-gris), les flèches et le choix du folio de ce manuscrit déplacent aussi le curseur dans l’édition, comme décrit ci-dessus ; relâché, ils ne font que feuilleter le manuscrit, sans toucher à l’édition. Par défaut, seul le bouton du témoin pivot est enfoncé. Le panneau suit toujours l’édition quand le curseur y bouge. L’état de chaque manuscrit est retenu pour le projet, sans modifier project.xml.

Lacunes des témoins

Le passage qu’un témoin n’a pas (feuillet perdu, texte interrompu) s’encadre, en TEI, par <lacunaStart/> et <lacunaEnd/>. La TEI place ces balises dans une leçon : le témoin est celui du <rdg> (ou du <lem>) qui les contient, ou, dans une leçon de plusieurs témoins, celui de leur propre @wit :

<app><lem wit="#T1 #P"/><rdg wit="#T2"><lacunaStart/></rdg></app>
…
<app><lem wit="#T1 #P"/><rdg wit="#T2"><lacunaEnd/></rdg></app>

<rdg wit="#T2 #P">… <lacunaStart wit="#P"/></rdg>

Varians reconnaît aussi ces balises hors d’une leçon, avec @wit, mais la validation TEI les y signale comme erreurs.

Dans les panneaux. Quand le curseur est dans une lacune d’un témoin, son panneau garde la ligne (ou, pour un témoin suivi par pages, la page) où son texte s’interrompt, avec le bandeau « Lacune de ce témoin : son texte s’interrompt ici. ». Quand le curseur est dans une lacune du témoin pivot, les témoins synchronisés par lignes restent sur la dernière ligne du pivot, avec le bandeau « Lacune du témoin pivot : les lignes ne sont plus synchronisées dans ce passage. » ; la barre d’état le signale aussi. Les témoins suivis par pages continuent de suivre leurs <pb>, qui ne dépendent pas du pivot.

Débugger l’apparat. Le contrôle « <app> incomplets (un témoin n’y a pas de leçon) » n’attend pas de leçon d’un témoin dans sa lacune.

Une lacune sans <lacunaEnd/> court jusqu’à la fin du texte. Dans une édition en parties, une lacune peut commencer dans une partie et finir dans une autre ; dans un texte synchronisé à part, seules comptent les lacunes de ce texte. Le viewer web montre les mêmes bandeaux.

Disposition des panneaux

Affichage → Choisir les témoins affichés… : cochez les témoins à montrer, puis Monter et Descendre pour les ranger. Sans témoin affiché, la zone des images disparaît. Les panneaux se partagent la hauteur, réglable ; un double-clic sur l’en-tête d’un témoin l’agrandit, un second rétablit la répartition. Le viewer web publie les témoins affichés, dans cet ordre.

Affichage → Disposition des témoins : Verticale, Horizontale ou Grille (2 colonnes), sans perdre zoom, cadres ni synchronisation. Détacher un témoin (ou ↗ dans son en-tête) l’ouvre dans sa propre fenêtre, à placer sur un autre écran, avec sa case Toujours au premier plan ; fermer cette fenêtre, ou ↙, le Rattacher ; Rattacher tous les témoins les ramène tous. La barre entre l’éditeur et les images se déplace : l’éditeur peut n’occuper qu’un cinquième de la largeur. Recharger images (F5) relit les images.

Ces choix sont gardés sur votre ordinateur, pour chaque projet ; ils ne modifient ni la TEI, ni project.xml, ni les alignements.

État des témoins

Affichage → État des témoins… donne, pour chaque témoin, ses pages, ses images, ses lignes et ses liens valides vers le pivot. Ses avertissements distinguent l’absence normale d’alignement des défauts : fichier d’alignement introuvable, autre pivot, liens vers des lignes inconnues, lignes ALTO ou PAGE non associées à une image IIIF. Pour une édition en parties, il donne aussi la portée (l’édition ou le texte affiché), les textes synchronisés à part, et l’ordre des textes dans chaque manuscrit.

9. Apparat critique

Encoder l’apparat

Varians attend un apparat en parallel segmentation (voir Notions clés) : un <app> par lieu variant, dans le texte, avec sa leçon retenue (<lem>) et ses variantes (<rdg>), dont @wit cite les témoins. Les leçons d’un <rdgGrp> comptent comme les autres ; une leçon vide, <rdg wit="#B"/>, est une omission du témoin B. Un <app> peut en contenir d’autres.

<app>
  <lem wit="#A #C">uidelicet</lem>
  <rdg wit="#B">scilicet</rdg>
  <rdg wit="#D"/>
</app>
  • Saisie. Dans un @wit, taper # ouvre la liste des témoins de la <listWit>, avec leur description ; plusieurs témoins se séparent par des espaces, et ceux qui sont déjà cités ne sont pas reproposés.
  • Témoins cités. Un témoin cité sans être déclaré dans la <listWit> est signalé par Éditer → Références (voir Références entre documents).
  • Lacunes. Le passage qu’un témoin n’a pas s’encadre par <lacunaStart/> et <lacunaEnd/>, dans une de ses leçons : voir Lacunes des témoins.
  • Texte établi. Partout où Varians publie le texte établi, le <lem> prime ; un <app> sans <lem> prend la leçon d’un témoin choisi, par défaut le pivot.

Débugger l’apparat

Aide → Débugger l’apparat… propose des requêtes XPath toutes prêtes pour repérer les erreurs de l’apparat critique du document affiché, encodé en parallel segmentation : chaque <app> réunit ses leçons (<lem>, <rdg>, y compris dans un <rdgGrp>), dont @wit cite les témoins sous la forme #A. Les témoins sont ceux du <listWit> du document.

  • Témoin cité plusieurs fois : un même témoin figure dans deux leçons d’un <app>, ou deux fois dans le même @wit ; sa leçon est ambiguë.
  • <app> incomplets : un témoin n’a pas de leçon. Pour un <app> de premier niveau, tous les témoins du <listWit> sont attendus ; pour un <app> imbriqué, ceux de la leçon qui le contient. Un <lem> sans @wit est réputé couvrir les témoins absents des <rdg> : son <app> n’est pas signalé.
  • <app> sans <lem> : les <app> qui n’ont pas de <lem> ; un <lem> placé dans un <rdgGrp> de l’<app> compte. Cette recherche ne dépend pas des témoins : elle reste disponible sans <listWit>.
  • Témoin donné : les <app> où un témoin choisi dans la liste apparaît, ou n’apparaît pas, dans <lem> ou <rdg>, ou dans <rdg> seulement.
  • Mes requêtes : vos propres requêtes XPath, nommées, pour les contrôles propres à votre encodage. Ajouter… propose la requête en cours du panneau XPath ; Modifier… et Supprimer les gèrent. Elles sont enregistrées dans project.xml (élément <xpathQueries>) et suivent le projet.

Rechercher lance la requête dans le panneau XPath : un clic sur un résultat sélectionne l’<app>. La requête reste dans le champ XPath : c’est du XPath 1.0 ordinaire, avec le préfixe tei:, que l’on peut copier dans d’autres outils XML. Elle peut être longue, car elle comporte une condition par témoin.

Limites : les groupes de témoins (un <listWit xml:id="…"> cité dans @wit) ne sont pas développés ; un témoin cité mais absent du <listWit> est signalé par la commande Éditer → Références ; si des témoins du <listWit> ne sont pas collationnés dans l’apparat, tous les <app> paraissent incomplets.

Publier l’apparat

  • Édition critique (HTML) : le texte établi, et l’apparat après chaque division, appelé par des chiffres ; voir Édition critique.
  • TEI : DOCX (Word) et TEI : ODT (LibreOffice) : l’apparat en notes de bas de page, selon les mêmes règles ; voir TEI Stylesheets.
  • Viewer web : un rond violet à chaque lieu variant montre les leçons et leurs témoins ; le texte affiché est, au choix, le texte établi ou la transcription d’un témoin ; voir Viewer web.

10. Éditions en parties (XInclude)

Une édition longue, une collection ou un corpus peuvent être découpés en fichiers, un par texte, que l’édition assemble par XInclude. Varians traite l’ensemble comme un seul document, tout en éditant chaque fichier à part. Ce chapitre décrit le fonctionnement, puis la mise en place pas à pas.

Principe

Pour mettre en place un tel projet pas à pas, voir le mode d’emploi.

Une édition peut inclure ses parties, par exemple un fichier par sermon, selon la norme XInclude. L’édition déclarée dans project.xml reste le document maître ; ses parties se déduisent de ses xi:include, sans autre déclaration :

<TEI xmlns="http://www.tei-c.org/ns/1.0"
     xmlns:xi="http://www.w3.org/2001/XInclude">
  …
  <body>
    <xi:include href="sermons/s01.xml"/>
    <xi:include href="sermons/s02.xml" xpointer="s02"/>
    <xi:include href="sermons/s03.xml" xpointer="element(/1/2/1/1)"/>
  </body>

Une partie est soit un fragment (le fichier entier, dont la racine est par exemple le <div> du sermon), soit un élément d’un document TEI complet, désigné par xpointer : son identifiant (s02 ou element(s02)) ou son chemin (element(/1/2/1/1) : TEI, puis son 2ᵉ enfant text, puis body, puis le premier div). Une partie peut elle-même en inclure d’autres. Les chemins relatifs écrits dans une partie partent du dossier de la partie.

Parties et onglets

Chaque partie a son onglet, nommé d’après son fichier, après celui de l’édition et dans l’ordre d’inclusion. Elle s’édite et s’enregistre seule (Ctrl+S), avec son propre historique d’annulation ; avant de quitter, Varians propose d’enregistrer les parties modifiées. La liste des parties est relue à chaque enregistrement de l’édition ou d’une partie. « Renommer l’onglet… » et « Retirer le document du projet » ne concernent que les documents auxiliaires. La Vue XSLT / CSS reste ouverte quand une partie est affichée : elle montre toute l’édition (voir Vue XSLT / CSS de l’édition assemblée) ; les témoins restent eux aussi affichés (voir ci-dessous). Enregistrer l’édition dans un autre dossier romprait les chemins de ses xi:include : Varians le signale avant.

Validation

L’édition et chacune de ses parties font valider l’édition assemblée, avec le schéma de l’édition et en tenant compte des modifications non enregistrées des parties. Le panneau RELAX NG ajoute alors une colonne Document ; un double-clic sur une erreur ouvre la bonne partie à la bonne ligne. L’onglet de chaque partie prend la couleur de ses propres erreurs. Une partie absente ou mal formée, une inclusion circulaire ou une forme non prise en charge (parse="text", xi:fallback, autre schéma xpointer) est signalée à la ligne de son xi:include.

Références et témoins

L’édition et ses parties forment un seul document : un #id se cherche d’abord dans le fichier qui le contient (en-tête compris), puis dans les autres parties. F12, la commande Références et la complétion en tiennent compte. Seuls les identifiants de l’élément inclus d’une partie appartiennent à l’édition assemblée : un témoin déclaré seulement dans le <teiHeader> d’un sermon inclus par xpointer est trouvé par Varians dans ce sermon, mais un outil qui ne lit que l’édition assemblée ne le verra pas. Dans une partie, Aide → Débugger l’apparat… prend les témoins propres à la partie : son <listWit>, sinon les témoins de l’édition dont un <locus target="#s01"> vise la partie, sinon ceux que citent ses @wit.

Synchronisation des témoins

Quand l’édition est découpée en fichiers par commodité (une collection dont les textes se suivent comme dans le témoin pivot), les témoins se synchronisent comme pour une édition en un seul fichier : les lignes du pivot (<lb edRef="#A"/>) sont comptées dans l’ordre de l’édition assemblée, d’une partie à l’autre, et les fichiers d’alignement restent ceux d’une édition en un seul fichier, un par témoin pour toute l’édition. Le curseur de l’édition ou d’une partie fait suivre les témoins ; un clic ou un défilement dans le pivot place le curseur dans la partie qui contient la ligne et ouvre son onglet, même après « Masquer l’onglet ». L’état de structure (barre d’état) compte les lignes du pivot dans toute l’édition assemblée, et l’enregistrement de l’édition ou d’une partie avertit si ce nombre diffère de celui de l’alignement du pivot. Un <lb/> placé dans un commentaire ou hors de l’élément inclus d’une partie ne compte pas, comme dans les autres outils XML.

Condition : le pivot doit contenir ces textes dans l’ordre de l’édition. Varians vérifie le nombre de lignes, pas leur ordre. Les autres témoins peuvent avoir un autre ordre, ou ne pas avoir un texte : leur alignement désigne déjà des lignes du pivot. Un témoin synchronisé par pages suit le dernier <pb> qui le concerne, dans l’ordre de l’édition, même dans une partie précédente : si ce témoin a les textes dans un autre ordre, marquez sa page au début de chaque texte.

Depuis une partie, « Marquer la page » insère le <pb> dans la partie, au curseur, et complète le <facsimile> de l’édition ; « Double page… » écrit ses zones dans le <facsimile> de l’édition. L’édition est alors modifiée sans être affichée : son onglet porte « * ». Annuler dans la partie retire le <pb>, pas les ajouts au <facsimile>.

Textes synchronisés à part

Dans un corpus dont les textes ne sont pas transmis par les mêmes témoins, ni dans le même ordre, un texte peut avoir ses propres alignements : un JSON par témoin, au format habituel, dans un dossier qui porte le nom du fichier du texte, sans extension (alignments/s02/B.json pour xml/sermons/s02.xml). Rien n’est à déclarer : un texte qui a son dossier est synchronisé à part ; les autres suivent la numérotation continue. Le pivot d’un texte est celui du projet, sauf exception déclarée dans project.xml : <part name="s02" base="B"/>.

Quand un tel texte est affiché, les panneaux des témoins prennent ses alignements et son pivot ; la disposition, le zoom et les fenêtres détachées ne changent pas. Un témoin sans JSON pour ce texte garde son panneau, qui indique « Pas d’alignement de ce témoin pour ce texte. ». Les lignes sont comptées dans le texte seul (par exemple « B : 8 lignes ✓ ») ; un clic dans le pivot reste dans le texte. Le diagnostic des témoins et l’actualisation des synchronisations portent sur le texte affiché.

Témoins suivis par pages. Un témoin qui n’a pas de JSON pour ce texte, mais qui l’a — un <pb edRef="#C"/> dans le texte, ou un <locus target="#s04"> dans son <witness> du <listWit> —, y suit ses pages. Avant son premier <pb> dans le texte, il montre sa page de départ : le @from de ce locus (<locus from="13r" to="14r" target="#s04">), sinon la page qui précède celle de ce premier <pb>, dans l’ordre des pages du témoin. « Marquer la page » y fonctionne aussi. Le diagnostic des témoins nomme, pour chaque texte, ses témoins suivis par pages. Les autres témoins sans JSON gardent le message d’absence.

Vue XSLT / CSS de l’édition assemblée

La Vue XSLT / CSS montre toute l’édition, parties comprises, quel que soit le document affiché, et s’utilise comme pour une édition en un seul fichier. Passer de l’édition à une partie ne la quitte pas ; seul l’affichage d’un document auxiliaire la referme.

  • Édition par fragment. Le crayon ✎ d’un élément l’ouvre dans l’éditeur de fragment, tel qu’il est écrit dans le fichier qui le contient ; l’étiquette nomme ce fichier, par exemple « Fragment TEI · <p> 10/16 · s03.xml ». Le fragment appliqué est écrit dans ce fichier, même s’il n’est pas affiché ou n’a jamais été ouvert : son onglet porte alors « * », et une seule annulation, dans la partie, retire la modification. Le fichier doit rester bien formé. Ctrl+S dans l’éditeur de fragment enregistre ce fichier, puis le document affiché s’il est modifié ; avant de quitter, Varians propose d’enregistrer un fragment non appliqué avec son fichier.
  • Clic, table des matières, recherche. Un clic sur une ligne place le curseur à cette ligne, dans le fichier qui la contient, dont l’onglet s’ouvre, sans quitter l’aperçu ; les témoins suivent, avec la numérotation propre d’un texte synchronisé à part. La table des matières et la recherche dans l’aperçu font de même.
  • Sélections. Une chaîne sélectionnée dans l’aperçu est sélectionnée, en revenant à l’onglet XML source, dans le fichier qui contient le texte (une partie, ou l’édition), à la même occurrence du même paragraphe ; sans sélection, le curseur va à la ligne affichée. Inversement, la sélection ou la position d’une partie est retrouvée dans l’aperçu. Entre l’aperçu et l’éditeur de fragment, les sélections se répondent comme pour une édition en un seul fichier.
  • Limites. Un paragraphe qui contient lui-même un xi:include s’édite dans le fichier de sa balise ; le texte inclus s’édite dans sa partie. Comme pour une édition en un seul fichier, un paragraphe ou une ligne que la XSLT ne rend pas décale les crayons ou les repères de ligne qui le suivent.

Export web de l’édition assemblée

Générer viewer web exporte toute l’édition, parties comprises, avec les continuités de la fenêtre.

  • Texte et lignes. Le texte des parties est dans le viewer, et les lignes du pivot y sont comptées d’une partie à l’autre, comme dans la fenêtre. Un texte synchronisé à part garde son pivot et ses JSON (alignments/s02/) : quand la ligne choisie y passe, chaque panneau montre son témoin dans ce texte, par ses lignes, par ses pages depuis sa page de départ, ou par « Pas d’alignement de ce témoin pour ce texte. ». Le zoom et les cadres de chaque panneau restent d’un texte à l’autre. Les boutons de l’en-tête parcourent toutes les lignes dans l’ordre de lecture, d’un texte à l’autre.
  • Flèches des panneaux. Comme dans la fenêtre, les flèches ← → de tout panneau mènent le texte dans l’ordre propre du manuscrit, d’une partie ou d’un texte à l’autre, et la liste des folios d’un témoin suivi par pages aussi ; ⤺ ramène le panneau sur la ligne reliée. Les messages de la barre d’état de la fenêtre (début ou fin du manuscrit, ligne non reliée, page non située, place incertaine) s’affichent sous le titre du viewer.
  • Lacunes. Les bandeaux sont ceux de la fenêtre (voir Lacunes des témoins) : une lacune continue d’une partie à l’autre, et un texte synchronisé à part repart sans lacune.
  • Enregistrement. L’export lit les fichiers enregistrés : Varians enregistre d’abord l’édition, chaque partie modifiée et le fragment non appliqué d’une partie ; si l’un d’eux ne peut l’être, l’export est annulé. Une partie introuvable, ou une inclusion non prise en charge (parse="text", xi:fallback), est signalée dans le compte rendu de l’export : le texte concerné manque dans le viewer.
  • Limites. La position retenue est celle du fragment de texte cliqué. Un <pb> ou un <lb> placé dans une leçon non retenue ou dans une note n’est pas vu par le viewer. « État des témoins… », « Actualiser les synchronisations… », « Marquer la page » et « Double page… » restent propres à la fenêtre. Régénérez le viewer après une modification de l’édition.

Limites

L’ordre des textes dans un manuscrit est déduit de ses pages ; un texte qui ne s’y rattache pas garde sa place dans l’ordre de l’édition (voir Suivre un manuscrit dans son propre ordre). L’export web a ses propres limites : voir Export web de l’édition assemblée. Un projet sans xi:include n’est pas concerné.

Mode d’emploi

Ce mode d’emploi décrit, pas à pas, comment organiser un projet dont l’édition est découpée en plusieurs fichiers, par exemple un fichier par sermon. Le détail de chaque fonction se trouve plus haut, dans Principe.

1. Organiser les fichiers

Gardez un seul fichier d’édition, celui que déclare project.xml (par exemple xml/edition.xml) : c’est le document maître, avec l’en-tête, la liste des témoins et l’ordre des textes. Rangez les textes dans un dossier voisin, un fichier par texte. Donnez à chaque fichier un nom unique dans tout le projet : ce nom, sans extension, sert aussi au dossier d’alignements d’un texte synchronisé à part (étape 4). Les chemins sont relatifs au fichier qui les contient : sermons/s01.xml depuis l’édition, ../personnes.xml#augustinus depuis un sermon.

project.xml
alignments/T1.json, T2.json …
alignments/s02/B.json, D.json
xml/edition.xml
xml/sermons/s01.xml, s02.xml, s03.xml …

2. Écrire les xi:include

Déclarez l’espace de noms XInclude sur l’élément racine de l’édition, puis placez un xi:include à l’endroit de chaque texte :

<TEI xmlns="http://www.tei-c.org/ns/1.0" xmlns:xi="http://www.w3.org/2001/XInclude">
  …
  <body>
    <xi:include href="sermons/s01.xml"/>
    <xi:include href="sermons/s02.xml" xpointer="s02"/>
  </body>
</TEI>

Un texte est soit un fragment : le fichier entier, dont la racine est l’élément inclus et porte l’espace de noms TEI (<div xmlns="http://www.tei-c.org/ns/1.0" xml:id="s01">) ; soit un document TEI complet, dont on n’inclut qu’un élément, par son identifiant (xpointer="s02") ou par son chemin (xpointer="element(/1/2/1/1)"). Un document complet peut aussi être validé seul ; son en-tête n’entre pas dans l’édition. Un texte peut lui-même en inclure un autre. N’utilisez ni parse="text" ni xi:fallback : Varians les signale sans les prendre en charge. Enregistrez l’édition : chaque texte reçoit son onglet.

3. Déclarer les témoins

Déclarez chaque manuscrit une seule fois, dans Fichier → Paramètres du projet…, avec un sigle commun à toute la collection. Dans le TEI, déclarez les témoins dans le <listWit> de l’édition, dans celui de chaque texte (document TEI complet), ou dans les deux. Un témoin déclaré seulement dans l’en-tête d’un texte inclus par xpointer est trouvé par Varians, mais un outil qui ne lit que l’édition assemblée ne le voit pas.

4. Choisir la synchronisation de chaque texte

  • Les textes se suivent comme dans le pivot, avec les mêmes témoins (une collection découpée par commodité) : numérotation continue. Un JSON par témoin pour toute l’édition, comme pour une édition en un seul fichier, déclaré dans les paramètres du projet. Les lignes du pivot sont comptées d’un texte à l’autre, dans l’ordre de l’édition ; le pivot doit contenir les textes dans cet ordre.
  • Les témoins changent d’un texte à l’autre (un corpus) : texte synchronisé à part. Créez le dossier alignments/<nom du fichier du texte>/ et placez-y un JSON par témoin pour ce texte, au format habituel : alignments/s02/B.json, alignments/s02/D.json. Produisez ces JSON avec VariansSynchro sur le fichier du texte. Il n’y a rien à déclarer : le dossier suffit. Un témoin sans JSON pour ce texte, mais qui y a ses <pb edRef> ou un <locus target> dans son <witness>, y suit ses pages : voir Textes synchronisés à part.
  • Les deux peuvent se mêler : les textes qui ont leur dossier sont synchronisés à part ; les autres suivent la numérotation continue, et le JSON global de chaque témoin ne contient que leurs lignes.

5. Déclarer un pivot propre à un texte

Le pivot d’un texte synchronisé à part est celui du projet. Si le pivot du projet n’a pas ce texte, ou si un autre témoin doit servir de référence, écrivez l’exception à la main dans project.xml, avant </teiManuscriptProject>, puis rouvrez le projet :

<parts>
  <part name="s02" base="B"/>
</parts>

name est le nom du fichier du texte, sans extension ; base, le sigle du pivot. Les lignes de ce texte sont alors ses <lb edRef="#B"/>, et son dossier doit contenir B.json. Varians garde cet élément quand on enregistre les paramètres du projet.

6. Vérifier

  • Affichez chaque texte : l’état de structure, dans la barre d’état, doit être juste, par exemple « B : 8 lignes ✓ » ; sa bulle d’aide dit si le compte porte sur l’édition assemblée ou sur un texte synchronisé à part.
  • Affichage → État des témoins… indique la portée (l’édition ou le texte affiché), les textes synchronisés à part avec leur pivot et leurs témoins, et les problèmes : JSON d’un témoin non déclaré, pivot inconnu, JSON du pivot manquant…
  • La validation RELAX NG porte sur l’édition assemblée ; la colonne Document indique le fichier de chaque erreur.
  • La commande Références vérifie les renvois d’un texte à l’autre.
  • Un autre outil XML assemble le projet sans Varians : xmllint --xinclude --noout xml/edition.xml, ou oXygen avec XInclude activé dans les préférences du validateur.
  • Affichage → État des témoins… donne aussi l’ordre des textes dans chaque manuscrit ; une place incertaine y est signalée : voir Suivre un manuscrit dans son propre ordre.

7. Au quotidien

  • Chaque texte s’édite dans son onglet et s’enregistre seul (Ctrl+S) ; avant de quitter, Varians propose d’enregistrer les textes modifiés.
  • Pour ajouter un texte : créez son fichier, ajoutez son xi:include dans l’édition, enregistrez l’édition ; son onglet apparaît. Pour un texte synchronisé à part, ajoutez aussi son dossier d’alignements, puis Affichage → Actualiser les synchronisations….
  • S’il y a beaucoup d’onglets : clic droit sur un onglet → Masquer l’onglet ; un clic dans le pivot fait réapparaître l’onglet du texte voulu.
  • Enregistrer l’édition dans un autre dossier romprait ses xi:include : Varians le signale avant.
  • La Vue XSLT / CSS montre toute l’édition : le crayon ✎ y ouvre un élément de n’importe quel texte, et un clic y mène au texte qui contient la ligne ; voir Vue XSLT / CSS de l’édition assemblée. L’export web contient toute l’édition ; voir Export web de l’édition assemblée.
  • Pour lire un manuscrit d’un texte à l’autre, utilisez les flèches de son panneau : l’édition affiche le bon texte.

11. Viewer web

Le viewer web publie l’édition avec ses fac-similés : le texte à gauche, les manuscrits à droite, synchronisés comme dans Varians. C’est une page HTML autonome, qui s’ouvre dans tout navigateur, sans serveur ni Varians, et peut être mise en ligne telle quelle.

Générer le viewer

Générer viewer web (barre d’outils, ou Fichier → Générer le viewer web) demande d’abord le texte à afficher (voir Choix du texte), puis écrit le viewer dans web_output/ (viewer.html), avec les images locales qu’il emploie (web_output/images/). Le dossier et le nom du fichier se règlent dans Fichier → Paramètres du projet….

Avant l’export, Varians enregistre l’édition, ses parties modifiées et le fragment non appliqué d’une partie ; si l’un d’eux ne peut l’être, l’export est annulé. Le viewer publie les témoins affichés, dans leur ordre (Affichage → Choisir les témoins affichés…) ; un pivot masqué n’y sert qu’à la synchronisation. Le compte rendu de l’export signale les images introuvables et les passages sans leçon du témoin choisi. Le viewer est une copie : générez-le de nouveau après une modification de l’édition.

Sans ouvrir Varians, déposez le project.xml d’un projet sur generer_viewer_web.bat, ou exécutez python -m web_viewer.generator project.xml : le viewer est le même, avec le choix du texte enregistré dans le projet.

Le texte

Texte de lecture. Le viewer lit tous les textes de l’édition : <front>, <body> et <back>, et chaque texte d’un <group>. Une division est titrée par son premier <head>, sinon par son @n ; son @xml:id n’est pas un titre. Des préliminaires ou des annexes sans titre s’intitulent « Préliminaires » ou « Annexes ». Le sommaire liste les divisions titrées, en retrait sous la division titrée qui les contient. Chaque <lg> est une strophe, chaque <l> sur sa ligne, son @n en marge ; une liste garde ses sous-listes ; un <table> est un tableau, avec sa légende, ses en-têtes (@role="label") et ses cellules fusionnées (@cols, @rows) ; une <note> placée entre deux paragraphes est un repère, masqué avec les notes. Chaque réplique (<sp>) est un bloc, son locuteur (<speaker>) en tête, en petites capitales ; une didascalie (<stage>) est entre parenthèses, en italique, en bloc entre deux répliques ou dans une réplique, dans la phrase quand elle est dans un paragraphe. Comme dans « Édition critique (HTML) », un <choice> montre une forme (correction, régularisation, développement), l’autre en infobulle ; <del> est barré, <add> souligné de pointillés, <supplied> entre crochets, et <gap> donne « […] », sa raison et son étendue en infobulle. Les leçons d’un <rdgGrp> comptent comme les autres. Le texte prend la langue de son @xml:lang, ce qui règle la césure. Comme dans « Édition critique (HTML) », le <ref> d’une <cit> portant type="bible" suit la citation entre chevrons ; celui d’une autre <cit> est une note.

Choix du texte. « Générer viewer web » demande d’abord quel texte afficher : le texte établi (le <lem>, à défaut la leçon du témoin choisi, comme « Édition critique (HTML) ») ou le texte du témoin choisi, même quand ce n’est pas le <lem>, ce qui reconstitue sa transcription. Le témoin choisi est par défaut le pivot de chaque texte. Là où il n’a pas de leçon (aucune leçon de l’<app> ne le nomme : passage absent, lacune, apparat incomplet), le viewer affiche le <lem>, sinon la leçon du pivot, sur fond grisé et encadré de pointillés, avec l’infobulle « Pas de leçon de … ici » ; « ∅ » marque un tel passage vide. Une omission (<rdg wit="#T2"/>) est une leçon et n’est pas signalée. L’en-tête du viewer et le compte rendu de l’export donnent le nombre de ces passages. La synchronisation suit toujours les lignes du pivot : celles de sa leçon non affichée se répartissent dans le texte affiché ; quand le témoin omet le passage, un repère invisible garde leur place. Avec le texte établi, la case Surligner en jaune les leçons qui ne viennent pas d’un <lem> de la même boîte surligne au départ les leçons retenues faute de <lem>, celles qui restent à trancher ; dans le viewer, le lecteur les montre ou les cache par la case Leçons hors <lem> de l’en-tête. Le choix est gardé dans project.xml, <webViewer text="established|witness" textWitness="T2" highlightNonLem="true"/> ; generer_viewer_web.bat le suit.

Dans le texte, un rond violet v marque chaque variante : un clic montre les leçons et leurs témoins. Un rond n marque une note. Les cases Variantes et Notes de l’en-tête masquent ces repères ; la case Leçons hors <lem>, dans le texte établi, surligne en jaune les leçons qui ne viennent pas d’un <lem> ; A− et A+ règlent la taille du texte ; Langue change la langue du viewer.

Le texte et les manuscrits

Chaque témoin a sa carte, à droite, avec les commandes de son panneau dans Varians : flèches, zoom (aussi à la molette, et par double-clic pour revenir à 100 %), Cadres, Page ↗ et ⤺. Un projet sans image est publié sans colonne de fac-similés.

  • Par lignes. Un clic sur le texte choisit la ligne du pivot ; chaque témoin synchronisé montre sa ligne, recadrée, avec un contour bleu, même quand ses autres cadres sont masqués. ← ligne et ligne →, dans l’en-tête, parcourent les lignes dans l’ordre de lecture.
  • Par pages. Un clic dans le texte montre, pour chaque témoin suivi par pages, la page de son dernier <pb> ; sans aucun alignement, les boutons de l’en-tête deviennent ← page et page →.
  • Dans l’ordre du manuscrit. Comme dans Varians, les flèches ← → de toute carte mènent le texte : le témoin avance dans son propre ordre, et le texte va à la ligne du pivot que désigne sa ligne, ou à son <pb> pour un témoin suivi par pages, dont la liste des folios mène aussi le texte ; ⤺ ramène la carte sur la ligne reliée. Les messages (début ou fin du manuscrit, ligne non reliée…) s’affichent sous le titre.
  • Lacunes. Les lacunes des témoins ont leurs bandeaux, comme dans Varians (voir Lacunes des témoins).

Un texte sans repère de ligne, ou une ligne absente de l’export, est signalé : le viewer ne déduit jamais une correspondance incertaine. Pour une édition en parties, voir Export web de l’édition assemblée.

Chercher

Le champ Rechercher… de l’en-tête cherche un mot ou une expression dans tout le texte affiché : titres, vers, entrées de liste, cellules, locuteurs et didascalies compris. Sans autre choix, la recherche est exacte, sans tenir compte de la casse ; sous Graphies médiévales, les cases u/v, i/j et c/t rendent ces lettres équivalentes. Les résultats sont listés et surlignés ; un résultat mène à son passage et aux lignes des manuscrits.

Les images

Les images locales sont copiées avec le viewer. Les images IIIF sont lues sur leurs serveurs : le viewer demande à chaque fois la taille utile (services IIIF Image 1, 2 et 3), et se replie sur une image plus petite, puis sur l’image entière, puis sur l’aperçu du manifeste si le serveur refuse. Elles demandent donc un accès à Internet et les droits nécessaires, sauf pour les pages dont la copie locale est publiée (voir Copies locales des images IIIF). Les cadres suivent les contours PAGE et les zones d’une double page, aux coordonnées de l’image source.

12. Publier avec XSLT

Au-delà du viewer web, Varians publie l’édition par des feuilles XSLT : les siennes (Édition critique, Édition HTML), celles du TEI Consortium (DOCX, ODT, EPUB, HTML, LaTeX…), et les vôtres. Chaque publication est un scénario, que l’on rejoue d’un clic.

Scénarios de transformation XSLT

Un scénario de transformation applique une feuille XSLT à l’édition ou à un autre document du projet, et écrit le résultat dans un fichier : édition HTML, index, liste de citations, XML transformé… Il est nommé, enregistré dans le projet, et se rejoue à l’identique. Le viewer web reste une publication à part, qu’un scénario ne modifie pas.

Fichier → Scénarios de transformation… montre deux groupes :

  • Scénarios du projet, enregistrés dans project.xml (élément <transformations>) : Ajouter…, Modifier…, Dupliquer… et Supprimer les gèrent.
  • Scénarios prédéfinis, fournis par Varians : Édition HTML (feuille de Varians), qui publie l’édition avec la feuille et la CSS de l’aperçu de Varians dans publications/edition.html ; Édition critique (HTML), une édition critique avec son apparat, d’après le témoin pivot (voir Édition critique) ; et, dans le sous-groupe TEI Stylesheets, replié au départ (un clic sur sa flèche le déplie), les scénarios des feuilles du TEI-C (voir TEI Stylesheets). Dans le menu du bouton Transformer, ces derniers forment un sous-menu. On peut exécuter un scénario prédéfini tel quel, ou le dupliquer dans le projet pour l’adapter.

Chaque ligne indique la source, le moteur et, en rouge, ce qui empêche le scénario de s’exécuter (feuille introuvable, Saxon non installé…). Exécuter lance le scénario choisi ; Aperçu l’exécute dans un dossier temporaire et ouvre le résultat, sans toucher au fichier du scénario.

Un scénario

  • Source : Édition (l’édition du projet, assemblée si elle a des parties : chaque partie garde son emplacement, et un document() relatif y trouve ses fichiers), Document affiché (le document de l’onglet courant, par exemple un document auxiliaire, voir Documents XML auxiliaires ; l’édition assemblée si c’est elle) ou Fichier (un fichier lu tel quel).
  • Moteur : XSLT 1.0 (lxml), ou XSLT 3.0 (Saxon) pour les feuilles en XSLT 2.0 ou 3.0. Saxon-HE (paquet saxonche) s’installe avec Varians : installer_dependances.bat, ou pip install -r requirements.txt.
  • Feuille XSLT et CSS facultative : chemins relatifs au projet ; ${varians}/ désigne les feuilles fournies avec Varians. La CSS est copiée à côté du résultat, et son nom est passé à la feuille par le paramètre css (la feuille de Varians le met dans son <link>). Un nouveau scénario propose la feuille et la CSS de l’aperçu.
  • Résultat : le fichier écrit, remplacé à chaque exécution (publications/<nom>.html est proposé). Il ne peut pas être une source du projet (project.xml, l’édition et ses parties, un document, une feuille, un schéma, un JSON d’alignement). Avec Saxon, une feuille peut écrire d’autres fichiers par xsl:result-document (une page par sermon, par exemple), dans le dossier du résultat et ses sous-dossiers seulement ; ailleurs, l’exécution est refusée.
  • Format du résultat (avec Saxon) : Un seul fichier, le plus souvent ; Pages HTML (une par division), quand la feuille écrit index.html et ses pages par xsl:result-document ; DOCX (Word), ODT (LibreOffice) ou EPUB, quand elle écrit les fichiers d’une archive dans le dossier dont elle reçoit l’adresse, comme les feuilles du TEI-C : Varians fait alors l’archive, qui est le résultat (voir TEI Stylesheets).
  • Pré-passage TEI → TEI (facultatif), avec Saxon : une feuille appliquée à la source avant celle du scénario, avec les mêmes paramètres. Les scénarios DOCX et ODT mettent ainsi l’apparat en notes de bas de page.
  • Paramètres : des paires nom / valeur, passées à la feuille (<xsl:param name="titre"/>). Avec Saxon, elles sont passées sans type, comme par sa ligne de commande : « false » convient à un paramètre xs:boolean, « 3 » à un xs:integer, et la valeur reste une chaîne ailleurs ; avec lxml, ce sont des chaînes. Dans une valeur, ${pivot} devient l’identifiant du témoin pivot du projet, et ${tei}/ l’adresse du dossier des TEI Stylesheets installées.

Exécution

Le bouton Transformer, à côté de Générer viewer web, relance le dernier scénario exécuté dans le projet (aussi Ctrl+Shift+T) ; sa flèche donne la liste des scénarios. Avant l’exécution, Varians enregistre ce que le scénario lit : l’édition, ses parties modifiées et le fragment non appliqué, comme pour l’export web, ainsi que le document source, la feuille et la CSS s’ils sont ouverts et modifiés. La transformation tourne dans un processus à part : Varians reste utilisable, et Annuler l’arrête.

Le compte rendu donne les fichiers écrits et la durée ; Ouvrir ouvre le résultat dans l’application par défaut (le navigateur, pour du HTML), Ouvrir le dossier le dossier qui le contient. Ses détails donnent le journal : moteur et version, paramètres, xsl:message, lectures réseau (avec lxml), écritures refusées. En cas d’erreur, le message indique le fichier et la ligne en cause, et le résultat précédent reste intact.

Sécurité : une feuille peut lire tout fichier local, et des adresses http ou https (le résultat peut alors dépendre d’un serveur) ; elle n’écrit que son résultat (et, avec Saxon, des fichiers de son dossier). Les entités externes des sources ne sont pas lues.

Édition critique

Le scénario prédéfini Édition critique (HTML) publie l’édition (assemblée, si elle est en parties) en une page HTML autonome, à lire à l’écran ou à imprimer : publications/edition-critique.html. Sa feuille, edition-critique.xsl (${varians}/, en XSLT 3.0 : moteur Saxon), est tirée d’une feuille d’édition critique TEI, retouchée pour Varians.

  • Texte établi. Le <lem> d’un apparat prime toujours (un <lem/> vide est une omission établie) ; sinon, c’est la leçon du témoin choisi par le paramètre temoin-de-base, qui vaut ${pivot} : le témoin pivot du projet. Dans la boîte d’un scénario dupliqué, il se choisit dans une liste : le témoin pivot en tête (« T1 (pivot) »), les autres témoins du projet et du <listWit>, puis « aucun (lemmes seuls) » ; une valeur écrite autrement (#B) est gardée ; sans valeur, c’est le premier <witness> de <listWit>. Avec aucun, le texte suit les seuls <lem>, et chaque <app> doit en avoir un. Un témoin inconnu, ou aucun devant un apparat sans lemme, arrêtent l’exécution avec un message clair. Un apparat sans leçon du témoin choisi donne « [lecture du témoin non disponible] ». Quand le texte établi compte des leçons qui ne viennent pas d’un <lem>, la page porte une case Surligner les leçons hors <lem> : cochée, elle les surligne en jaune, pour voir ce qui reste à trancher.
  • Apparat. Après chaque division, en deux séries : l’Apparat critique, appelé dans le texte par des chiffres, et les Notes de l’éditeur, moins nombreuses, appelées par des lettres (a, b… z, aa…). Une entrée donne la leçon retenue, « ] », puis chaque autre leçon suivie de ses sigles en italique ; les leçons d’un <rdgGrp> comptent comme les autres. Une leçon vide donne om. ; quand le texte établi omet le passage, les autres leçons sont des additions (add.). Une leçon qui ne contient que <lacunaStart/> ou <lacunaEnd/> donne « lacuna incipit T1 » ou « lacuna desinit T1 » (voir Lacunes des témoins). Tout texte de l’apparat qui ne vient pas d’un témoin est en italique : sigles, om., add., lacuna incipit et desinit, commentaires ; les leçons restent en romain, même un <sic> (suivi de « sic » en italique), une citation ou une mise en relief. Appels et entrées sont liés dans les deux sens.
  • Texte. Une division sans <head> prend pour titre son @n, sinon n’en a pas. Seuls les <pb> du témoin choisi, ou sans @edRef, s’affichent (⟨12r⟩), et tous avec aucun (⟨T1 : 12r⟩). Des <lb> contigus de plusieurs témoins font une seule coupure, qui soude un mot si l’un d’eux porte break="no". Vers et strophes (<l>, <lg>) gardent leur structure et leurs numéros. Chaque réplique (<sp>) est un bloc, son locuteur (<speaker>) en petites capitales ; une didascalie (<stage>) est entre parenthèses, en italique : un bloc entre deux répliques ou deux vers, dans la phrase quand elle est dans un paragraphe.
  • Paramètres (boîte du scénario, après Dupliquer… ; des cases à cocher, sauf temoin-de-base) : montrer-folios et montrer-numeros-de-vers ; sauts-lb (coché : un saut de ligne du témoin choisi devient un saut de ligne de la page) ; surligner-hors-lemme (coché : la case de la page est cochée au départ ; non coché par défaut).

Les mêmes règles mettent l’apparat en notes de bas de page dans les scénarios DOCX et ODT (voir TEI Stylesheets). Les textes de la page (« Apparat critique », « Notes »…) sont en français : pour les changer, dupliquez le scénario, puis Ouvrir la feuille ; la feuille est copiée dans xslt/ avec apparat-commun.xsl, qui réunit ses règles (voir Scénarios de transformation XSLT).

TEI Stylesheets

Les TEI Stylesheets sont les feuilles XSLT du TEI Consortium (github.com/TEIC/Stylesheets), celles qu’emploient aussi Oxygen et d’autres outils. Varians les apporte et les installe au premier usage, une seule fois pour tous les projets, dans le dossier de données de l’utilisateur : elles marchent sans réseau. Elles sont écrites en XSLT 3.0 : leurs scénarios emploient Saxon.

Scénarios prédéfinis. Dans Fichier → Scénarios de transformation…, le sous-groupe TEI Stylesheets des scénarios prédéfinis réunit huit scénarios qui publient l’édition (assemblée, si elle est en parties) : TEI : HTML, TEI : HTML en plusieurs fichiers, TEI : DOCX (Word), TEI : ODT (LibreOffice), TEI : EPUB, TEI : texte, TEI : Markdown et TEI : LaTeX. Il est replié au départ, et forme un sous-menu du bouton Transformer. Leurs résultats sont écrits dans publications/tei/ (edition.html, pages/index.html, edition.docx, edition.odt, edition.epub, edition.txt, edition.md, edition.tex). Le HTML reçoit à côté de lui la CSS des TEI Stylesheets (tei.css), sans lien vers le site du TEI-C ; les textes qu’ajoutent les feuilles (« Table des matières »…) suivent la langue de l’interface, par les paramètres lang et documentationLanguage. Dans un scénario, ${tei}/ désigne un fichier des TEI Stylesheets installées, par exemple ${tei}/profiles/default/html/to.xsl ; voir Scénarios de transformation XSLT. Le journal d’une exécution nomme la version employée (« Bibliothèque : TEI Stylesheets 7.61.0 »).

Formats en plusieurs fichiers. Quatre de ces scénarios ont un Format du résultat propre (voir Scénarios de transformation XSLT) :

  • TEI : HTML en plusieurs fichiers écrit publications/tei/pages/index.html, le sommaire, et une page par division et par sous-division (s02.html…, d’après leur @xml:id), avec tei.css. Le paramètre splitLevel règle le découpage : 1, la valeur du scénario, découpe les divisions et leurs sous-divisions, ce qui donne une page par pièce quand le texte est une seule division qui les réunit ; 0, les seules divisions de premier niveau. Selon la règle des TEI Stylesheets, la première division reste sur la page du sommaire quand rien ne la précède (pas de <front>).
  • TEI : DOCX (Word) et TEI : ODT (LibreOffice) écrivent edition.docx et edition.odt, à partir du modèle des TEI Stylesheets. Celles-ci rendraient mal l’apparat (toutes les leçons à la suite, chacune dans son paragraphe), et feraient de chaque <pb> un saut de page et de chaque <lb> un saut de ligne : un pré-passage de Varians, apparat-en-notes.xsl, prépare d’abord le texte d’après le témoin pivot (paramètre temoin-de-base, qui vaut ${pivot}). Chaque <app> devient sa leçon retenue, suivie d’une note de bas de page (<note place="foot" type="apparatus">) : « leçon ] variante sigles ; … », avec om., add., lacuna incipit et lacuna desinit, selon les règles de l’édition critique. Une note de l’éditeur sans @place devient une note de fin (place="end") : l’apparat et les notes forment deux séries. Seuls les folios du témoin pivot restent, en repères ⟨12r⟩ dans le texte, et les sauts de ligne des témoins se fondent dans le texte.
  • TEI : EPUB écrit edition.epub, avec les CSS des TEI Stylesheets installées (${tei}/tei.css), lues sans réseau.
  • Les images locales (<graphic url="…"/>) sont mises dans l’archive DOCX, ODT ou EPUB, avec leurs dimensions ; une image distante n’est pas téléchargée, et le journal le dit.

Personnaliser une feuille. On ne modifie pas les TEI Stylesheets : on les surcharge dans une feuille du projet. Dupliquez un scénario TEI (Dupliquer…), puis choisissez la copie et Ouvrir la feuille : Varians propose de créer dans xslt/ une feuille de personnalisation, par exemple xslt/tei-html.xsl (Créer la feuille de personnalisation), que le scénario emploie ensuite. Elle importe (xsl:import) la feuille du TEI-C par son adresse officielle, http://www.tei-c.org/release/xml/tei/stylesheet/…, que Varians lit dans les TEI Stylesheets installées, sans réseau ; Oxygen fait de même, et la feuille y reste valable. Les paramètres (xsl:param) et les règles (xsl:template) que vous y écrivez l’emportent sur ceux qu’elle importe ; tout le reste vient des TEI Stylesheets. Par exemple :

<xsl:stylesheet version="3.0" xmlns:xsl="http://www.w3.org/1999/XSL/Transform"
    xmlns:tei="http://www.tei-c.org/ns/1.0" xmlns="http://www.w3.org/1999/xhtml"
    exclude-result-prefixes="#all">
  <xsl:import href="http://www.tei-c.org/release/xml/tei/stylesheet/profiles/default/html/to.xsl"/>
  <!-- Pas de numérotation des titres. -->
  <xsl:param name="numberHeadings">false</xsl:param>
  <!-- Les noms de personnes en gras. -->
  <xsl:template match="tei:persName"><b><xsl:apply-templates/></b></xsl:template>
</xsl:stylesheet>

Pour une sortie HTML, xmlns="http://www.w3.org/1999/xhtml" fait des éléments ajoutés (ici <b>) du XHTML, comme ceux des TEI Stylesheets. La feuille de personnalisation s’édite, se vérifie (F8) et se complète comme toute feuille : voir Éditer une feuille XSLT. Une mise à jour des TEI Stylesheets ne la touche pas : elle continue de s’appliquer.

Mises à jour. Le TEI-C publie environ deux versions par an. Au lancement, Varians vérifie au plus une fois par mois, sans bloquer la fenêtre, si une nouvelle version est publiée ; s’il n’y en a pas, ou sans réseau, rien n’est dit. Sinon, il propose de l’installer : Installer ou Plus tard (la question revient à la vérification suivante). L’installation montre sa progression et peut être annulée ; une archive incorrecte ou une annulation laissent la version installée. La nouvelle version sert dès la transformation suivante, pour tous les projets ; l’ancienne est supprimée au lancement suivant. Fichier → TEI Stylesheets…, ou le bouton TEI Stylesheets… de la liste des scénarios, montre la version installée, son origine, son dossier, sa licence et la date de la dernière vérification ; Rechercher une mise à jour vérifie aussitôt. Une seule version est installée : une publication refaite après une mise à jour peut différer de la précédente, et le journal donne la version.

Licence. Le TEI Consortium distribue les TEI Stylesheets, au choix, sous la licence BSD à deux clauses ou sous la licence CC BY-SA 3.0 ; le fichier LICENCE est installé avec elles (Voir la licence).

Limites. Le LaTeX se compile en PDF avec une installation de TeX (xelatex), hors de Varians. En texte et en Markdown, les TEI Stylesheets écrivent le lemme et la variante à la suite : une feuille de personnalisation peut changer ce choix du TEI-C. En DOCX et en ODT, l’apparat est numéroté 1, 2, 3 en bas de page, et les notes de l’éditeur i, ii… en fin de document ; dans Word, les TEI Stylesheets ajoutent une espace après l’appel d’une note de fin. Les pages HTML n’emportent pas les images : leur adresse reste celle de la source.

Éditer une feuille XSLT

Une feuille XSLT est un document XML : Varians l’ouvre comme un document du projet, dans son propre onglet (voir Documents XML auxiliaires), la vérifie et aide à l’écrire, sans outil extérieur.

  • Ajouter une feuille : Fichier → Documents XML / XSLT du projet… → Ajouter un document XML, XSLT ou Schematron… accepte les fichiers .xsl et .xslt. Une feuille située hors du dossier du projet y est copiée, dans le dossier xslt/ (au même niveau que xml/), sans jamais remplacer un fichier existant ; une feuille déjà dans le projet reste où elle est.
  • Nouvelle feuille XSLT… (même menu) crée une feuille minimale, en XSLT 1.0 (lxml) ou en XSLT 3.0 (Saxon), proposée dans xslt/ : espace de noms TEI déclaré, sortie HTML, un modèle pour la racine du document.
  • Depuis les scénarios (voir Scénarios de transformation XSLT) : Ouvrir la feuille, dans la liste des scénarios ou dans la boîte d’un scénario (qui est alors enregistré), affiche la feuille d’un scénario du projet. Une feuille fournie avec Varians (${varians}/…) est d’abord copiée dans xslt/ ; une feuille hors du projet peut l’être aussi, ou s’ouvrir sans copie. Après une copie, le scénario emploie la copie. Pour un scénario prédéfini, utilisez d’abord Dupliquer…. Une feuille de Varians qui en inclut ou en importe d’autres (xsl:include, xsl:import) est copiée avec elles, sans remplacer un fichier déjà présent : edition-critique.xsl avec apparat-commun.xsl.

Vérification. Pour une feuille, Vérifier la feuille XSLT (F8, à la place de Valider RNG) la compile sans l’exécuter, avec le moteur des scénarios du projet qui l’emploient (les deux s’ils diffèrent) ; une feuille qu’aucun scénario n’emploie est vérifiée d’après sa version : version="1.0" par lxml, une autre par Saxon. Comme pour la validation RELAX NG, la feuille est vérifiée à son premier affichage, après chaque modification une fois F8 utilisé, et à l’enregistrement, qui demande confirmation si elle a des erreurs. Le panneau de validation donne chaque erreur avec sa ligne ; un double-clic y mène. Une erreur dans une feuille importée (xsl:import) ou incluse (xsl:include) nomme son fichier dans la colonne Document, et le double-clic mène à cette feuille si elle fait partie du projet. La barre d’état indique le résultat, et l’onglet de la feuille se colore comme celui d’un document non valide.

Complétion. Ctrl+Espace propose les éléments et attributs XSLT permis à cet endroit, avec le préfixe de la feuille (xsl:), et la liste des attributs s’ouvre pendant la frappe. Dans un élément du résultat (<div>, <tei:p>…), ce sont les instructions XSLT et les attributs xsl:*. Une feuille version="1.0" ne reçoit que les éléments et attributs d’XSLT 1.0. Les propositions viennent du schéma RELAX NG d’XSLT 3.0 du W3C, fourni avec Varians (licence BSD) ; les éléments personnalisés du projet (custom-elements.xml) ne sont pas proposés dans une feuille.

Fichiers annexes. Varians ne copie que la feuille elle-même. Les fichiers dont elle a besoin pour que le résultat soit complet (feuilles importées par xsl:import ou incluses par xsl:include, images, CSS, JavaScript…) sont à placer vous-même dans le dossier xslt/ du projet, en gardant les chemins relatifs qu’emploie la feuille. La vérification signale une feuille importée ou incluse introuvable. La CSS d’un scénario, elle, est copiée automatiquement à côté du résultat.

Limites : une feuille faite pour être importée ou incluse est vérifiée seule, et ses renvois à des déclarations de la feuille principale peuvent être signalés comme erreurs ; une feuille XSLT 2.0 reçoit les propositions d’XSLT 3.0 ; les noms déclarés dans la feuille (modèles, modes, clés) et les expressions XPath ne sont pas complétés.
