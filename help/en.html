1. Projects and startup

No project is opened on the first launch. Later, Varians may reopen the project that was active when the application was closed. File → Close project (Ctrl+W) returns to the welcome screen and prevents automatic reopening of that closed project.

File → New project… can use an existing TEI file or start a new transcription. The latter creates a minimal xml/edition.xml and builds a TEI <listWit> from the project witnesses. A witness may initially have no image, ALTO or synchronization; these resources can be added later.

Older projects with a root-level edition.xml remain supported.

Witness siglum and identifier. The siglum of a witness, entered in File → Project settings…, also serves as its XML identifier: the xml:id of its <witness>, the target of @wit and @edRef. An XML identifier starts with a letter or “_” and contains no space and no sign such as “/” or “:”. If the siglum entered is not one (“1760”, “T 2”), Varians derives a valid identifier from it, shown under the field: each forbidden character becomes “_”, and a “_” is added in front of a siglum that does not start with a letter; “1760” gives _1760, “T 2” gives T_2. In the TEI, you then write wit="#_1760". The siglum remains what Varians displays wherever it names the witness; it is kept in project.xml (siglum attribute of the <witness>) and, in the TEI created with the project, in an <idno type="siglum">:

<witness xml:id="_1760"><idno type="siglum">1760</idno>Troyes, ms. 1760</witness>

The stylesheets supplied with Varians (XSLT / CSS preview, Critical edition, apparatus in notes) and the web viewer show this siglum instead of the identifier. A witness added later, in File → Project settings…, receives a <witness> of the same form at the end of the edition’s <listWit>, if there is one: Varians does not create it. The box confirming that the settings were saved says what was added. Two sigla that would give the same identifier (“T 2” and “T/2”) cannot coexist.

2. XML editing and XSLT/CSS preview

XML source contains the TEI document. Visual line wrapping does not alter XML or logical line numbers. XSLT / CSS provides an editorial preview. Source and preview selections are synchronized when possible, including repeated occurrences of the same word within a passage.

The fragment editor lets you edit a restricted passage and apply it back to the main document.

Selections shared with the fragment editor. The pencil ✎ at the start of an element of the preview (a paragraph, a stanza, a heading…: see Editable elements) opens that element in the fragment editor without moving the witness images; a click on the text of the preview still synchronizes them. While the editor is open, a string selected in that element of the preview (by dragging the mouse or by a double-click) is also selected in the fragment editor, which takes the focus: the passage to correct is found at once. Conversely, a selection made in the fragment editor is selected in the preview, which scrolls to it; the focus stays in the editor. The same occurrence of a repeated word is found, including a word cut by a <lb break="no"/>. A selection in another element does not change the fragment editor: open that element with its pencil. Text typed in the fragment appears in the preview only after Apply to XML. Clicking the pencil keeps the current selection of the preview: if it lies in that element, it is also selected in the fragment editor. In the preview, F2 opens the element of the selection (or of the cursor) in the fragment editor, with the selection. An element that is already open and has unapplied corrections is not reloaded.

Editable elements. The pencil ✎ opens each block placed in a division of the <body>: any element of the TEI classes model.divPart (<p>, <ab>, <lg>, <l>, <sp>…) and model.inter (<list>, <table>, <quote>, <cit>, <bibl>…), as well as <head>, <figure> and <note>. An element contained in another element of this set has no pencil of its own: it opens with that element. So an <lg> has its pencil, its <l> elements do not; a <p> has its own, the <quote> or <note> it contains does not; a <note> placed between two paragraphs has its own. The classes are read from the project’s RELAX NG schema, as found by validation: an element added to these classes by an ODD customization is editable. Without a schema, or if the schema does not define these classes, Varians uses the TEI P5 4.10.2 list. Varians places the pencils itself, whatever XSLT stylesheet the view uses: the stylesheet needs nothing for them, and an element it does not display has no pencil. The editor label names the open element, for example “TEI fragment · <lg> 3/40”. The stylesheet shipped with Varians displays verse (each <l> on its own line), headings, lists and figures.

3. Markup assistance, RNG and custom-elements.xml

Ctrl+E wraps a selection in an element or inserts a new element at the cursor. In the list, an entry is highlighted only when you choose it (click, arrows, or Tab / ↓ from the field, which select the first one): Enter inserts the highlighted entry, otherwise the text typed in the field; typing again in the field clears the choice. Ctrl+Space completes element names, attributes and selected attribute values using the RELAX NG schema and custom-elements.xml. Suggestions are labelled according to their source.

Pointer lists such as @wit are completed token by token. The dynamic witnesses source can offer project identifiers such as #A1 and #B1.

Important: project completion aids never change RELAX NG validity. Full validation (F8) remains authoritative.

Validation results appear in a bottom panel. They are cleared when switching projects so diagnostics from an older document cannot remain visible.

4. XPath search

XPath (Ctrl+Shift+F) runs XPath 1.0 against the TEI. A simple expression such as //note is automatically retried in the TEI namespace when appropriate; advanced expressions can use the explicit tei: prefix.

Results show the source line, element, path and preview. From version 0.8.4.2, clicking a result selects the complete XML element, from opening tag through closing tag, even across multiple source lines. Self-closing elements are selected in full.

Scalar expressions such as count(//tei:note) display their value instead of an element list.

To check the critical apparatus, Help → Debug the apparatus… offers ready-made queries: see Debug the apparatus.

5. Tag pairs and safe formatting

Varians recognizes XML tag pairs. When the cursor is in an opening tag, the matching closing tag is highlighted. QName edits and full opening-tag deletion can be mirrored to the corresponding closing tag when the pairing is unambiguous.

Edit → Indent the XML formats structural regions conservatively while protecting mixed text. No new whitespace is introduced around <lb/>; xml:space="preserve" is respected; ambiguous or mixed content is left untouched. custom-elements.xml can use formatting="inline", block or preserve.

6. Witnesses, images, facsimile and pages

A witness may use no images, local JPEG/PNG/TIFF/BMP/WebP files, or an IIIF Presentation 2/3 Manifest. Local files may be copied into the project or referenced in place.

Image pages can be represented in TEI with stable <surface> identifiers:

<facsimile>
  <surface xml:id="A1-p0002" n="1v">
    <graphic url="../images/A1/002.jpg"/>
  </surface>
</facsimile>
Safety: Varians updates facsimile data incrementally. It does not blindly rebuild an existing <facsimile> or discard manually added zones and metadata.

Mark page inserts a page break for the currently displayed witness page:

<pb n="1v" edRef="#A1" facs="#A1-p0002"/>

If the cursor is inside any XML tag, the operation is refused; place the cursor in text or between tags.

7. ALTO and line synchronization

ALTO is optional and independent from image sources. It provides OCR text and page geometry, but ALTO alone is not a line synchronization. Without a real TEI-to-line alignment Varians stays in page mode and displays the whole current page.

Line mode is enabled only when synchronization is actually usable: reference lines for the pivot witness and real base_keys for secondary witnesses. Empty or provisional alignment JSON does not switch the interface to line mode.

8. Witness display

The View menu includes Reload images, Choose displayed witnesses… and the language submenu. You may display zero to any number of witnesses. The choice is stored locally per project and does not modify project.xml.

Witness panels use a vertical splitter and can be resized. Double-clicking a witness header temporarily maximizes that witness; double-click again to restore the previous proportions.

V0.8.5.16 — Visibility and display order. Open View → Choose displayed witnesses…, check the witnesses you want, select a row, and use Move up or Move down to arrange image panels from top to bottom. Hidden witnesses retain their list position. The choice is stored locally per project and survives restarting Varians; newly added witnesses are appended. It does not change the pivot witness, the alignment data, project.xml, or the generated web viewer order.

9. Web viewer

Generate web viewer builds a standalone output, normally under web_output/. Required local images are copied into the output package.

Without line synchronization the viewer uses page mode, with ← page and page → navigation. Clicking the edition text resolves the latest relevant <pb> independently for each witness. With usable line synchronization, line navigation is enabled instead. Projects with no images are exported without an empty facsimile column.

As in the window, the ← → arrows of every panel lead the text: the witness moves in its own order, and the text goes to the pivot line that its line designates, or to its <pb> for a witness followed by pages, whose folio list also leads the text; ⤺ brings the panel back to the linked line. The lacunae of the witnesses have their banners. For an edition in parts, see Web export of the assembled edition.

Reading text. The viewer reads every text of the edition: <front>, <body> and <back>, and each text of a <group>. A division is titled by its first <head>, otherwise by its @n; its @xml:id is not a title. Untitled front or back matter is titled “Front matter” or “Back matter”. The table of contents lists the titled divisions, indented under the titled division that contains them. Each <lg> is a stanza, each <l> on its own line, with its @n in the margin; a list keeps its sublists; a <table> is a table, with its caption, its header cells (@role="label") and its merged cells (@cols, @rows); a <note> placed between two paragraphs is a marker, hidden with the notes. As in “Critical edition (HTML)”, a <choice> shows one form (correction, regularization, expansion), the other in a tooltip; <del> is struck through, <add> underlined with dots, <supplied> in square brackets, and <gap> gives “[…]”, with its reason and extent in a tooltip. The readings of a <rdgGrp> count like the others. The text takes the language of its @xml:lang, which governs hyphenation.

10. Saving and safety

Ctrl+S saves the edition. XML well-formedness is checked automatically, compiled RNG schemas are cached, and important writes use atomic replacement and/or .bak safety copies where appropriate. Ambiguous automatic edits should be refused rather than silently rewriting editorial TEI.

ALTO, PAGE XML and local IIIF copies (0.8.5)

Witness layout formats

Open Project Settings → Witnesses → Edit → Layout transcription (ALTO / PAGE) and add XML files in page order. Varians detects the format of each file independently; ALTO and PAGE witnesses may coexist in one project, and a witness may contain both formats. Copy the files into the project for portability.

ALTO lines commonly have rectangular coordinates; PAGE line polygons (Coords/@points) and optional baselines (Baseline/@points) are retained exactly. Enable Frames to see their outlines. The PAGE transcription comes from each line's TextEquiv/Unicode, falling back to words if needed. Importing layout files does not automatically align them to TEI <lb> elements; synchronization is a separate resource.

IIIF download manager

Under Project Settings → Witnesses → Edit, enable the local working copy and choose All pages in the manifest or Only pages with matching ALTO or PAGE files. The choice belongs to each witness. For selective downloads, declare its ALTO/PAGE files first. Varians compares image filenames, page labels and folio numbers with IIIF canvases. File order alone is never used. Ambiguous or unmatched pages are skipped and reported, never silently mapped to a different image.

The separate download manager starts after saving project settings without blocking editing. Reopen it using File → IIIF Download Manager…. It shows all, selected, cached, pending and excluded page counts. Download missing resumes without downloading completed files again; Refresh selection forces new downloads. Pause, Resume and Stop take effect between images; a request already in progress may continue until its network timeout. Closing the manager hides it without cancelling the job.

Downloaded files stay in iiif/local/<witness>/ and become usable in the editor at the end of the operation without reopening the project. Pages not cached still use remote URLs: selective copies therefore do not make the entire manuscript available offline. The web export switch remains independent; only images actually cached can be packaged.

Independent web viewer setting

Use Use the local copy when generating the web viewer to package available cached images into web_output/images/. Uncheck it to keep original remote IIIF requests even when Varians itself works locally. An exported viewer with missing local pages may still need Internet access. Check the holding institution's image rights and licensing conditions before redistributing images.

Explicit IIIF image selection and local OCR linking (0.8.5.4)

In Project settings → Witnesses → Edit, select “Only images selected for the edition”, then “Choose images and link OCR files…”. The manifest remains a catalogue; only checked canvases become editorial images. Filter the folios, select or clear visible rows, and use Preview to inspect a remote IIIF image.

Varians automatically suggests a IIIF canvas / ALTO–PAGE association when the image basenames match exactly (ignoring extensions). It also checks the source image filename recorded inside the OCR XML, even if the XML file was renamed. Ambiguous matches are not applied and existing manual choices take precedence. Use “Match automatically (exact names)” to fill empty links; any suggestion can be changed or removed. No matching by file order or approximate folio labels is performed.

After importing local ALTO/PAGE files, link each selected canvas to the correct OCR file in the last column. Names need not match. Manual linking currently requires one OCR file per image; the same OCR file cannot be assigned to multiple canvases.

In the download manager, “All pages” now means all selected editorial pages when this mode is active. “Pages with ALTO/PAGE” further limits the download to pages with OCR correspondence. Unselected canvases generate neither downloads nor new TEI surfaces. Surface IDs retain their original manifest positions.

Existing TEI surfaces and previously cached images are not deleted automatically, to preserve editorial annotations and references. Inspect unused existing surfaces before removing them manually. Newly imported local images and ALTO/PAGE files use natural filename order (1r, 1v, 2r, etc.); “Natural sort” reapplies this to an existing list without preventing manual adjustments.

Synchronized pages and IIIF Canvases (0.8.5.6)

For an IIIF witness, import the JSON exported by Varians-Synchro, then open Choose images and link OCR…. The JSON retains its own page and line identifiers; the IIIF selection determines which images are shown, even when the manifest contains hundreds of Canvases.

Varians resolves each page using an exact Canvas ID, the IIIF Image service, a carefully normalized image URL, a reliable ALTO/PAGE link or an unambiguous folio label. Exactly matching file names are linked automatically. Where no certain link exists, use the new Synchronized page column to select the JSON page for a Canvas. The position in a list is never used as identity evidence. Manual choices take precedence and are saved in project.xml.

The Local copy and Link status columns show whether a downloaded file exists, how a link was established and which image source is preferred. Offline viewing requires an available local copy; otherwise the IIIF service remains the fallback. Ambiguous matches are never chosen arbitrarily. Only selected editorial Canvases generate new TEI surfaces; existing surfaces are not silently deleted.

Prepare a blank TEI transcription from the pivot witness

In New Project or Project Settings, enable pivot-witness <pb/> preparation and optionally <lb/> generation. Only selected editorial pages receive a <pb/>; @facs points to the <surface> and @edRef identifies the witness. Generated <lb/> markers have @edRef but no @n and no automatic link to image zones. Varians first counts unambiguously linked ALTO/PAGE lines; otherwise it counts physical lines actually listed in the synchronization JSON, even when numbering starts at 41 or later. Missing lines are reported, not invented. A selected page with no described lines still receives its <pb/>. Preview, explicit confirmation and a dated backup safeguard existing content; OCR text is not inserted.

When synchronization selects a line near a column or page boundary, Varians no longer adds context lines belonging to a different column or page to the image crop. The crop stays focused on physically adjacent lines. Line numbers, JSON alignments and synchronization keys are unchanged. Use “Page ↗” to open the full image.

Synchronized line outlines (0.8.5.10)

The “Frames” button is independent for each witness and its active state is now clearly visible. Orange outlines indicate synchronized lines; blue marks a line selected manually without implying an editorial alignment. When one base line maps to several distinct lines in a secondary witness, Varians always centers on an actual matching line, including at column boundaries. PAGE polygons are rendered as polygons; classic ALTO lines are generally rectangular. A diagnostic appears if geometry is missing. The generated web viewer currently uses rectangular highlights.

Mixed navigation: pages and lines per witness (0.8.5.11)

An edition can now combine witnesses synchronized at line level with an image-only witness. Each manuscript panel follows its own synchronization level. Witnesses with usable synchronization JSON continue to follow the pivot’s <lb/> milestones and base_keys; an unsynchronized witness follows its own <pb/> milestones, using @edRef and the @facs link to a <surface>. When @facs is absent, @n may identify the page if and only if its label is an exact, unique match. Image order is never used as a substitute. Page markers from one witness do not move other witnesses. This also applies to formatted-text navigation, line-panel navigation and line selection in the generated web viewer.

V0.8.5.12 — Multiple witnesses. The image-panel column now scrolls vertically without squeezing the fourth witness. The “pivot witness” is the technical synchronization anchor, not an editorial copy-text. When <pb/> lacks @facs, pages are resolved by the @edRef + @n pair: different manuscripts may share the same folio number.

Closing-tag completion

In both the XML source editor and the fragment editor, typing </ suggests the nearest still-open element. For instance, after <div><p>…</p></, Varians suggests div>: press Enter or Tab to insert </div>. You can also type a prefix such as </di. Esc dismisses the suggestion without changing the text; Ctrl+Space requests it again. Qualified names such as tei:div are preserved. Self-closing elements (<lb/>), comments, CDATA and incomplete attributes are not mistaken for open elements. If nesting is ambiguous, no closing tag is guessed.

IIIF images and ALTO/PAGE added later (0.8.5.14)

Adding ALTO or PAGE files to an unsynchronized IIIF witness no longer removes its images. Selected canvases remain authoritative, including when local working copies exist. OCR geometry is attached only when an exact canvas identity, manual link, unambiguous folio label, or the exact local image copy proves the correspondence. Unmatched OCR pages are retained in the derived cache; their count is shown in the witness tooltip. They are never assigned an image or crop by position. To link them, open the witness settings and choose « Select images and link OCR… ». The synchronization JSON and TEI remain unchanged.

Line synchronization and IIIF image quality (0.8.5.15)

ALTO/PAGE outlines alone do not prove line-level synchronization. If a witness JSON contains no base_keys links to the pivot witness, Varians reports this and keeps page navigation. It also reports links that match no pivot lines. When an IIIF Image API service is available, the editor requests a full-resolution image instead of a preview provided by the manifest, retaining the preview as fallback. Frames are scaled to the actual displayed bitmap even when a local copy is smaller than its Canvas. The zoom percentage is relative to automatic fit, not an indication of file resolution.

Auxiliary XML documents

Besides the edition, a project can bring together other XML documents: an authority file (persons, places), notes, etc. Use File → Project XML / XSLT documents…. Add an XML, XSLT or Schematron document… declares an existing file; a file located outside the project folder is copied into xml/, never replacing an existing file. New XML document… creates an empty document whose root element you choose. Remove the document from the project removes the displayed document without deleting its file.

As soon as an auxiliary document exists, a row of tabs appears above the XML source: Edition, then one tab per document. Each document keeps its own undo history, position and state; an asterisk marks unsaved changes, and the colour of the name a malformed or invalid XML. RELAX NG validation and completion follow the <?xml-model?> of the displayed document. The manuscripts, the XSLT / CSS view and the witness commands concern the edition only: they are hidden while another document is displayed, then restored unchanged. Ctrl+S saves the displayed document; before quitting or changing project, Varians offers to save every modified document. The web export uses the edition only.

Displayed tabs. View → Choose displayed documents… lets you choose which documents have a tab, and the order of the tabs. Right-clicking a tab offers Hide tab, Rename tab…, Choose displayed documents… and Remove the document from the project, for the document of that tab, even when it is not displayed. A hidden document stays in the project: its changes are kept, and Varians offers to save them before quitting. Its tab reappears when a reference leads to it (F12, Ctrl+click, double-click in the References panel). The last visible tab cannot be hidden; when the project opens, the edition is displayed, with its tab. These choices are saved locally for the project and do not change project.xml. The name given with Rename tab…, however, is written to the label attribute of the <document> in project.xml; an empty name restores the file name. When the tabs no longer fit in their row, an arrow ▾ (“All tabs”) appears on its right: it drops down the list of all the tabs, with the displayed document’s tab checked; a click shows the chosen document. The list ends with Choose displayed documents….

The documents are declared in project.xml by a <documents> element; a project without auxiliary documents is unchanged. An earlier version of Varians opens such a project normally, but erases this list if the project settings are saved there.

References between documents

A pointer attribute (@ref, @corresp, @target, @who, @wit, @edRef, @sameAs, @ana, @resp, @source, @hand, @facs, @prev, @next, @synch, @copyOf) designates an element by its @xml:id. As in standard TEI, and therefore for every XML tool, the short form #bernard designates an element of the document itself. To point to another document of the project (see Auxiliary XML documents), write personnes.xml#bernard, with a path relative to the document containing the reference. Web addresses (https://…) and values without “#” are not processed. A value may contain several pointers separated by spaces: wit="#T1 #T2".

Typing. In the value of such an attribute, type #: the list of identifiers opens by itself, with the text of each entry and its file, for example “personnes.xml#bernard — Bernardus”. The following letters filter the list; Enter or Tab inserts the value; Esc closes the list. For @wit and @edRef, the list offers the witnesses described in the TEI (<witness> of the <listWit>). Ctrl+Space opens the same values in a dialog (“Project identifiers”) where the filter also applies to the descriptions: “Bern” finds personnes.xml#bernard. The identifiers offered depend on the element: persName/@ref offers person, personGrp and persona; placeName/@ref offers place; orgName/@ref offers org; @who offers persons. Elsewhere, every identifier is offered. In custom-elements.xml, <values source="ids" elements="person personGrp" prefix="#"/> sets this list for an attribute. An identifier of another document is inserted as file.xml#id, an identifier of the document itself as #id.

Navigation. On a reference, press F12, Ctrl+click, or choose Go to target in the right-click menu: the document containing the target is displayed, with the element selected. If the identifier is defined more than once, Varians asks which target to display. Alt+← (or Go back in the right-click menu) returns to the starting point, even from another document. A target that cannot be found is reported in the status bar. On a short form whose target is only in another document, Varians goes there too and gives the form to write.

Checking. The Edit → References command checks the references of every document of the project. The panel that opens below the source gives their number and lists those with a problem: target not found, short form whose target is in another document (with the form to write), ambiguous target (identifier defined more than once in the target document) or file not found, with the columns Document, Line, Attribute, Value and Problem. A double-click goes to the reference. After a correction, Check again runs the check again. This check is an aid: it never prevents saving and modifies no file.

Debug the apparatus

Help → Debug the apparatus… offers ready-made XPath queries to find errors in the critical apparatus of the displayed document, encoded in parallel segmentation: each <app> groups its readings (<lem>, <rdg>, including inside a <rdgGrp>), whose @wit cites the witnesses as #A. The witnesses are those of the document’s <listWit>.

  • Witness cited more than once: the same witness appears in two readings of an <app>, or twice in the same @wit; its reading is ambiguous.
  • Incomplete <app>: a witness has no reading. For a top-level <app>, all witnesses of the <listWit> are expected; for a nested <app>, those of the reading that contains it. A <lem> without @wit is deemed to cover the witnesses missing from the <rdg>: its <app> is not reported.
  • <app> without <lem>: the <app> that have no <lem>; a <lem> inside a <rdgGrp> of the <app> counts. This search does not depend on the witnesses: it remains available without a <listWit>.
  • Given witness: the <app> where a witness chosen from the list appears, or does not appear, in <lem> or <rdg>, or in <rdg> only.
  • My queries: your own named XPath queries, for checks specific to your encoding. Add… proposes the current query of the XPath panel; Edit… and Delete manage them. They are saved in project.xml (<xpathQueries> element) and travel with the project.

Search runs the query in the XPath panel: clicking a result selects the <app>. The query stays in the XPath field: it is plain XPath 1.0, with the tei: prefix, which can be copied into other XML tools. It may be long, since it has one condition per witness.

Limits: witness groups (a <listWit xml:id="…"> cited in @wit) are not expanded; a witness cited but missing from the <listWit> is reported by the Edit → References command; if some witnesses of the <listWit> are not collated in the apparatus, every <app> looks incomplete.

RELAX NG validation without waiting

Since version 0.8.9.2, RELAX NG validation runs in a separate process, which Varians starts when first needed. At the first validation after launch, compiling a large schema such as TEI_ALL takes about ten seconds; meanwhile the window remains usable and a small glow turns next to RNG: validating… in the status bar. The compiled schema is then kept for the whole session, even when another project is opened.

Automatic validation (opening, switching documents, editing) never interrupts your work. Validate RNG (F8) and saving, however, wait for the result: the window keeps being drawn, but clicks and key presses are ignored until the answer arrives. Saving during the first compilation therefore waits for it to finish, then warns as usual if the document is not valid.

If the validation process cannot be started, Varians validates by itself, as before, and says so once in the status bar; the window may then freeze during the compilation. Downloading a remote schema, the very first time it is used, still happens inside Varians.

Schematron rules

A RELAX NG schema says which elements and attributes are allowed, and where. Schematron rules check what it cannot express: for example, in TEI, that an <lg> contains at least one line, or that @target and @cRef are not used together. Since version 0.9.2.3, Varians applies them together with the RNG: on opening, while typing, with Validate RNG (F8) and on saving, in the same separate process (see RELAX NG validation without waiting).

Which rules. First those embedded in the RELAX NG schema used, whether declared by the document or chosen in the project settings: tei_all.rng contains 91 groups of them, an ODD customization its own. Then those of each Schematron declaration of the document, to a .sch file or an RNG:

<?xml-model href="regles.sch" type="application/xml"
    schematypens="http://purl.oclc.org/dsdl/schematron"?>

A relative address starts from the document; an http address is downloaded once, then kept in the schema cache. The same rules are never checked twice: the Schematron declaration of TEI documents designates the same tei_all.rng as their RNG. New projects receive both declarations. For an edition in parts, the rules apply to the assembled edition, like the RNG.

XSD schema. An XSD schema declared as Schematron (same schematypens) gives the rules it embeds in its xs:appinfo, including those of the files it includes or imports (xs:include, xs:import). Varians does not validate the document against the XSD itself.

Phases. A Schematron file can group its patterns (sch:pattern) into phases (sch:phase). Unless told otherwise, Varians checks the default phase of the file (defaultPhase), otherwise all its rules. To choose a phase, add the standard phase attribute to the declaration, as in Oxygen:

<?xml-model href="regles.sch" type="application/xml"
    schematypens="http://purl.oclc.org/dsdl/schematron" phase="lecons"?>

#ALL checks all the rules, #DEFAULT the default phase. A phase that does not exist in the file is an incorrect rule (see below), given with the list of the phases of the file. Without writing the declaration yourself: clicking the Schematron label of the status bar, or the Rules… button of the validation panel, opens the Schematron rules of the document dialog. For each declared rules file, it offers the phase in a list (the default phase, all the rules, the phases of the file); it also adds or removes a declaration. The changes are written in the <?xml-model?> declarations of the document, and Ctrl+Z undoes them.

Messages. They are added to those of the RNG in the RELAX NG and Schematron validation panel: the Origin column says Schematron, and double-clicking leads to the line of the element concerned (for a rule on an attribute, that of its element), in its document. The level comes from @severity, otherwise from @role: warning, warn or nonfatal give a Warning, info an Information, anything else an error. An error makes the document invalid, like a RELAX NG error: tab name in orange, and the question Document is not valid before saving (Save anyway). A warning or an information stays in the list, without making the document invalid.

Status bar. Next to the RNG state, the Schematron label sums up the result: Schematron: ✓, the number of errors or messages, or Schematron: not checked when validation is disabled for the project. Its tooltip names the files of the rules applied, with their phase: “apparat.sch (phase lecons)”. Clicking the label opens the Schematron rules of the document dialog.

Incorrect rules. A faulty XPath expression, an unknown phase, or a rules file that cannot be found or is malformed, give Schematron: incorrect rules. Each incorrect rule has its row in the panel, after the messages of the document: origin Schematron (rules) and, in the Document column, the rules file. Double-clicking shows this file at the line of the rule; a file of the project folder that is not yet a project document can be added to them (Varians offers to); a file outside the project, such as the copy of a remote file in the cache, does not open, and the status bar says so. The schema is at fault: the document does not become invalid, and the other rules are applied. When a rules file has been changed and saved, the document is validated again as soon as you return to it.

Writing the rules in Varians. File → Project XML / XSLT documents… → Add an XML, XSLT or Schematron document… accepts .sch files; a file outside the project is copied into its xml/ folder. New Schematron file… creates a minimal file (xml/regles.sch is offered), which declares the tei prefix and contains an example rule; then add its declaration to the document. A displayed Schematron file is checked instead of the RELAX NG validation: Check the Schematron rules (F8), on display, while typing once F8 has been used, and on saving. The check concerns the displayed text, even unsaved: well-formedness, structure according to the ISO Schematron schema (provided with Varians), included files, then compilation of all the phases by Saxon; each error is given at its line, and double-clicking leads to it. Ctrl+Space and the automatic list of attributes offer the Schematron elements and attributes, with the prefix of the file, and common values for severity, role and queryBinding. The document is validated with the displayed text of an open rules file, even unsaved: returning to the document after changing its rules validates it again, and the tooltip of the Schematron label says so (“regles.sch, unsaved”). The same goes for a file it includes (sch:include, sch:extends), open and changed: the tooltip names it (“regles.sch (unsaved: motifs.sch)”), and the check of the rules file takes it into account, again when you return to that file. The novelties of the 2020 and 2025 editions of the standard, which SchXslt2 applies, are accepted and offered by the completion: sch:group, sch:rules, sch:library, schema-level sch:param, @visit-each, @from and @when of phases.

Engine. Varians uses SchXslt2 (David Maus, MIT licence), shipped with it, and Saxon (the saxonche package, installed by installer_dependances.bat, as for transformation scenarios). Without Saxon, the label shows Schematron: Saxon missing and only RELAX NG validation is done. The rules are prepared in less than a second when first checked, then kept for the session, and prepared again if their file changes.

Limits. The rules are evaluated in XPath 3.1, whatever their queryBinding: a rule written for XPath 1.0 almost always behaves the same. For the 2020 and 2025 editions, whose schema is not freely available, the check of a .sch file follows what SchXslt2 accepts. The former Schematron 1.5 is not supported, nor validation against an XSD.

Witness lacunae

The passage a witness lacks (a lost leaf, a text that breaks off) is enclosed, in TEI, by <lacunaStart/> and <lacunaEnd/>. The TEI places these elements inside a reading: the witness is that of the <rdg> (or <lem>) containing them or, in a reading of several witnesses, that of their own @wit:

<app><lem wit="#T1 #P"/><rdg wit="#T2"><lacunaStart/></rdg></app>
…
<app><lem wit="#T1 #P"/><rdg wit="#T2"><lacunaEnd/></rdg></app>

<rdg wit="#T2 #P">… <lacunaStart wit="#P"/></rdg>

Varians also recognizes these elements outside a reading, with @wit, but TEI validation reports them there as errors.

In the panels. When the cursor is in a lacuna of a witness, its panel keeps the line (or, for a witness followed by pages, the page) where its text breaks off, with the banner “Lacuna in this witness: its text breaks off here.”. When the cursor is in a lacuna of the pivot witness, the witnesses synchronized by lines stay on the last line of the pivot, with the banner “Lacuna in the pivot witness: lines are not synchronized in this passage.”; the status bar says so too. Witnesses followed by pages keep following their <pb>, which do not depend on the pivot.

Debug the apparatus. The check “Incomplete <app> (a witness has no reading)” expects no reading from a witness within its lacuna.

A lacuna without <lacunaEnd/> runs to the end of the text. In an edition in parts, a lacuna may begin in one part and end in another; in a text synchronized separately, only the lacunae of that text count. The web viewer shows the same banners.

Following a manuscript in its own order

The ← and → arrows of every witness panel lead the edition: the witness moves forward or back in its own order, and the edition cursor goes to the corresponding passage, displaying the part or text that contains it if needed. The other witnesses follow the pivot, as when the cursor moves. When an auxiliary document is displayed, the arrows only browse the witness.

Witness synchronized by lines. The panel moves to the next line of the witness; the edition goes to the pivot line that this line designates. A line not linked to the pivot leaves the edition on the linked line that precedes it, and the status bar says so. The ⤺ button brings the panel back to the line linked to the pivot’s.

Witness followed by pages. The arrows and the folio list lead the edition to the chosen page: to the witness’s first line on that page in one of its JSON files, otherwise to the end of its <pb edRef="#M" n="45v"/>, otherwise to the start of the text whose <locus from> for the witness is that page. Without any of these landmarks, the edition does not move and the status bar says so.

From one text to the next. At the end of a text, the arrows go on to the next text in the manuscript, whether it follows the continuous numbering or is synchronized separately. The pivot panel does the same: a pivot shared by several texts is read in one go. A page carrying the end of one text and the beginning of another stays displayed. The panel of a witness absent from the displayed text (“No alignment of this witness for this text.”) leads, with its arrows, to the next or previous text that has this witness, in the order of the edition.

Order of the texts in a manuscript. Varians deduces it from the witness’s pages:

  • the place of the pages in the witness’s declared image list (IIIF manifest or files, in File → Project settings…);
  • otherwise, the pages its JSON files share: each JSON is already in the order of the manuscript, and a page carrying the end of one text and the beginning of another links them;
  • otherwise, the witness’s <locus from> for the text, or the foliation of the text’s first page (a number followed by r or v), compared with that of the other pages;
  • otherwise, the text keeps its place in the order of the edition, and Varians reports it.

View → Witness diagnostics… gives the order of the texts in each manuscript present in several texts, and reports an uncertain place. To make it certain, declare the witness’s images, or add a <locus from="80r" target="#s04"> to its <witness>.

Leading the edition or browsing. The open-book button, just after ← → ⤺, decides whether the arrows of a manuscript lead the edition. When pressed (blue-grey background), the arrows and the folio list of this manuscript also move the cursor in the edition, as described above; when released, they only browse the manuscript, without touching the edition. By default, only the pivot witness’s button is pressed. The panel still follows the edition when the cursor moves there. The state of each manuscript is remembered for the project, without changing project.xml.

Assembled editions (XInclude)

To set up such a project step by step, see the guide.

An edition can include its parts, for example one file per sermon, following the XInclude standard. The edition declared in project.xml remains the master document; its parts are deduced from its xi:include elements, with no other declaration:

<TEI xmlns="http://www.tei-c.org/ns/1.0"
     xmlns:xi="http://www.w3.org/2001/XInclude">
  …
  <body>
    <xi:include href="sermons/s01.xml"/>
    <xi:include href="sermons/s02.xml" xpointer="s02"/>
    <xi:include href="sermons/s03.xml" xpointer="element(/1/2/1/1)"/>
  </body>

A part is either a fragment (the whole file, whose root is for instance the sermon’s <div>) or an element of a complete TEI document, designated by xpointer: its identifier (s02 or element(s02)) or its path (element(/1/2/1/1): TEI, then its 2nd child text, then body, then the first div). A part can itself include other parts. Relative paths written in a part start from the part’s folder.

Parts and tabs

Each part has its own tab, named after its file, after the edition’s tab and in inclusion order. It is edited and saved on its own (Ctrl+S), with its own undo history; before quitting, Varians offers to save the modified parts. The list of parts is read again each time the edition or a part is saved. “Rename tab…” and “Remove the document from the project” only concern auxiliary documents. The XSLT / CSS view stays open while a part is displayed: it shows the whole edition (see XSLT / CSS view of the assembled edition); the witnesses stay displayed too (see below). Saving the edition in another folder would break the paths of its xi:include elements: Varians warns you first.

Validation

The edition and each of its parts have the assembled edition validated, with the edition’s schema and taking the unsaved changes of the parts into account. The RELAX NG panel then adds a Document column; double-clicking an error opens the right part at the right line. The tab of each part takes the colour of its own errors. A missing or malformed part, a circular inclusion or an unsupported form (parse="text", xi:fallback, another xpointer scheme) is reported at the line of its xi:include.

References and witnesses

The edition and its parts form a single document: a #id is first looked for in the file that contains it (header included), then in the other parts. F12, the References command and completion take this into account. Only the identifiers of the included element of a part belong to the assembled edition: a witness declared only in the <teiHeader> of a sermon included by xpointer is found by Varians in that sermon, but a tool that reads only the assembled edition will not see it. In a part, Help → Debug the apparatus… uses the part’s own witnesses: its <listWit>, otherwise the witnesses of the edition whose <locus target="#s01"> points to the part, otherwise those cited by its @wit attributes.

Witness synchronization

When the edition is split into files for convenience (a collection whose texts follow one another as in the pivot witness), the witnesses are synchronized as for an edition in a single file: the pivot lines (<lb edRef="#A"/>) are counted in the order of the assembled edition, from one part to the next, and the alignment files stay the usual ones, one per witness for the whole edition. The cursor of the edition or of a part moves the witnesses; a click or scrolling in the pivot puts the cursor in the part that contains the line and opens its tab, even after “Hide tab”. The structure status (status bar) counts the pivot lines in the whole assembled edition, and saving the edition or a part warns if this number differs from the pivot alignment. An <lb/> placed in a comment or outside the included element of a part does not count, as in other XML tools.

Condition: the pivot must contain these texts in the order of the edition. Varians checks the number of lines, not their order. The other witnesses may have another order or lack a text: their alignment already points to pivot lines. A witness synchronized by pages follows the last <pb> that concerns it, in the order of the edition, even in a previous part: if this witness has the texts in another order, mark its page at the start of each text.

From a part, “Mark page” inserts the <pb> in the part, at the cursor, and completes the <facsimile> of the edition; “Two-page spread…” writes its zones in the <facsimile> of the edition. The edition is then modified without being displayed: its tab shows “*”. Undoing in the part removes the <pb>, not what was added to the <facsimile>.

Texts synchronized separately

In a corpus whose texts are not transmitted by the same witnesses, nor in the same order, a text can have its own alignments: one JSON per witness, in the usual format, in a folder named after the text’s file, without extension (alignments/s02/B.json for xml/sermons/s02.xml). Nothing has to be declared: a text that has its folder is synchronized separately; the others follow continuous numbering. A text’s pivot is the project pivot, unless an exception is declared in project.xml: <part name="s02" base="B"/>.

When such a text is displayed, the witness panels take its alignments and its pivot; layout, zoom and detached windows do not change. A witness without a JSON for this text keeps its panel, which says “No alignment of this witness for this text.”. Lines are counted in the text alone (for instance “B: 8 lines ✓”); a click in the pivot stays in the text. Witness diagnostics and synchronization refresh apply to the displayed text.

Witnesses followed by pages. A witness that has no JSON for this text but does have the text — a <pb edRef="#C"/> in the text, or a <locus target="#s04"> in its <witness> of the <listWit> — follows its pages there. Before its first <pb> in the text, it shows its starting page: the @from of that locus (<locus from="13r" to="14r" target="#s04">), otherwise the page preceding that of this first <pb>, in the witness’s own page order. “Mark page” works there too. The witness diagnostics name, for each text, its witnesses followed by pages. Other witnesses without a JSON keep the absence message.

XSLT / CSS view of the assembled edition

The XSLT / CSS view shows the whole edition, parts included, whatever document is displayed, and is used as for an edition in a single file. Switching from the edition to a part does not leave it; only displaying an auxiliary document closes it.

  • Fragment editing. The pencil ✎ of an element opens it in the fragment editor, as it is written in the file that contains it; the label names this file, for example “TEI fragment · <p> 10/16 · s03.xml”. The applied fragment is written into this file, even if it is not displayed or has never been opened: its tab then shows “*”, and a single undo, in the part, removes the change. The file must remain well formed. Ctrl+S in the fragment editor saves this file, then the displayed document if it is modified; before quitting, Varians offers to save an unapplied fragment with its file.
  • Click, table of contents, search. A click on a line places the cursor at this line, in the file that contains it, whose tab opens, without leaving the preview; the witnesses follow, with the own numbering of a text synchronized separately. The table of contents and the search in the preview do the same.
  • Selections. A string selected in the preview is selected, when you return to the XML source tab, in the file that contains the text (a part, or the edition), at the same occurrence of the same paragraph; without a selection, the cursor goes to the displayed line. Conversely, the selection or position of a part is found in the preview. Between the preview and the fragment editor, selections follow each other as for an edition in a single file.
  • Limits. A paragraph that itself contains an xi:include is edited in the file of its tag; the included text is edited in its part. As for an edition in a single file, a paragraph or a line that the XSLT does not render shifts the pencils or line markers that follow it.

Web export of the assembled edition

Generate web viewer exports the whole edition, parts included, with the continuities of the window.

  • Text and lines. The text of the parts is in the viewer, and the pivot lines are counted from one part to the next, as in the window. A text synchronized separately keeps its pivot and its JSON files (alignments/s02/): when the chosen line enters it, each panel shows its witness in that text, by its lines, by its pages from its start page, or with “No alignment of this witness for this text.” The zoom and the frames of each panel are kept from one text to another. The header buttons go through every line in reading order, from one text to the next.
  • Panel arrows. As in the window, the ← → arrows of every panel lead the text in the manuscript’s own order, from one part or text to the next, and so does the folio list of a witness followed by pages; ⤺ brings the panel back to the linked line. The messages of the window’s status bar (start or end of the manuscript, unlinked line, unplaced page, uncertain place) appear under the viewer’s title.
  • Lacunae. The banners are those of the window (see Witness lacunae): a lacuna continues from one part to the next, and a text synchronized separately starts without a lacuna.
  • Saving. The export reads the saved files: Varians first saves the edition, every modified part and the unapplied fragment of a part; if one of them cannot be saved, the export is cancelled. A part that cannot be found, or an unsupported inclusion (parse="text", xi:fallback), is reported in the export summary: the text concerned is missing from the viewer.
  • Limits. The position used is that of the clicked text fragment. A <pb> or <lb> placed in a reading that is not retained, or in a note, is not seen by the viewer. “Witness diagnostics…”, “Refresh synchronization…”, “Mark page” and “Two-page spread…” remain specific to the window. Generate the viewer again after changing the edition.

The web export has its own limits: see Web export of the assembled edition. A project without xi:include is not affected.

Setting up an edition in parts (XInclude): guide

This guide describes, step by step, how to organize a project whose edition is split into several files, for instance one file per sermon. Each function is detailed in Assembled editions (XInclude).

1. Organize the files

Keep a single edition file, the one declared in project.xml (for instance xml/edition.xml): it is the master document, with the header, the list of witnesses and the order of the texts. Put the texts in a neighbouring folder, one file per text. Give each file a name that is unique in the whole project: this name, without extension, is also used for the alignment folder of a text synchronized separately (step 4). Paths are relative to the file that contains them: sermons/s01.xml from the edition, ../personnes.xml#augustinus from a sermon.

project.xml
alignments/T1.json, T2.json …
alignments/s02/B.json, D.json
xml/edition.xml
xml/sermons/s01.xml, s02.xml, s03.xml …

2. Write the xi:include elements

Declare the XInclude namespace on the root element of the edition, then put an xi:include where each text goes:

<TEI xmlns="http://www.tei-c.org/ns/1.0" xmlns:xi="http://www.w3.org/2001/XInclude">
  …
  <body>
    <xi:include href="sermons/s01.xml"/>
    <xi:include href="sermons/s02.xml" xpointer="s02"/>
  </body>
</TEI>

A text is either a fragment: the whole file, whose root is the included element and carries the TEI namespace (<div xmlns="http://www.tei-c.org/ns/1.0" xml:id="s01">); or a complete TEI document, of which only one element is included, by its identifier (xpointer="s02") or by its path (xpointer="element(/1/2/1/1)"). A complete document can also be validated on its own; its header does not enter the edition. A text can itself include another one. Do not use parse="text" or xi:fallback: Varians reports them without supporting them. Save the edition: each text gets its tab.

3. Declare the witnesses

Declare each manuscript only once, in File → Project settings…, with a siglum common to the whole collection. In the TEI, declare the witnesses in the <listWit> of the edition, in that of each text (complete TEI document), or in both. A witness declared only in the header of a text included by xpointer is found by Varians, but a tool that reads only the assembled edition does not see it.

4. Choose the synchronization of each text

  • The texts follow one another as in the pivot, with the same witnesses (a collection split for convenience): continuous numbering. One JSON per witness for the whole edition, as for an edition in a single file, declared in the project settings. Pivot lines are counted from one text to the next, in the order of the edition; the pivot must contain the texts in that order.
  • The witnesses change from one text to another (a corpus): text synchronized separately. Create the folder alignments/<name of the text’s file>/ and put in it one JSON per witness for this text, in the usual format: alignments/s02/B.json, alignments/s02/D.json. Produce these JSON files with VariansSynchro on the text’s file. There is nothing to declare: the folder is enough. A witness without a JSON for this text, but with its <pb edRef> in it or a <locus target> in its <witness>, follows its pages there: see Texts synchronized separately.
  • Both can be mixed: the texts that have their folder are synchronized separately; the others follow continuous numbering, and each witness’s global JSON contains only their lines.

5. Declare a pivot specific to a text

The pivot of a text synchronized separately is the project pivot. If the project pivot lacks this text, or if another witness must serve as reference, write the exception by hand in project.xml, before </teiManuscriptProject>, then reopen the project:

<parts>
  <part name="s02" base="B"/>
</parts>

name is the name of the text’s file, without extension; base, the siglum of the pivot. The lines of this text are then its <lb edRef="#B"/>, and its folder must contain B.json. Varians keeps this element when the project settings are saved.

6. Check

  • Display each text: the structure status, in the status bar, must be right, for instance “B: 8 lines ✓”; its tooltip says whether the count covers the assembled edition or a text synchronized separately.
  • View → Witness diagnostics… gives the scope (the edition or the displayed text), the texts synchronized separately with their pivot and their witnesses, and the problems: JSON of an undeclared witness, unknown pivot, missing pivot JSON…
  • RELAX NG validation covers the assembled edition; the Document column gives the file of each error.
  • The References command checks the references from one text to another.
  • Another XML tool assembles the project without Varians: xmllint --xinclude --noout xml/edition.xml, or oXygen with XInclude enabled in the validator preferences.
  • View → Witness diagnostics… also gives the order of the texts in each manuscript and reports an uncertain place: see Following a manuscript in its own order.

7. Day to day

  • Each text is edited in its tab and saved on its own (Ctrl+S); before quitting, Varians offers to save the modified texts.
  • To add a text: create its file, add its xi:include to the edition, save the edition; its tab appears. For a text synchronized separately, also add its alignment folder, then View → Refresh synchronization….
  • With many tabs: right-click a tab → Hide tab; a click in the pivot makes the tab of the needed text reappear.
  • Saving the edition in another folder would break its xi:include elements: Varians warns you first.
  • The XSLT / CSS view shows the whole edition: the pencil ✎ opens an element of any text there, and a click leads to the text that contains the line; see XSLT / CSS view of the assembled edition. The web export contains the whole edition; see Web export of the assembled edition.
  • To read a manuscript from one text to the next, use the arrows of its panel: the edition displays the right text.

XSLT transformation scenarios

A transformation scenario applies an XSLT stylesheet to the edition or to another document of the project, and writes the result to a file: HTML edition, index, list of quotations, transformed XML… It is named, saved in the project, and can be run again identically. The web viewer remains a separate publication, which a scenario does not change.

File → Transformation scenarios… shows two groups:

  • Project scenarios, saved in project.xml (element <transformations>): Add…, Edit…, Duplicate… and Delete manage them.
  • Predefined scenarios, provided by Varians: HTML edition (Varians stylesheet), which publishes the edition with the stylesheet and CSS of the Varians preview in publications/edition.html; Critical edition (HTML), a critical edition with its apparatus, following the pivot witness (see Critical edition); and, in the TEI Stylesheets sub-group, collapsed at first (a click on its arrow expands it), the scenarios of the TEI-C stylesheets (see TEI Stylesheets). In the menu of the Transform button, the latter form a submenu. A predefined scenario can be run as it is, or duplicated into the project to adapt it.

Each row shows the source, the engine and, in red, what prevents the scenario from running (stylesheet not found, Saxon not installed…). Run runs the chosen scenario; Preview runs it in a temporary folder and opens the result, without touching the scenario’s file.

A scenario

  • Source: Edition (the edition of the project, assembled if it has parts: each part keeps its location, and a relative document() finds its files there), Displayed document (the document of the current tab, for example an auxiliary document, see Auxiliary XML documents; the assembled edition if it is the edition) or File (a file read as it is).
  • Engine: XSLT 1.0 (lxml), or XSLT 3.0 (Saxon) for stylesheets in XSLT 2.0 or 3.0. Saxon-HE (package saxonche) is installed with Varians: installer_dependances.bat, or pip install -r requirements.txt.
  • XSLT stylesheet and optional CSS: paths relative to the project; ${varians}/ designates the stylesheets provided with Varians. The CSS is copied next to the result, and its name is passed to the stylesheet in the parameter css (the Varians stylesheet puts it in its <link>). A new scenario offers the stylesheet and CSS of the preview.
  • Result: the file written, replaced at each run (publications/<name>.html is offered). It cannot be a source of the project (project.xml, the edition and its parts, a document, a stylesheet, a schema, an alignment JSON). With Saxon, a stylesheet may write other files with xsl:result-document (one page per sermon, for example), only in the folder of the result and its subfolders; elsewhere, the run is refused.
  • Output format (with Saxon): A single file, most often; HTML pages (one per division), when the stylesheet writes index.html and its pages with xsl:result-document; DOCX (Word), ODT (LibreOffice) or EPUB, when it writes the files of an archive into the folder whose address it receives, like the TEI-C stylesheets: Varians then builds the archive, which is the result (see TEI Stylesheets).
  • TEI → TEI pre-pass (optional), with Saxon: a stylesheet applied to the source before the scenario’s own, with the same parameters. This is how the DOCX and ODT scenarios put the apparatus into footnotes.
  • Parameters: name / value pairs, passed to the stylesheet (<xsl:param name="title"/>). With Saxon they are passed untyped, as by its command line: “false” suits an xs:boolean parameter, “3” an xs:integer, and the value stays a string elsewhere; with lxml they are strings. In a value, ${pivot} becomes the identifier of the project’s pivot witness, and ${tei}/ the address of the folder of the installed TEI Stylesheets.

Running

The Transform button, next to Generate web viewer, runs again the last scenario run in the project (also Ctrl+Shift+T); its arrow lists the scenarios. Before running, Varians saves what the scenario reads: the edition, its modified parts and the unapplied fragment, as for the web export, and the source document, the stylesheet and the CSS if they are open and modified. The transformation runs in a separate process: Varians remains usable, and Cancel stops it.

The summary gives the files written and the duration; Open opens the result in the default application (the browser, for HTML), Open the folder the folder that contains it. Its details give the log: engine and version, parameters, xsl:message, network reads (with lxml), refused writes. If an error occurs, the message gives the file and line concerned, and the previous result is left intact.

Security: a stylesheet may read any local file, and http or https addresses (the result may then depend on a server); it writes only its result (and, with Saxon, files in its folder). External entities of the sources are not read.

Editing an XSLT stylesheet

An XSLT stylesheet is an XML document: Varians opens it as a project document, in its own tab (see Auxiliary XML documents), checks it and helps you write it, without any external tool.

  • Adding a stylesheet: File → Project XML / XSLT documents… → Add an XML, XSLT or Schematron document… accepts .xsl and .xslt files. A stylesheet located outside the project folder is copied into it, in the xslt/ folder (next to xml/), never replacing an existing file; a stylesheet already in the project stays where it is.
  • New XSLT stylesheet… (same menu) creates a minimal stylesheet, in XSLT 1.0 (lxml) or XSLT 3.0 (Saxon), proposed in xslt/: TEI namespace declared, HTML output, a template for the document root.
  • From the scenarios (see XSLT transformation scenarios): Open stylesheet, in the list of scenarios or in the box of a scenario (which is then saved), shows the stylesheet of a project scenario. A stylesheet supplied with Varians (${varians}/…) is first copied into xslt/; a stylesheet outside the project can be copied too, or opened without copying. After a copy, the scenario uses the copy. For a predefined scenario, first use Duplicate…. A Varians stylesheet that includes or imports others (xsl:include, xsl:import) is copied with them, without replacing a file already there: edition-critique.xsl with apparat-commun.xsl.

Checking. For a stylesheet, Check XSLT stylesheet (F8, instead of Validate RNG) compiles it without running it, with the engine of the project scenarios that use it (both if they differ); a stylesheet that no scenario uses is checked according to its version: version="1.0" by lxml, any other by Saxon. As with RELAX NG validation, the stylesheet is checked when it is first displayed, after each change once F8 has been used, and when saving, which asks for confirmation if it has errors. The validation panel lists each error with its line; a double-click leads to it. An error in an imported (xsl:import) or included (xsl:include) stylesheet names its file in the Document column, and the double-click leads to that stylesheet if it belongs to the project. The status bar shows the result, and the stylesheet’s tab is coloured like that of an invalid document.

Completion. Ctrl+Space proposes the XSLT elements and attributes allowed at that place, with the stylesheet’s prefix (xsl:), and the list of attributes opens while you type. In an element of the result (<div>, <tei:p>…), these are the XSLT instructions and the xsl:* attributes. A version="1.0" stylesheet only receives the elements and attributes of XSLT 1.0. The proposals come from the W3C RELAX NG schema of XSLT 3.0, supplied with Varians (BSD licence); the project’s custom elements (custom-elements.xml) are not proposed in a stylesheet.

Related files. Varians only copies the stylesheet itself. The files it needs for a complete result (stylesheets imported by xsl:import or included by xsl:include, images, CSS, JavaScript…) must be placed yourself in the project’s xslt/ folder, keeping the relative paths the stylesheet uses. Checking reports an imported or included stylesheet that cannot be found. The CSS of a scenario, on the other hand, is copied automatically next to the result.

Limits: a stylesheet meant to be imported or included is checked on its own, and its references to declarations of the main stylesheet may be reported as errors; an XSLT 2.0 stylesheet receives the XSLT 3.0 proposals; names declared in the stylesheet (templates, modes, keys) and XPath expressions are not completed.

TEI Stylesheets: predefined scenarios and customization

The TEI Stylesheets are the XSLT stylesheets of the TEI Consortium (github.com/TEIC/Stylesheets), also used by Oxygen and other tools. Varians brings them and installs them on first use, once for all projects, in the user’s data folder: they work without network. They are written in XSLT 3.0: their scenarios use Saxon.

Predefined scenarios. In File → Transformation scenarios…, the TEI Stylesheets sub-group of the predefined scenarios gathers eight scenarios that publish the edition (assembled, if it is in parts): TEI: HTML, TEI: HTML in several files, TEI: DOCX (Word), TEI: ODT (LibreOffice), TEI: EPUB, TEI: plain text, TEI: Markdown and TEI: LaTeX. It is collapsed at first, and forms a submenu of the Transform button. Their results are written to publications/tei/ (edition.html, pages/index.html, edition.docx, edition.odt, edition.epub, edition.txt, edition.md, edition.tex). The HTML receives next to it the CSS of the TEI Stylesheets (tei.css), with no link to the TEI-C site; the texts added by the stylesheets (“Table of contents”…) follow the language of the interface, through the parameters lang and documentationLanguage. In a scenario, ${tei}/ designates a file of the installed TEI Stylesheets, for example ${tei}/profiles/default/html/to.xsl; see XSLT transformation scenarios. The log of a run names the version used (“Library: TEI Stylesheets 7.61.0”).

Formats in several files. Four of these scenarios have their own Output format (see XSLT transformation scenarios):

  • TEI: HTML in several files writes publications/tei/pages/index.html, the table of contents, and one page per division and sub-division (s02.html…, after their @xml:id), with tei.css. The splitLevel parameter sets the splitting: 1, the scenario’s value, splits divisions and their sub-divisions, which gives one page per piece when the text is a single division gathering them; 0, top-level divisions only. Following the rule of the TEI Stylesheets, the first division stays on the contents page when nothing precedes it (no <front>).
  • TEI: DOCX (Word) and TEI: ODT (LibreOffice) write edition.docx and edition.odt, from the template of the TEI Stylesheets. These would render the apparatus badly (all readings one after the other, each in its own paragraph), and turn each <pb> into a page break and each <lb> into a line break: a Varians pre-pass, apparat-en-notes.xsl, first prepares the text after the pivot witness (parameter temoin-de-base, set to ${pivot}). Each <app> becomes its retained reading, followed by a footnote (<note place="foot" type="apparatus">): “reading ] variant sigla; …”, with om., add., lacuna incipit and lacuna desinit, following the rules of the critical edition. An editor’s note without @place becomes an endnote (place="end"): the apparatus and the notes form two series. Only the folios of the pivot witness remain, as ⟨12r⟩ marks in the text, and the line breaks of the witnesses merge into the text.
  • TEI: EPUB writes edition.epub, with the CSS of the installed TEI Stylesheets (${tei}/tei.css), read without network.
  • Local images (<graphic url="…"/>) are put into the DOCX, ODT or EPUB archive, with their dimensions; a remote image is not downloaded, and the log says so.

Customizing a stylesheet. The TEI Stylesheets are not modified: they are overridden in a stylesheet of the project. Duplicate a TEI scenario (Duplicate…), then choose the copy and Open stylesheet: Varians offers to create in xslt/ a customization stylesheet, for example xslt/tei-html.xsl (Create the customization stylesheet), which the scenario then uses. It imports (xsl:import) the TEI-C stylesheet through its official address, http://www.tei-c.org/release/xml/tei/stylesheet/…, which Varians reads from the installed TEI Stylesheets, without network; Oxygen does the same, and the stylesheet remains valid there. The parameters (xsl:param) and templates (xsl:template) you write in it take precedence over the imported ones; everything else comes from the TEI Stylesheets. For example:

<xsl:stylesheet version="3.0" xmlns:xsl="http://www.w3.org/1999/XSL/Transform"
    xmlns:tei="http://www.tei-c.org/ns/1.0" xmlns="http://www.w3.org/1999/xhtml"
    exclude-result-prefixes="#all">
  <xsl:import href="http://www.tei-c.org/release/xml/tei/stylesheet/profiles/default/html/to.xsl"/>
  <!-- No numbering of headings. -->
  <xsl:param name="numberHeadings">false</xsl:param>
  <!-- Personal names in bold. -->
  <xsl:template match="tei:persName"><b><xsl:apply-templates/></b></xsl:template>
</xsl:stylesheet>

For an HTML output, xmlns="http://www.w3.org/1999/xhtml" makes the added elements (here <b>) XHTML, like those of the TEI Stylesheets. The customization stylesheet is edited, checked (F8) and completed like any stylesheet: see Editing an XSLT stylesheet. An update of the TEI Stylesheets does not touch it: it still applies.

Updates. The TEI-C publishes about two versions a year. At startup, Varians checks at most once a month, without blocking the window, whether a new version has been published; if there is none, or without network, nothing is said. Otherwise it offers to install it: Install or Later (the question comes back at the next check). The installation shows its progress and can be cancelled; an incorrect archive or a cancellation keeps the installed version. The new version is used from the next transformation on, for all projects; the old one is removed at the next start. File → TEI Stylesheets…, or the TEI Stylesheets… button of the scenario list, shows the installed version, its origin, its folder, its licence and the date of the last check; Check for an update checks at once. A single version is installed: a publication made again after an update may differ from the previous one, and the log gives the version.

Licence. The TEI Consortium distributes the TEI Stylesheets under either the BSD 2-Clause licence or the CC BY-SA 3.0 licence; the LICENCE file is installed with them (Show the licence).

Limits. LaTeX is compiled to PDF with a TeX installation (xelatex), outside Varians. In plain text and Markdown, the TEI Stylesheets write the lemma and the variant one after the other: a customization stylesheet can change this choice of the TEI-C. In DOCX and ODT, the apparatus is numbered 1, 2, 3 at the foot of the page, and the editor’s notes i, ii… at the end of the document; in Word, the TEI Stylesheets add a space after the call of an endnote. HTML pages do not carry the images: their address remains that of the source.

Critical edition

The predefined scenario Critical edition (HTML) publishes the edition (assembled, if it is in parts) as a self-contained HTML page, to read on screen or print: publications/edition-critique.html. Its stylesheet, edition-critique.xsl (${varians}/, in XSLT 3.0: Saxon engine), comes from a TEI critical-edition stylesheet, adapted for Varians.

  • Established text. The <lem> of an apparatus always prevails (an empty <lem/> is an established omission); otherwise, the reading of the witness chosen by the temoin-de-base parameter, set to ${pivot}: the pivot witness of the project. In the box of a duplicated scenario, it is chosen from a list: the pivot witness first (“T1 (pivot)”), the other witnesses of the project and of the <listWit>, then “aucun (lemmas only)”; a value written otherwise (#B) is kept; without a value, it is the first <witness> of <listWit>. With aucun, the text follows the <lem> elements only, and each <app> must have one. An unknown witness, or aucun with an apparatus without lemma, stops the run with a clear message. An apparatus without a reading of the chosen witness gives “[lecture du témoin non disponible]”.
  • Apparatus. After each division, in two series: the Apparat critique, called in the text by numbers, and the editor’s Notes, fewer, called by letters (a, b… z, aa…). An entry gives the retained reading, “]”, then each other reading followed by its sigla in italics; the readings of a <rdgGrp> count like the others. An empty reading gives om.; when the established text omits the passage, the other readings are additions (add.). A reading that contains only <lacunaStart/> or <lacunaEnd/> gives “lacuna incipit T1” or “lacuna desinit T1” (see Witness lacunae). Calls and entries are linked both ways.
  • Text. A division without <head> takes its @n as title, otherwise has none. Only the <pb> of the chosen witness, or without @edRef, are shown (⟨12r⟩), and all of them with aucun (⟨T1 : 12r⟩). Contiguous <lb> of several witnesses make a single break, which joins a word if one of them has break="no". Verses and stanzas (<l>, <lg>) keep their structure and their numbers.
  • Parameters (scenario box, after Duplicate…): montrer-folios and montrer-numeros-de-vers (true or false); sauts-lb (true: a line break of the chosen witness becomes a line break of the page).

The same rules put the apparatus into footnotes in the DOCX and ODT scenarios (see TEI Stylesheets). The texts of the page (“Apparat critique”, “Notes”…) are in French: to change them, duplicate the scenario, then Open stylesheet; the stylesheet is copied into xslt/ with apparat-commun.xsl, which holds its rules (see XSLT transformation scenarios).

Search and replace

Two menus follow File: Edit and Search.

  • Edit: Undo (Ctrl+Z), Redo (Ctrl+Y), Cut, Copy, Paste, Select all, Indent the XML, References. The first six act on the field that has the focus (XML, fragment, text field), otherwise on the XML; their shortcuts remain those of each field. Indent the XML acts on the displayed document; References checks the references of the whole project (see References between documents).
  • Simple search (Ctrl+F): the toolbar field for the XML, the fragment search bar when the focus is in the fragment; F3 and Shift+F3 go to the next or previous occurrence.
  • List all (Search → List all occurrences, Ctrl+Shift+L), a button next to the search field: a panel under the editor lists every occurrence of the XML search, with the same options (case, regular expressions). Each row gives the line number and the occurrence in context, highlighted and centred between the text before it and the text after it (KWIC layout). A click leads to the occurrence. With Whole project ticked, the list covers every document of the project, with a Document column; a click on an occurrence in another document shows that document. The open panel follows new searches, the options, changes to the text and the displayed document; beyond 2,000 occurrences, only the first ones are listed. × closes it.
  • Match case and Regular expressions: two checkable options of the Search menu, also shown as the Aa and .* buttons next to the search fields. They apply to the XML and the fragment (the search of the XSLT / CSS view stays literal) and are remembered from one session to the next. Regular expressions are those of Python (module re): ^ and $ apply to each line, \b marks a word boundary; an incorrect expression is reported in the status bar.
  • Find and replace (Ctrl+H) opens a bar under the XML editor or, with the focus in the fragment, the Replace with row under its search. Replace changes the highlighted occurrence then goes to the next one; Replace all changes the whole document (or the whole fragment) and is undone with a single Ctrl+Z. The searched text is taken as typed, spaces included. What was found is replaced, nothing more: replacing a start tag neither renames nor deletes its end tag. Esc closes the bar.
  • With a regular expression, the replacement text can reuse the groups in parentheses: \1, \2…, or \g<name> for a named group (?P<name>…); \n starts a new line. Examples: wit="#(\w+)" replaced with wit="#\1 #T3" adds T3 to each reading of a single witness; <(rdg|lem)\b finds both elements; <lb n="\d+"/> finds the numbered line breaks.
  • XPath search (Ctrl+Shift+F): see XPath search. The toolbar keeps its buttons (XPath, search).
  • Searching the help: in this help window, the field at the top (Ctrl+F) searches the whole help, regardless of accents and case; several words: the sections that contain them all, in any order; between quotes, the exact phrase ("replace all"). On the left, the list of the sections found, with an excerpt; a click leads to the section. The occurrences are highlighted; Enter, F3 and Shift+F3, or ◀ ▶, go through them.

Version 0.9.1.4 — following a manuscript in its own order

The arrows of every witness panel now lead the edition, not only those of the pivot: the witness is followed in its own order, from one part or text to the next, including a witness followed by pages (arrows and folio list); the pivot goes on from one text synchronized separately to the next. The order of the texts in each manuscript is deduced from its pages and shown in “Witness diagnostics…”; see Following a manuscript in its own order. Browsing a witness without moving the edition is now possible only while an auxiliary document is displayed.

Version 0.9.1.5 — XSLT / CSS view of an assembled edition

In an edition in parts, the XSLT / CSS view is no longer read-only: the pencil ✎ opens a paragraph in the file that contains it and writes the applied fragment there, a click on a line leads to the right file and makes the witnesses follow, and selections pass from the preview to the part that contains the text, and back; see XSLT / CSS view of the assembled edition. The preview stays open while a part is displayed. The web export of the assembled edition will come in a later version. An edition in a single file is unchanged.

Version 0.9.1.6 — web export of an assembled edition

The web viewer of an edition in parts now contains the whole edition, with the continuities of the window: the text of the parts, the continuous numbering of the lines, the texts synchronized separately, the lacunae and the route of each manuscript in its own order; see Web export of the assembled edition. Before the export, the edition, its modified parts and the unapplied fragment of a part are saved, without any further question. For an edition in a single file too, the arrows of every panel and the folio list now lead the text, and the lacunae have their banners; see Web viewer. Generate the viewer again to benefit from this.

Version 0.9.1.7 — document tabs

The tab of the displayed document now clearly stands out from the others: white background, blue line at the top, name in bold; the other tabs are set back, on a darker background. The colour of a malformed (red) or invalid (orange) document remains visible, even on the current tab; see Auxiliary XML documents.

Version 0.9.2.0 — XSLT transformation scenarios

Named transformation scenarios, saved in the project, apply an XSLT 1.0 (lxml) or 3.0 (Saxon) stylesheet to the edition, to the displayed document or to a file, and write the result: File → Transformation scenarios…, Transform button, Ctrl+Shift+T; see XSLT transformation scenarios. Saxon is now installed with Varians (installer_dependances.bat).

Version 0.9.2.1 — editing XSLT stylesheets

XSLT stylesheets are added to the project, in the xslt/ folder, created (New XSLT stylesheet…) and opened from their scenarios (Open stylesheet); Varians checks them by compiling them (F8) and completes their elements and attributes (Ctrl+Space); see Editing an XSLT stylesheet. In any document, Ctrl+Space also completes an element name typed just before another tag (<h before </p>). The project.xml format is unchanged. The Project XML / XSLT documents… submenu is now just below Project settings…. A project that keeps a copy of the translations in its i18n/ folder keeps the former names of this submenu and its commands: replace these files with those of Varians’s i18n/ folder to adopt the new ones.

Version 0.9.2.2 — TEI Stylesheets

Varians brings the TEI Stylesheets of the TEI Consortium, installed for all projects and usable without network: four predefined scenarios publish the edition in HTML, plain text, Markdown and LaTeX, in publications/tei/; Open stylesheet, on a duplicated TEI scenario, creates in xslt/ a customization stylesheet that overrides them; at startup, at most once a month, Varians offers their new version (File → TEI Stylesheets…); see TEI Stylesheets. The summary of a transformation also offers Open the folder, which opens the folder of the result; the standard buttons and texts of the windows (“Show Details…”, “Close”…) now follow the language of the interface. The format of project.xml is unchanged.

Version 0.9.2.3 — Schematron rules

Varians applies Schematron rules, together with RELAX NG validation: those embedded in the RNG used (91 groups of rules in tei_all.rng) and those of the Schematron declarations of the document. Their messages are added to the validation panel, which now has an Origin column; a Schematron error counts as a RELAX NG error; a Schematron label is added to the status bar; see Schematron rules. A TEI document valid so far may therefore receive new messages. New projects also declare the rules of TEI All. The format of project.xml is unchanged. A project that keeps a copy of the translations in its i18n/ folder keeps the former title of the panel and the former text of the saving question: replace these files with those of Varians’s i18n/ folder to adopt the new ones.

Version 0.9.2.4 — Schematron phases and files

A Schematron declaration can choose its phase (phase attribute), which the tooltip of the Schematron label names. An incorrect rule now has its row in the validation panel, and double-clicking leads to the rule. .sch files become project documents: adding, New Schematron file…, check (F8) and completion; see Schematron rules. The format of project.xml is unchanged.

Version 0.9.2.5 — Schematron rules: unsaved text, phase, 2020 standard, XSD

The document is validated with the unsaved text of an open rules file. The Schematron rules of the document dialog (click on the Schematron label, or Rules… button of the validation panel) chooses the phase, adds or removes a declaration. The check and the completion of a .sch file accept the novelties of the 2020 and 2025 editions. The rules of an XSD declared as Schematron include those of its xs:include and xs:import. Fix: on a change of language, the headers of the validation panel no longer shift. See Schematron rules. The format of project.xml is unchanged.

Version 0.9.2.6 — unsaved included files

A file included by a rules file (sch:include, sch:extends, RELAX NG and XSD inclusions), open and changed in Varians, is applied with its unsaved text, like the rules file itself since version 0.9.2.5; the check of a .sch file reads it in the same way, and is done again on returning to that file when an included file has changed. Fix: Varians no longer freezes when switching from a long, scrolled document to a short one. See Schematron rules. The format of project.xml is unchanged.

Version 0.9.2.7 — DOCX, ODT, EPUB, HTML in several files, critical edition

Four more TEI scenarios: HTML in several files, DOCX, ODT and EPUB; in DOCX and ODT, the apparatus goes into footnotes. The TEI scenarios are gathered in the expandable TEI Stylesheets sub-group; see TEI Stylesheets. New predefined scenario Critical edition (HTML); see Critical edition. A scenario now has an output format and a pre-pass, written in project.xml (attributes package and prepare of <scenario>); with Saxon, parameters are passed untyped, and ${pivot} designates the pivot witness in them; see XSLT transformation scenarios. A project that keeps a copy of the translations in its i18n/ folder does not find the new names there: replace these files with those of the i18n/ folder of Varians.

Version 0.9.2.8 — Edit and Search menus, find and replace

Two new menus after File: Edit and Search. The search of the XML and of the fragment can match case and take regular expressions; Find and replace (Ctrl+H) replaces step by step or all at once, in a single undo step. See Search and replace. Fix: the occurrence found is highlighted exactly, even after a character beyond U+FFFF. The format of project.xml is unchanged. “Indent the XML” and “References” are now in the Edit menu, no longer in the toolbar. The help can be searched: see Searching the help. List all (Ctrl+Shift+L) lists every occurrence of the XML search in context, in the displayed document or in the whole project: see List all. When the document tabs no longer fit in their row, an arrow ▾ drops down the list of all the tabs: see Auxiliary XML documents. A project that keeps a copy of the translations in its i18n/ folder does not find the new names there: replace these files with those of the i18n/ folder of Varians.

Version 0.9.2.8.1 — browsing a manuscript, debugging the apparatus, Ctrl+E

An open-book button in each witness panel decides whether its arrows lead the edition; by default, only the pivot’s do, and the other witnesses are browsed on their own: see Leading the edition or browsing. The “Debug the apparatus” window offers a third search, the <app> without <lem>: see Debug the apparatus. In the Ctrl+E list, the highlighted entry is the one inserted; with no entry chosen, the typed text is. The format of project.xml is unchanged.

Version 0.9.2.8.2 — witness sigla, pencil and F2

A witness siglum that is not an XML identifier (“1760”, “T 2”) is accepted: Varians derives the identifier from it and keeps the siglum for display; see Witness siglum and identifier. project.xml then receives a siglum attribute; an existing project does not change. In the XSLT / CSS view, the pencil ✎ keeps the current selection, and F2 opens the paragraph of the selection in the fragment editor: see Selections shared with the fragment editor. Varians releases no longer contain the tests or the test project. A witness added in the project settings is declared in the edition’s existing <listWit>. “Mark page” accepts any XML identifier, in any script (“Σ”, “伝本”), as does “Debug the apparatus”.

Version 0.9.2.9 — editable elements as fragments

In the XSLT / CSS view, the pencil ✎ is no longer limited to paragraphs: each block of a division (stanza, heading, list, table, quotation, figure, note…) has its own, according to the TEI classes model.divPart and model.inter of the project schema; see Editable elements. The pencils are placed whatever the XSLT stylesheet of the view, and the label of the fragment editor names the open element. The stylesheet shipped with Varians displays verse, headings, lists and figures. In this stylesheet as in “Critical edition (HTML)”, a list is numbered if it has @rend="numbered" or @type="ordered" (or “numbered”), and the heading of a list is placed before it. In this stylesheet, as in “Critical edition (HTML)”, a division is titled by its first <head>, otherwise by its @n: its @xml:id is no longer taken as a title. The table of contents of the preview lists the titled divisions, by level, and the header only shows the title of the edition. The format of project.xml is unchanged.

Version 0.9.3.0 — reading text of the web viewer

The web viewer displays the structure of the text: titles of divisions and a table of contents by level, front and back matter, every text of a <group>, stanzas with numbered lines, nested lists, tables, figure captions, notes placed between two paragraphs; see Reading text. It handles choices, deletions, additions, supplied text and gaps as “Critical edition (HTML)” does, reads the readings of a <rdgGrp> and gives the text its language. A division is no longer titled by its @xml:id there: a division without <head> or @n has no title. The preview stylesheet and “Critical edition (HTML)” display <table> elements: caption, header cells, merged cells. The format of project.xml is unchanged; a viewer already exported must be exported again to benefit from this. In the preview of the XSLT / CSS view, a stanza is a single indented block, its lines one after the other, even with the CSS of a project created by an earlier version.
