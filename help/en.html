Varians — TEI XML Editor for textual criticism

Varians is an XML editor for the critical edition of texts transmitted by manuscripts or early editions, encoded in TEI. It brings together in a single interface the transcription, the images of the witnesses and a reading view, and lets you transform the edition into a web format.

1. Overview

What Varians does

  • Edit TEI. An XML editor that completes elements and attributes according to the schema, helps with markup, searches the text (regular expressions, XPath), follows references between documents, folds and indents without damaging the text.
  • Validate the XML. RELAX NG and Schematron rules, while you type, without freezing the window.
  • Read what you edit. The XSLT / CSS view shows the formatted edition; each block opens there to be corrected in a fragment editor. The XML source tab, open by default, always gives access to the raw XML code.
  • See the manuscripts. The images of each witness (local files or IIIF), possibly with their lines (ALTO, PAGE XML), are aligned with the transcription, page by page or line by line depending on the data available.
  • Check the apparatus. Ready-made queries find the frequent errors of a critical apparatus (a forgotten or redundant witness, for example); the lacunae of the witnesses are recognized.
  • Publish. A standalone web viewer, where the text and the facsimiles stay synchronized; an HTML critical edition with its apparatus; DOCX, ODT, EPUB, HTML, LaTeX… through the TEI Stylesheets, supplied with Varians; and any XSLT stylesheet of your choice.

How it differs from a general-purpose XML editor

A general-purpose XML editor treats every XML document in the same way. Varians starts from the work of the textual editor:

  • The manuscripts next to the text. Each witness has its panel. When the cursor moves in the transcription, each panel shows the corresponding page, or line, of its manuscript. Conversely, you can read the edition in the order of a particular manuscript: the arrows of its panel lead the edition to the corresponding passage.
  • A pivot witness. Synchronization relies on the lines of a reference witness, called here the pivot; every other witness can align its own lines with those of the pivot, visually, even before you have started transcribing. The choice of a pivot witness is technical, for alignment: it implies nothing about the stemma or about the base manuscript that will be adopted.
  • The apparatus at the centre. Completion of @wit from the list of witnesses, apparatus checks, lacunae, and, on publication, a choice between the established text and the transcription of a particular witness; the readings that do not yet come from a <lem> can be highlighted.
  • A reading view you can edit. You correct the edition where you read it, block by block, without losing your place in the XML.
  • An edition optionally in several files (one file per text, assembled by XInclude) is treated as a single document: validation, references, witness synchronization, publication.
  • Built-in web publication. The web viewer, a configurable XSLT that follows the conventions of critical editions, and the formats of the TEI Stylesheets are available in Varians, with neither server nor network.
  • Standard TEI. Varians writes only ordinary TEI into your files (<pb/>, <lb/>, <facsimile>…). What concerns only the project (witnesses, images, alignments, scenarios) is in a separate project.xml file; your display preferences stay on your computer. Any other XML tool can read your edition.
  • Caution. Varians does not guess: a doubtful correspondence between a line and an image, an ambiguous tag closing, a page that cannot be found are never invented, but reported. Important writes keep a .bak copy.
  • Seven interface languages: French, English, German, Japanese, Czech, Italian and Russian (View → Language).

What Varians does not do

  • It does not align the lines of the manuscripts itself: the alignment files (JSON) come from Varians-Synchro, a separate tool.
  • It does not detect the lines on the images (segmentation): the ALTO or PAGE XML lines come from recognition software (eScriptorium, Transkribus, PERO OCR…).
  • It does not collate: you encode the apparatus in the TEI yourself; Varians helps you enter it and check it.
  • It is not a word processor: you edit the XML; the XSLT / CSS view is for reading and correcting one block at a time.

2. Quick start

This walkthrough leads from an empty folder to a first publication. Each step refers to the chapter that describes it in detail.

  1. Install and launch. Varians requires Python 3 and three libraries (PySide6, lxml and Saxon). On Windows, run installer_dependances.bat once, then launch Varians with lancer_editeur.bat. Elsewhere: pip install -r requirements.txt, then python editeur_tei.py.
  2. Create the project. File → New project…: choose an empty folder, then the Starting point, Start from an existing TEI edition (your file is copied into the project) or Start a new transcription (Varians creates a minimal TEI). See Projects.
  3. Declare the witnesses. Under Witnesses and resources, Add… each manuscript: its Siglum, its Display name, the Image source (you can choose between: none for now, local images or an IIIF Manifest). Designate the pivot: Set as pivot witness. The rest can come later. See Key concepts and Witnesses and facsimiles.
  4. Transcribe and mark up. In the XML source tab, Ctrl+E wraps the selection in an element, Ctrl+Space completes an element or attribute name, F8 validates the document. In the XSLT / CSS view tab, click the pencil ✎ of a block, or select a passage to change and press F2, to open this passage in the fragment editor; Apply to XML updates the source. See Editing the XML and Validating.
  5. Link the text to the images. Place the cursor, in the text, at the beginning of a page (e.g. f. 1v) of a witness (e.g. A1), and click Mark page in the panel of this witness: Varians inserts a <pb n="1v" edRef="#A1" facs="#A1-p0002"/>. From then on, the panel follows the text, page by page. To follow it line by line, declare the alignment file (JSON) of the witness in File → Project settings…. See Witnesses and facsimiles.
  6. Encode and check the apparatus. In a @wit, type # to choose a witness from the list. Help → Debug the apparatus… finds the witnesses without a reading or cited twice. See Critical apparatus.
  7. Proofread. The XSLT / CSS view tab shows the formatted edition; the pencil ✎ opens a block to correct it. See XSLT / CSS view and fragment editor.
  8. Web format. Generate web viewer creates a standalone site in web_output/, with text and images synchronized. The Transform button runs a scenario: Critical edition (HTML), TEI: DOCX (Word)… See Web viewer and Publishing with XSLT.
  9. Save. Ctrl+S saves the displayed document; before quitting or changing project, Varians offers to save each modified document.

3. Key concepts

The project

A project is a folder that contains a project.xml file. This file names the edition, its witnesses and their resources (images, lines, alignments), the preview stylesheet, the publication scenarios. The edition itself is a TEI file, xml/edition.xml, which can be split into parts (see Editions in parts). Other documents can be added to it: authority files, notes, XSLT stylesheets, Schematron rules.

Three kinds of data, three places. What belongs to the text is in the TEI: pages, lines, apparatus, facsimile. What belongs to the project is in project.xml: witnesses, images, alignments, scenarios, saved queries. Your working preferences (displayed witnesses and their layout, visible tabs…) stay on your computer, specific to each project, without changing any file of the project.

Witnesses, sigla and pivot witness

A witness is a manuscript, or a printed book, that transmits the text. Its siglum (A, T1, P…) designates it everywhere. In the TEI, it is the identifier of its <witness> in the <listWit>, cited by @wit (in the apparatus) and @edRef (pages and lines specific to this witness); see Witness siglum and identifier.

The pivot witness is the reference for synchronization: its lines (<lb edRef="#A"/>) mark the boundaries in the text, and every other witness links its own lines to those of the pivot. This choice is technical: it implies nothing about the place of the witness in the stemma, nor about the manuscript that the edition will adopt as its base manuscript. In an edition in parts, a part can have its own pivot.

Following a witness by pages or by lines

The panel of a witness follows the transcription in one of two ways:

  • by pages: a <pb edRef="#B" .../> marks the start of each page of witness B in the transcription; the panel shows the page of the last <pb> of B before the cursor. Images and <pb> elements with the right @edRef are enough;
  • by lines: an alignment file (JSON), produced by Varians-Synchro, links each line of the manuscript, located on the image by ALTO or PAGE XML, to a line of the pivot. The panel then shows the corresponding line, cropped. To see the edition aligned with the images of the manuscripts, you must have inserted the <lb/> elements of the pivot witness, and only its own: the other witnesses are aligned through them, without their own <lb/> elements being inserted in the edition.

Each witness has its own mode: in the same edition, some can be followed by lines, others by pages. Others may not have digital images yet.

The critical apparatus

Varians expects an apparatus in parallel segmentation: each point of variation is, in the text, an <app> that brings together the retained reading (<lem>) and the variants (<rdg>), each with the witnesses that carry it:

<app><lem wit="#A">dixit</lem><rdg wit="#B #C">ait</rdg></app>

It is normal to proceed in stages in editorial work: you often first record the variants neutrally, and decide later, once you have a better view of the tradition, what you will retain as the lemma:

<app><rdg wit="#A">dixit</rdg><rdg wit="#B #C">ait</rdg></app>

Varians lets you visualize the work even before all the lemmas have been chosen. Thus the established text of the Critical edition (HTML) and of the web viewer is made first of the <lem> elements; where there is none, of the reading of a chosen witness, by default the pivot. Both can highlight in yellow the readings that do not come from a <lem>, those that remain to be decided (see Choice of the text and Critical edition).

4. Projects

Creating, opening, closing

On the first launch, Varians opens no project; afterwards, it reopens the one that was open when it was closed. The File menu offers New project… (Ctrl+N), Open project… (Ctrl+O) and Reopen recent project…. File → Close project (Ctrl+W) returns to the welcome screen without quitting Varians; the closed project is not reopened at the next launch.

New project… asks for an empty folder, then the Starting point: Start from an existing TEI edition, whose file is copied into xml/edition.xml, or Start a new transcription: Varians creates a minimal TEI, with the <listWit> of the project’s witnesses.

<listWit>
  <witness xml:id="A1">Assisi, Sacro convento, 541</witness>
</listWit>

A witness can be declared without images, without ALTO and without synchronization: these resources can be added later if needed, in any order, in File → Project settings…. The same dialog sets the RELAX NG schema (detected from the document’s <?xml-model?>, chosen in the project, or none), the XSLT stylesheet and the CSS of the preview, the Ctrl+E configuration (custom-elements.xml), the folder and the file name of the web viewer.

Project structure

project.xml        the project
xml/edition.xml    the edition (its parts and the other XML documents, next to it)
xslt/              the project’s XSLT stylesheets
images/  alto/     local images, ALTO or PAGE XML lines copied into the project
alignments/        alignment files (JSON)
iiif/local/        local copies of IIIF images
rendering/         preview CSS, custom-elements.xml
i18n/              interface translations
publications/      results of the transformation scenarios
web_output/        web viewer

The i18n/ folder of a project contains a copy of the interface translations, which takes precedence over that of Varians: to adopt the texts of a new version of Varians, replace its files with those of the i18n/ folder of Varians.

Witness siglum and identifier. The siglum of a witness, entered in File → Project settings…, also serves as its XML identifier: the xml:id of its <witness>, the target of @wit and @edRef. An XML identifier starts with a letter or “_” and contains no space and no sign such as “/” or “:”. If the siglum entered does not follow these rules (“1760”, “T 2”), Varians derives a valid identifier from it, shown under the field: each forbidden character becomes “_”, and a “_” is added in front of a siglum that does not start with a letter; “1760” gives _1760, “T 2” gives T_2. In the TEI, you then write wit="#_1760". The siglum remains what Varians displays wherever it names the witness; it is kept in project.xml (siglum attribute of the <witness>) and, in the TEI created with the project, in an <idno type="siglum">:

<witness xml:id="_1760"><idno type="siglum">1760</idno>Troyes, BM, ms. 1760</witness>

The stylesheets supplied with Varians (preview, Critical edition, apparatus in notes) and the web viewer show this siglum instead of the identifier. A witness added later, in File → Project settings…, receives a <witness> of the same form at the end of the edition’s <listWit>, if there is one: Varians does not create it. The box confirming that the settings were saved says what was added. Two sigla that would give the same identifier (“T 2” and “T/2”) cannot coexist.

Preparing a blank transcription from the pivot witness

To start a transcription, Varians can pre-fill the pages (<pb/>) and the lines (<lb/>) of the pivot witness. In File → New project… (with Start a new transcription) or in File → Project settings…, the Prepare pivot-witness transcription box offers Prepare pivot-witness <pb/> markers in an empty TEI, then Also generate <lb/> markers from ALTO, PAGE or synchronization.

Only the pages selected for the edition receive a <pb/>: its @facs designates the <surface>, its @edRef the witness. The <lb/> elements carry only @edRef. Varians takes the ALTO or PAGE lines linked with certainty to the page, otherwise the lines described in the alignment file: a partial folio running from line 41 to line 68 gives 28 <lb/>. A page with no known line keeps its <pb/>; gaps are reported, never filled in. A preview, a confirmation and a dated backup protect the text; no automatic transcription is imported.

Project documents and tabs

Besides the edition, a project can bring together other XML documents: an authority file (persons, places), notes, etc. Use File → Project XML / XSLT documents…. Add an XML, XSLT or Schematron document… declares an existing file; a file located outside the project folder is copied into it, in xml/, never replacing an existing file. New XML document… creates an empty document whose root element you choose. Remove the document from the project removes the displayed document, without deleting its file.

As soon as an auxiliary document exists, a row of tabs appears above the XML source: Edition, then one tab per document. Each document keeps its own undo history, position and state; an asterisk marks unsaved changes, and the colour of the name a malformed or invalid XML. RELAX NG validation and completion follow the <?xml-model?> of the displayed document. The manuscripts, the XSLT / CSS view and the witness commands concern the edition only: they are hidden while another document is displayed, then restored unchanged. Ctrl+S saves the displayed document; before quitting or changing project, Varians offers to save all the modified documents. The web export uses the edition only.

Displayed tabs. View → Choose displayed documents… lets you choose which documents have a tab, and the order of the tabs. Right-clicking a tab offers Hide tab, Rename tab…, Choose displayed documents… and Remove the document from the project, for the document of that tab, even when it is not displayed. A hidden document stays in the project: its changes are kept, and Varians offers to save them before quitting. Its tab reappears when a reference leads to it (F12, Ctrl+click, double-click in the References panel). The last visible tab cannot be hidden; when the project opens, the edition is displayed, with its tab. These choices are saved locally for the project, without changing project.xml. The name given with Rename tab…, however, is written to the label attribute of the <document>, in project.xml; an empty name restores the file name. When the tabs no longer fit in their row, an arrow ▾ (“All tabs”) appears on its right: it drops down the list of all the tabs, with the displayed document’s tab checked; a click shows the chosen document. The list ends with Choose displayed documents….

The documents are declared in project.xml by a <documents> element.

Saving

File → Save edition (Ctrl+S) saves the displayed document: the edition, one of its parts or another document of the project. Save edition as… (Ctrl+Shift+S) writes it elsewhere. Before quitting or changing project, Varians offers to save each modified document. A malformed or invalid document can be saved, after confirmation.

Important writes use atomic replacement and keep a .bak copy. When an automatic operation would be ambiguous, Varians refrains rather than silently rewriting the TEI.

5. Editing the XML

The editor

The XML source tab (Ctrl+1) shows the displayed document; the XSLT / CSS view tab (Ctrl+2), the formatted edition (see XSLT / CSS view and fragment editor). The Wrap long lines visually option is purely visual: it changes neither the XML nor the line numbering.

Tag pairs. When the cursor is in an opening or closing tag, both tags of the pair are coloured pale blue, from <app> as from </app>, respecting nesting, prefixes (tei:div) and empty elements; comments, CDATA and processing instructions form no pairs. Renaming an opening tag renames its closing tag; deleting the whole opening tag removes the closing one while keeping the content. Crossed or uncertain markup gives no pair.

Closing tags. In the XML editor as in the fragment editor, typing </ suggests closing the nearest open element: after <div><p>…</p></, Varians suggests div>; Enter or Tab inserts it. You can also start the name, for example </di. Esc closes the list, Ctrl+Space reopens it. Empty elements (<lb/>), comments, CDATA and unfinished attributes are ignored; if the nesting is ambiguous, no closing tag is invented.

Folding. View → XML folding: Fold / unfold element (Ctrl+Alt+F), Fold structural elements, Unfold all (Ctrl+Alt+Shift+F); the ▾ / ▸ chevrons in the margin fold or unfold an element. Only elements spread over several lines, whose tags are on their own lines, can be folded. Folding changes neither the XML nor the undo history; any change to the text unfolds everything, and moving the cursor to a hidden line makes it visible.

Indenting. Edit → Indent the XML indents the structural regions of the document, cautiously:

  • no whitespace is added around an <lb/>;
  • xml:space="preserve" is respected;
  • mixed or ambiguous content is left untouched;
  • an element that, according to the schema, accepts text is treated as text.

custom-elements.xml can specify formatting="inline", formatting="block" or formatting="preserve"; the protections above take priority.

Markup assistance

Ctrl+E wraps the selection in an element or inserts a new element at the cursor. In the list, an entry is highlighted only when you choose it (click, arrows, or Tab / ↓ from the field, which select the first one): Enter inserts the highlighted entry, otherwise the text typed in the field; typing again in the field clears the choice. The elements that the RELAX NG schema allows at that place are offered first.

Ctrl+Space completes element and attribute names, and some attribute values, including an element name typed just before another tag (<h before </p>). The suggestions come from the RELAX NG schema, from the custom-elements.xml file, or from both, and their source is shown. In an opening tag, the beginning of an allowed attribute opens the filtered list by itself; Enter or Tab inserts the attribute and its quotes.

In a pointer attribute such as @wit, typing # opens the list of the witnesses or identifiers of the project (see References between documents); Varians completes a list of values separated by spaces without offering again those already in it.

Ctrl+E configuration. File → Ctrl+E configuration… opens the project’s custom-elements.xml file: elements offered by Ctrl+E, attributes and values offered by Ctrl+Space (a witnesses source gives the project’s witnesses in the form #A1, #B1…), indentation rules. This file helps you type; it never changes the validity of the document. Its format is described in CUSTOM_ELEMENTS.md.

Dictionary. Ctrl+? (or Help → Latin Dictionary) looks up the selected text in the Vocabula Latin dictionary, in the browser.

References between documents

A pointer attribute (@ref, @corresp, @target, @who, @wit, @edRef, @sameAs, @ana, @resp, @source, @hand, @facs, @prev, @next, @synch, @copyOf) designates an element by its @xml:id. As in standard TEI, and therefore for every XML tool, the short form #bernard designates an element of the document itself. To point to another document of the project (see Auxiliary XML documents), write personnes.xml#bernard, with a path relative to the document that contains the reference. Web addresses (https://…) and values without “#” are not processed. A value may contain several pointers separated by spaces: wit="#T1 #T2".

Typing. In the value of such an attribute, type #: the list of identifiers opens by itself, with the text of each entry and its file, for example “personnes.xml#bernard — Bernardus”. The following letters filter the list; Enter or Tab inserts the value; Esc closes the list. For @wit and @edRef, the list offers the witnesses described in the TEI (<witness> of the <listWit>). Ctrl+Space opens the same values in a dialog (“Project identifiers”) where the filter also applies to the descriptions: “Bern” finds personnes.xml#bernard. The identifiers offered depend on the element: persName/@ref offers the person, personGrp and persona elements; placeName/@ref the place elements; orgName/@ref the org elements; @who the persons. Elsewhere, every identifier is offered. In custom-elements.xml, <values source="ids" elements="person personGrp" prefix="#"/> sets this list for an attribute. An identifier of another document is inserted in the form file.xml#id, an identifier of the document itself in the form #id.

Navigation. On a reference, press F12, Ctrl+click, or choose Go to target in the right-click menu: the document that contains the target is displayed, with the element selected. If the identifier is defined more than once, Varians asks which target to display. Alt+← (or Go back in the right-click menu) returns to the starting point, even from another document. A target that cannot be found is reported in the status bar. On a short form whose target is only in another document, Varians goes there too and gives the form to write.

Checking. The Edit → References command checks the references of every document of the project. The panel that opens below the source gives their number and lists those with a problem: target not found, short form whose target is in another document (with the form to write), ambiguous target (identifier defined more than once in the target document) or file not found, with the columns Document, Line, Attribute, Value and Problem. A double-click leads to the reference. After a correction, Check again runs the check again. This check is an aid: it never prevents saving and modifies no file.

Search and replace

The Search menu brings together the searches in the XML and in the fragment; XPath search has its own section.

  • Simple search (Ctrl+F): the toolbar field for the XML, the fragment search bar when the focus is in the fragment; F3 and Shift+F3 go to the next or previous occurrence.
  • List all (Search → List all occurrences, Ctrl+Shift+L), a button next to the search field: a panel under the editor lists every occurrence of the XML search, with the same options (case, regular expressions). Each row gives the line number and the occurrence in its context, highlighted and centred between the text before it and the text after it (KWIC layout). A click leads to the occurrence. With the Whole project box ticked, the list covers every document of the project, with a Document column; a click on an occurrence in another document shows that document. The open panel follows new searches, the options, changes to the text and the displayed document; beyond 2,000 occurrences, only the first ones are listed. × closes it.
  • Match case and Regular expressions: two checkable options of the Search menu, also available as the Aa and .* buttons next to the search fields. They apply to the XML and the fragment (the search of the XSLT / CSS view stays literal) and are remembered from one session to the next. Regular expressions are those of Python (module re): ^ and $ apply to each line, \b marks a word boundary; an incorrect expression is reported in the status bar.
  • Find and replace (Ctrl+H) opens a bar under the XML editor or, with the focus in the fragment, the Replace with row under its search. Replace changes the highlighted occurrence then goes to the next one; Replace all changes the whole document (or the whole fragment) and is undone with a single Ctrl+Z. The searched text is taken as typed, spaces included. What was found is replaced, nothing more: replacing an opening tag neither renames nor deletes its closing tag. Esc closes the bar.
  • With a regular expression, the replacement text can reuse the groups in parentheses: \1, \2…, or \g<name> for a named group (?P<name>…); \n starts a new line. Examples: wit="#(\w+)" replaced with wit="#\1 #T3" adds T3 to each reading of a single witness; <(rdg|lem)\b finds both elements; <lb n="\d+"/> finds the numbered line breaks.
  • XPath search (Ctrl+Shift+F): see XPath search. The XPath button of the toolbar also opens it.
  • Searching the help: in this help window, the field at the top (Ctrl+F) searches the whole help, regardless of accents and case; several words: the sections that contain them all, in any order; between quotes, the exact phrase ("replace all"). On the left, the list of the sections found, with an excerpt; a click leads to the section. The occurrences are highlighted; Enter, F3 and Shift+F3, or ◀ ▶, go through them.

XPath search

Search → XPath search (XPath button, Ctrl+Shift+F) opens a panel under the editor: an XPath 1.0 expression searches the displayed document there, for example //note for the <note> elements. In a TEI that uses the standard namespace, a simple query without a prefix is retried with the tei: prefix.

The results give the line, the element, its path and an excerpt. Clicking a result selects the whole element, from its opening tag to its closing tag, even across several lines; the selection is kept when you switch to the XSLT / CSS view, and found again when you return to the source. An expression that returns a value, such as count(//tei:note), displays that value.

To check the critical apparatus, Help → Debug the apparatus… offers ready-made queries: see Debug the apparatus.

6. Validating

Varians checks the displayed document against its RELAX NG schema and its Schematron rules. An XSLT stylesheet or a Schematron rules file is also checked when it is displayed: see Editing an XSLT stylesheet and Schematron rules.

RELAX NG validation

The schema of a document is the one declared by its <?xml-model?>, or the one set in File → Project settings… (which can also disable validation). Varians validates the document on opening, on saving and on request: Validate RNG (F8). The errors are listed in the RELAX NG and Schematron validation panel, under the editor, with their level, their line and their column; a double-click leads to the error. Once this panel has been used, validation runs again by itself after a short pause in typing, and a corrected error disappears from the list. The status bar sums up the result; the tab name of a malformed document turns red, that of an invalid document orange.

A remote schema (http address) is downloaded the first time it is used, then kept in the schema cache; the Refresh the remote schema and validate again button of the panel downloads it again.

Without freezing the window. Validation runs in a separate process, which Varians starts when first needed. The first compilation of a large schema such as TEI_ALL takes about ten seconds; meanwhile, the window remains usable and a small glow turns next to the RNG: validating… state in the status bar. The compiled schema is then kept for the whole session, even when another project is opened. Automatic validation never interrupts your work; Validate RNG (F8) and saving, however, wait for the result: the window stays displayed, but clicks and key presses are ignored until the answer arrives. If the validation process cannot be started, Varians validates by itself and says so in the status bar; the window may then freeze during the compilation.

Schematron rules

A RELAX NG schema says which elements and attributes are allowed, and where. Schematron rules check what it cannot express: for example, in TEI, that an <lg> contains at least one line, or that @target and @cRef are not used together. Varians applies them together with the RNG: on opening, while typing, with Validate RNG (F8) and on saving, in the same separate process (see RELAX NG validation).

Which rules. First those embedded in the RELAX NG schema used, whether declared by the document or chosen in the project settings: tei_all.rng contains 91 groups of them, an ODD customization its own. Then those of each Schematron declaration of the document, to a .sch file or an RNG:

<?xml-model href="regles.sch" type="application/xml"
    schematypens="http://purl.oclc.org/dsdl/schematron"?>

A relative address starts from the document; an http address is downloaded once, then kept in the schema cache. The same rules are never checked twice: the Schematron declaration of TEI documents designates the same tei_all.rng as their RNG. New projects receive both declarations. For an edition in parts, the rules apply to the assembled edition, like the RNG.

XSD schema. An XSD schema declared as Schematron (same schematypens) gives the rules it embeds in its xs:appinfo, including those of the files it includes or imports (xs:include, xs:import). Varians does not validate the document against the XSD itself.

Phases. A Schematron file can group its patterns (sch:pattern) into phases (sch:phase). Unless told otherwise, Varians checks the default phase of the file (defaultPhase), otherwise all its rules. To choose a phase, add the standard phase attribute to the declaration, as in Oxygen:

<?xml-model href="regles.sch" type="application/xml"
    schematypens="http://purl.oclc.org/dsdl/schematron" phase="lecons"?>

#ALL checks all the rules, #DEFAULT the default phase. A phase that does not exist in the file is an incorrect rule (see below), given with the list of the phases of the file. Without writing the declaration yourself: clicking the Schematron label of the status bar, or the Rules… button of the validation panel, opens the Schematron rules of the document dialog. For each declared rules file, it offers the phase in a list (the default phase, all the rules, the phases of the file); it also adds or removes a declaration. The changes are written in the <?xml-model?> declarations of the document, and Ctrl+Z undoes them.

Messages. They are added to those of the RNG in the RELAX NG and Schematron validation panel: the Origin column says Schematron, and double-clicking leads to the line of the element concerned (for a rule on an attribute, that of its element), in its document. The level comes from @severity, otherwise from @role: warning, warn or nonfatal give a Warning, info an Information, anything else an error. An error makes the document invalid, like a RELAX NG error: tab name in orange, and the question Document is not valid before saving (Save anyway). A warning or an information stays in the list, without making the document invalid.

Status bar. Next to the RNG state, the Schematron label sums up the result: Schematron: ✓, the number of errors or messages, or Schematron: not checked when validation is disabled for the project. Its tooltip names the files of the rules applied, with their phase: “apparat.sch (phase lecons)”. Clicking the label opens the Schematron rules of the document dialog.

Incorrect rules. A faulty XPath expression, an unknown phase, or a rules file that cannot be found or is malformed, give Schematron: incorrect rules. Each incorrect rule has its row in the panel, after the messages of the document: origin Schematron (rules) and, in the Document column, the rules file. Double-clicking shows this file at the line of the rule; a file of the project folder that is not yet a project document can be added to the project (Varians offers to do so); a file outside the project, such as the copy of a remote file in the cache, does not open, and the status bar says so. The schema is at fault: the document does not become invalid, and the other rules are applied. When a rules file has been changed and saved, the document is validated again as soon as you return to it.

Writing the rules in Varians. File → Project XML / XSLT documents… → Add an XML, XSLT or Schematron document… accepts .sch files; a file outside the project is copied into its xml/ folder. New Schematron file… creates a minimal file (xml/regles.sch is offered), which declares the tei prefix and contains an example rule; then add its declaration to the document. A displayed Schematron file is checked instead of the RELAX NG validation: Check the Schematron rules (F8), on display, while typing once F8 has been used, and on saving. The check concerns the displayed text, even unsaved: well-formedness, structure according to the ISO Schematron schema (supplied with Varians), included files, then compilation of all the phases by Saxon; each error is given at its line, and double-clicking leads to it. Ctrl+Space and the automatic list of attributes offer the Schematron elements and attributes, with the prefix of the file, and common values for severity, role and queryBinding. The document is validated with the displayed text of an open rules file, even unsaved: returning to the document after changing its rules validates it again, and the tooltip of the Schematron label says so (“regles.sch, unsaved”). The same goes for a file it includes (sch:include, sch:extends), open and changed: the tooltip names it (“regles.sch (unsaved: motifs.sch)”), and the check of the rules file takes it into account, again when you return to that file. The novelties of the 2020 and 2025 editions of the standard, which SchXslt2 applies, are accepted and offered by the completion: sch:group, sch:rules, sch:library, schema-level sch:param, @visit-each, @from and @when of phases.

Engine. Varians uses SchXslt2 (David Maus, MIT licence), shipped with it, and Saxon (the saxonche package, installed by installer_dependances.bat, as for transformation scenarios). Without Saxon, the label shows Schematron: Saxon missing and only RELAX NG validation is done. The rules are prepared in less than a second when first checked, then kept for the session, and prepared again if their file changes.

Limits. The rules are evaluated in XPath 3.1, whatever their queryBinding: a rule written for XPath 1.0 almost always behaves the same. For the 2020 and 2025 editions, whose schema is not freely available, the check of a .sch file follows what SchXslt2 accepts. The former Schematron 1.5 is not supported, nor validation against an XSD.

7. XSLT / CSS view and fragment editor

The preview

The XSLT / CSS view tab shows the edition formatted by an XSLT stylesheet and a CSS: those of Varians, or those of the project (File → Project settings…, XSLT source: Editor default XSLT, which follows the fixes made to Varians, or Custom XSLT, a file of the project); the Formatting row of the view lets you try another XSLT or CSS stylesheet. The preview is updated when you return to it after a change; Auto preview updates it at each pause in typing, Refresh on request; Size enlarges or reduces the text. A table of contents gives access to the titled divisions; the Search preview field searches it for a word or a phrase.

A click on the text of the preview places the cursor of the source at the same place and makes the witnesses follow. A string selected in the preview is selected in the source when you return to the XML source tab, at the same occurrence of the same passage (even a word split by an <lb break="no"/>); conversely, the selection of the source, for example an XPath result, is found again in the preview. Returning to the source without having changed the selection of the preview restores the original selection.

A transformation may read local files (an authority file, for example), but can neither write files nor access the network. An error in the stylesheet is reported as is, with its file and line.

The fragment editor

The pencil ✎ placed at the start of a block of the preview opens this block, as it is written in the XML, in the fragment editor, below the preview. You correct it as in the source (completion, Ctrl+E, search and replace), then Apply to XML writes it into the document, in its place; Apply and continue writes it without closing the editor; Reload fragment takes the text from the document again. The fragment must remain well formed. Before quitting, Varians offers to apply a modified fragment.

Selections shared with the fragment editor. The pencil ✎ placed at the start of an element of the preview (a paragraph, a stanza, a heading…: see Editable elements) opens that element in the fragment editor, without moving the witness images; a click on the text of the preview still synchronizes them. While the editor is open, a string selected in that element of the preview (by dragging the mouse or by a double-click) is also selected in the fragment editor, which takes the focus: the passage to correct is found at once. Conversely, a selection made in the fragment editor is selected in the preview, which scrolls to it; the focus stays in the editor. The same occurrence of a repeated word is found, including a word split by an <lb break="no"/>. A selection in another element does not change the fragment editor: open that element with its pencil. Text typed in the fragment appears in the preview only after Apply to XML. Clicking the pencil keeps the current selection of the preview: if it lies in that element, it is also selected in the fragment editor. In the preview, F2 opens the element of the selection (or of the cursor) in the fragment editor, with the selection. An element that is already open and has unapplied corrections is not reloaded.

Editable elements. The pencil ✎ opens each block placed in a division of the <body>: any element of the TEI classes model.divPart (<p>, <ab>, <lg>, <l>, <sp>…) and model.inter (<list>, <table>, <quote>, <cit>, <stage>…), as well as <head>, <figure> and <note>. An element contained in another element of this set has no pencil of its own: it opens with that element. So an <lg> has its pencil, its <l> elements do not; a <p> has its own, the <quote> or <note> it contains does not; a speech (<sp>) has its own, placed on its speaker; a <note> placed between two paragraphs has its own. The classes are read from the project’s RELAX NG schema, as found by validation: an element added to these classes by an ODD customization is editable. Without a schema, or if the schema does not define these classes, Varians uses the TEI P5 4.10.2 list. Varians places the pencils itself, whatever XSLT stylesheet the view uses: the stylesheet needs nothing for them, and an element it does not display has no pencil. The label of the editor names the open element, for example “TEI fragment · <lg> 3/40”.

The Varians stylesheet

The stylesheet shipped with Varians (tei-to-html.xsl, also that of the HTML edition (Varians stylesheet) scenario) renders:

  • the structure: a division is titled by its first <head>, otherwise by its @n (never by its @xml:id), and the table of contents lists the titled divisions, by level; each stanza (<lg>) is an indented block, each line of verse (<l>) on its own line; a list is numbered if it has @rend="numbered" or @type="ordered" (or numbered), and its heading precedes it; a <table> is a table, with its caption, its header cells (@role="label") and its merged cells (@cols, @rows); a figure is a block, with its caption;
  • drama: each speech (<sp>) is a block, with its speaker (<speaker>) at the top, in small capitals; a stage direction (<stage>) is in parentheses, in italics: an indented block between two speeches or two paragraphs, a line within a stanza, and within the sentence when it is in a paragraph;
  • editorial phenomena, as in “Critical edition (HTML)”: a <choice> shows one form (<corr>, <reg>, <expan>, otherwise <sic>, <orig>, <abbr>), the others in a tooltip; <sic> is marked; <del> and <surplus> are struck through, <add> underlined; <supplied> is in square brackets; <gap> gives “[lacune]” (French for “gap”); <hi> renders bold, underline, superscript, subscript and small capitals; <emph>, <title> and <foreign> are in italics;
  • quotations: the <ref> of a <cit> follows the quotation, in angle brackets and in grey.

The project CSS (rendering/tei.css) controls the appearance; Varians provides by default the indentation of stanzas and the look of speeches, which the project CSS can override. The preview (Qt) understands a subset of CSS: a rule placed after an @media is ignored there.

8. Witnesses and facsimiles

Each witness of the project has its panel, next to the editor. Its resources are declared in File → Project settings…, under Witnesses and resources (Add…, Edit…): the images, the lines (ALTO or PAGE XML), the alignment file. All are optional and can be added in any order.

Images

The Image source of a witness is one of three:

  • No images for now;
  • Local images (JPEG, PNG, TIFF, BMP, WebP): Add images…; Copy images into the project makes the project portable. Each image receives a folio or page label (Folio / page) and the identifier of its TEI surface (TEI surface). The files added are sorted in natural order (img_1r, img_1v, img_2r…); Natural sort sorts an existing list, and ↑ / ↓ move an image;
  • IIIF Manifest (IIIF Presentation 2 or 3): paste the address of the manifest, then Load / refresh.

Varians completes the edition’s <facsimile> with one <surface> per selected image, without ever rebuilding an existing <facsimile>: the surfaces, the zones and what you have added to them are kept, and a surface that is no longer needed is never deleted without your consent.

<facsimile>
  <surface xml:id="A1-p0002" n="1v">
    <graphic url="../images/A1/002.jpg"/>
  </surface>
</facsimile>

IIIF images selected for the edition

A manifest often has many more pages than the edition uses. Choose Only images selected for the edition, then Choose images and link OCR files…: filter the folios, tick the useful pages; the preview opens a page in the browser. Only the ticked pages form the image corpus of the witness and receive a TEI surface, whose identifier keeps the position of the page in the manifest.

The same dialog links each page to its lines and to its synchronized page:

  • OCR (ALTO or PAGE XML). Varians automatically links an IIIF page and a file whose image name (without extension) is the same, including the image name declared inside the file; an ambiguous match is not applied. Match automatically (exact names) fills the empty cells; the last column lets you choose the file of each page, even when the names are entirely different. A file corresponds to one page only.
  • Synchronized page. For a witness synchronized by lines, Varians finds the page of the alignment file that corresponds to each IIIF page through the Canvas identifier, the image service, the image address, a reliable OCR link or an unambiguous folio label. Otherwise, the Synchronized page column lets you choose it; this choice is kept in project.xml.
  • The Local copy and Link status columns say whether a copy of the page is present, where the link comes from and which source will be displayed.

The place of a page in a list is never used to identify it: without proof, Varians links nothing.

Local copies of IIIF images

Use a local IIIF image working copy in Varians downloads the pages, as you choose (Download pages:) All images in the selected corpus or Only pages with matching ALTO or PAGE files. The download starts after the settings are saved, in a separate window, without blocking editing; File → IIIF Download Manager… reopens it at any time. It gives the number of pages of the manifest, selected, present, missing and excluded; Download missing resumes without downloading the pages already received again, Refresh selection downloads everything again; Pause, Resume and Stop take effect between two images. Closing the window hides it without stopping the job. The copies are stored in iiif/local/<witness>/; a page that has not been copied is still read from the server.

Use the local copy when generating the web viewer is a separate choice: when ticked, the web viewer takes along the copies present and works offline for these pages; when unticked, it reads the images from the original servers. Check the reproduction rights of the holding institutions before distributing images.

When the server offers an IIIF image service, Varians displays the image at full resolution, and falls back on the preview image of the manifest if this fails. The zoom percentage is relative to the automatic fit, not to the resolution of the file.

Lines: ALTO and PAGE XML

The lines of a witness (their position on the image and their text) come from one ALTO or PAGE XML file per page, produced by recognition software. In the witness dialog, the Layout transcription (ALTO / PAGE) section offers, for the ALTO / PAGE source, Automatic / data from synchronization file or Separate ALTO or PAGE files: Add ALTO / PAGE files…, in folio order, and Copy ALTO / PAGE files into project. Each file is recognized separately: a witness can mix both formats. An ALTO line is usually a rectangle; a PAGE line keeps its polygon (Coords/@points) and its baseline (Baseline/@points); its text comes from its TextEquiv/Unicode, or from its words.

Adding lines to an IIIF witness does not change its images. An OCR page is linked to an image only if the link is proven; the others are counted in the tooltip of the witness.

Lines are not a synchronization. As long as no alignment links the lines of the manuscript to those of the pivot, the witness is followed by pages and the panel shows the whole page; the frames of the lines can be displayed, but no line is singled out.

Line synchronization

The alignment file of a witness (JSON synchronization (optional), and Copy synchronization into the project) is produced by Varians-Synchro. That of the pivot describes its physical lines, page by page; that of each other witness links its lines to those of the pivot (base_keys). The format is described in ALIGNMENT_FORMAT.md.

In the TEI, the first <lb edRef="#A"/> of pivot A corresponds to the first line of its alignment file, the next one to the next line, and so on; the <pb> elements locate the pages without renumbering the lines. The status bar counts the lines of the pivot (for example “A: 3599 lines ✓”) and reports a number different from that of the alignment; saving points it out again. A change inside a tag, such as edRef="#T" completed into edRef="#T1", is taken into account immediately.

A witness is followed by lines only if its alignment is usable: real lines for the pivot, real links to the pivot for the others. An empty or provisional file, a file without links to the pivot, or one whose links designate no line of the pivot leaves the witness followed by pages, and Varians reports it.

After re-exporting alignments, View → Refresh synchronization… (Ctrl+Shift+R) reads them again without reopening the project: the files are checked, the list of changes is submitted for confirmation, and an incorrect file never replaces what is loaded. The transcription and its undo history do not change; the panels keep, as far as possible, their page, their zoom and their frames.

The witness panel

The header of the panel names the witness and the displayed position (page and line). Its controls:

  • ← → go to the previous or next line (or page) of the manuscript; ⤺ returns to the correspondence of the passage of the edition; the open-book button decides whether these arrows lead the edition (see Following a manuscript in its own order);
  • − and + set the zoom, the button between them resets it to 100%; the mouse wheel also zooms, and a double-click on the image returns to 100%;
  • Frames shows the outlines of the lines of this witness: in orange the synchronized lines, in blue the line being viewed; PAGE polygons are drawn as they are; without geometry, a message says so;
  • Page ↗ opens the whole image of the page in the default application or browser;
  • Mark page and Two-page spread…, then the Folios: list, for a witness followed by pages;
  • ↗ detaches the panel into its own window (see Panel layout).

In a narrow panel, Frames, Page ↗, Mark page and Two-page spread… shrink to ▣, □, pb and ↔; their tooltip names them.

The crop of a line shows its neighbours, but not those of another column or another page. If a line of the pivot corresponds to several lines of a witness, the panel centres on a line that is actually linked.

Mark page inserts at the cursor the start of the displayed page:

<pb n="1v" edRef="#A1" facs="#A1-p0002"/>

@n takes the folio label, @edRef the witness, @facs the TEI surface (or zone). The cursor must be in the text or between two tags, not inside a tag. A witness followed by pages shows the page of its last <pb> before the cursor: its @facs designates the page; failing that, an @n that designates only one page of the witness. Two witnesses can have the same folio number: the @edRef distinguishes them.

Two-page spread… describes an image that shows two folios or two pages: the dialog shows a thumbnail of the image, with a red bar to place at the separation, and asks for the label of the Left part: and of the Right part:. Varians writes two <zone> elements in the surface of the image, without touching the image. Mark page then targets the part that contains the displayed line, or asks which one to choose; the Folios: list and the arrows go from one part to the other; Full image shows the complete image. Cancelling the dialog adds nothing.

Following a manuscript in its own order

The ← and → arrows of every witness panel lead the edition: the witness moves forward or back in its own order, and the edition cursor goes to the corresponding passage, displaying the part or text that contains it if needed. The other witnesses follow the pivot, as when the cursor moves. When an auxiliary document is displayed, the arrows only browse the witness.

Witness synchronized by lines. The panel moves to the next line of the witness; the edition goes to the pivot line that this line designates. A line not linked to the pivot leaves the edition on the linked line that precedes it, and the status bar says so. The ⤺ button brings the panel back to the line linked to that of the pivot.

Witness followed by pages. The arrows and the folio list lead the edition to the chosen page: to the first line of the witness on that page in one of its JSON files, otherwise to the end of its <pb edRef="#M" n="45v"/>, otherwise to the start of the text whose <locus from> for the witness is that page. Without any of these landmarks, the edition does not move and the status bar says so.

From one text to the next. At the end of a text, the arrows go on to the next text in the manuscript, whether it follows the continuous numbering or is synchronized separately. The panel of the pivot does the same: a pivot shared by several texts is read in one go. A page carrying the end of one text and the beginning of another stays displayed. The panel of a witness absent from the displayed text (“No alignment of this witness for this text.”) leads, with its arrows, to the next or previous text that has this witness, in the order of the edition.

Order of the texts in a manuscript. Varians deduces it from the pages of the witness:

  • the place of the pages in the declared image list of the witness (IIIF manifest or files, in File → Project settings…);
  • otherwise, the pages its JSON files share: each JSON is already in the order of the manuscript, and a page carrying the end of one text and the beginning of another links them;
  • otherwise, the <locus from> of the witness for the text, or the foliation of the first page of the text (a number followed by r or v), compared with that of the other pages;
  • otherwise, the text keeps its place in the order of the edition, and Varians reports it.

View → Witness diagnostics… gives the order of the texts in each manuscript present in several texts, and reports an uncertain place. To make it certain, declare the images of the witness, or add a <locus from="80r" target="#s04"> to its <witness>.

Leading the edition or browsing. The open-book button, just after ← → ⤺, decides whether the arrows of a manuscript lead the edition. When pressed (blue-grey background), the arrows and the choice of folio of this manuscript also move the cursor in the edition, as described above; when released, they only browse the manuscript, without touching the edition. By default, only the button of the pivot witness is pressed. The panel still follows the edition when the cursor moves there. The state of each manuscript is remembered for the project, without changing project.xml.

Witness lacunae

The passage a witness lacks (a lost leaf, a text that breaks off) is enclosed, in TEI, by <lacunaStart/> and <lacunaEnd/>. The TEI places these elements inside a reading: the witness is that of the <rdg> (or <lem>) that contains them or, in a reading of several witnesses, that of their own @wit:

<app><lem wit="#T1 #P"/><rdg wit="#T2"><lacunaStart/></rdg></app>
…
<app><lem wit="#T1 #P"/><rdg wit="#T2"><lacunaEnd/></rdg></app>

<rdg wit="#T2 #P">… <lacunaStart wit="#P"/></rdg>

Varians also recognizes these elements outside a reading, with @wit, but TEI validation reports them there as errors.

In the panels. When the cursor is in a lacuna of a witness, its panel keeps the line (or, for a witness followed by pages, the page) where its text breaks off, with the banner “Lacuna in this witness: its text breaks off here.”. When the cursor is in a lacuna of the pivot witness, the witnesses synchronized by lines stay on the last line of the pivot, with the banner “Lacuna in the pivot witness: lines are not synchronized in this passage.”; the status bar says so too. The witnesses followed by pages keep following their <pb> elements, which do not depend on the pivot.

Debug the apparatus. The check “Incomplete <app> (a witness has no reading)” expects no reading from a witness within its lacuna.

A lacuna without <lacunaEnd/> runs to the end of the text. In an edition in parts, a lacuna may begin in one part and end in another; in a text synchronized separately, only the lacunae of that text count. The web viewer shows the same banners.

Panel layout

View → Choose displayed witnesses…: tick the witnesses to show, then use Move up and Move down to arrange them. With no witness displayed, the image area disappears. The panels share the height, which can be adjusted; a double-click on the header of a witness enlarges it, a second one restores the distribution. The web viewer publishes the displayed witnesses, in this order.

View → Witness layout: Vertical, Horizontal or Grid (2 columns), without losing zoom, frames or synchronization. Detach a witness (or ↗ in its header) opens it in its own window, to be placed on another screen, with its Always on top box; closing this window, or ↙ (Reattach), docks it again; Reattach all witnesses brings them all back. The bar between the editor and the images can be moved: the editor can take up as little as a fifth of the width. Reload images (F5) reads the images again.

These choices are kept on your computer, for each project; they change neither the TEI, nor project.xml, nor the alignments.

Witness diagnostics

View → Witness diagnostics… gives, for each witness, its pages, its images, its lines and its valid links to the pivot. Its warnings distinguish the normal absence of an alignment from defects: alignment file not found, different pivot, links to unknown lines, ALTO or PAGE lines not linked to an IIIF image. For an edition in parts, it also gives the scope (the edition or the displayed text), the texts synchronized separately, and the order of the texts in each manuscript.

9. Critical apparatus

Encoding the apparatus

Varians expects an apparatus in parallel segmentation (see Key concepts): one <app> per point of variation, in the text, with its retained reading (<lem>) and its variants (<rdg>), whose @wit cites the witnesses. The readings of a <rdgGrp> count like the others; an empty reading, <rdg wit="#B"/>, is an omission by witness B. An <app> can contain others.

<app>
  <lem wit="#A #C">uidelicet</lem>
  <rdg wit="#B">scilicet</rdg>
  <rdg wit="#D"/>
</app>
  • Typing. In a @wit, typing # opens the list of the witnesses of the <listWit>, with their description; several witnesses are separated by spaces, and those already cited are not offered again.
  • Cited witnesses. A witness cited without being declared in the <listWit> is reported by Edit → References (see References between documents).
  • Lacunae. The passage a witness lacks is enclosed by <lacunaStart/> and <lacunaEnd/>, in one of its readings: see Witness lacunae.
  • Established text. Wherever Varians publishes the established text, the <lem> prevails; an <app> without <lem> takes the reading of a chosen witness, by default the pivot.

Debug the apparatus

Help → Debug the apparatus… offers ready-made XPath queries to find errors in the critical apparatus of the displayed document, encoded in parallel segmentation: each <app> groups its readings (<lem>, <rdg>, including inside a <rdgGrp>), whose @wit cites the witnesses in the form #A. The witnesses are those of the document’s <listWit>.

  • Witness cited more than once: the same witness appears in two readings of an <app>, or twice in the same @wit; its reading is ambiguous.
  • Incomplete <app>: a witness has no reading. For a top-level <app>, all the witnesses of the <listWit> are expected; for a nested <app>, those of the reading that contains it. A <lem> without @wit is deemed to cover the witnesses missing from the <rdg> elements: its <app> is not reported.
  • <app> without <lem>: the <app> elements that have no <lem>; a <lem> placed in a <rdgGrp> of the <app> counts. This search does not depend on the witnesses: it remains available without a <listWit>.
  • Given witness: the <app> elements where a witness chosen from the list appears, or does not appear, in <lem> or <rdg>, or in <rdg> only.
  • My queries: your own named XPath queries, for checks specific to your encoding. Add… proposes the current query of the XPath panel; Edit… and Delete manage them. They are saved in project.xml (<xpathQueries> element) and travel with the project.

Search runs the query in the XPath panel: clicking a result selects the <app>. The query stays in the XPath field: it is plain XPath 1.0, with the tei: prefix, which can be copied into other XML tools. It may be long, since it has one condition per witness.

Limits: witness groups (a <listWit xml:id="…"> cited in @wit) are not expanded; a witness cited but missing from the <listWit> is reported by the Edit → References command; if some witnesses of the <listWit> are not collated in the apparatus, every <app> looks incomplete.

Publishing the apparatus

  • Critical edition (HTML): the established text, and the apparatus after each division, called by numbers; see Critical edition.
  • TEI: DOCX (Word) and TEI: ODT (LibreOffice): the apparatus in footnotes, following the same rules; see TEI Stylesheets.
  • Web viewer: a purple circle at each point of variation shows the readings and their witnesses; the displayed text is, as you choose, the established text or the transcription of a witness; see Web viewer.

10. Editions in parts (XInclude)

A long edition, a collection or a corpus can be split into files, one per text, which the edition assembles through XInclude. Varians treats the whole as a single document, while editing each file separately. This chapter describes how it works, then how to set it up step by step.

How it works

To set up such a project step by step, see the guide.

An edition can include its parts, for example one file per sermon, following the XInclude standard. The edition declared in project.xml remains the master document; its parts are deduced from its xi:include elements, with no other declaration:

<TEI xmlns="http://www.tei-c.org/ns/1.0"
     xmlns:xi="http://www.w3.org/2001/XInclude">
  …
  <body>
    <xi:include href="sermons/s01.xml"/>
    <xi:include href="sermons/s02.xml" xpointer="s02"/>
    <xi:include href="sermons/s03.xml" xpointer="element(/1/2/1/1)"/>
  </body>

A part is either a fragment (the whole file, whose root is for instance the <div> of the sermon) or an element of a complete TEI document, designated by xpointer: its identifier (s02 or element(s02)) or its path (element(/1/2/1/1): TEI, then its 2nd child text, then body, then the first div). A part can itself include others. Relative paths written in a part start from the folder of the part.

Parts and tabs

Each part has its own tab, named after its file, after the tab of the edition and in inclusion order. It is edited and saved on its own (Ctrl+S), with its own undo history; before quitting, Varians offers to save the modified parts. The list of parts is read again each time the edition or a part is saved. “Rename tab…” and “Remove the document from the project” only concern auxiliary documents. The XSLT / CSS view stays open while a part is displayed: it shows the whole edition (see XSLT / CSS view of the assembled edition); the witnesses stay displayed too (see below). Saving the edition in another folder would break the paths of its xi:include elements: Varians warns you first.

Validation

The edition and each of its parts have the assembled edition validated, with the schema of the edition and taking the unsaved changes of the parts into account. The RELAX NG panel then adds a Document column; double-clicking an error opens the right part at the right line. The tab of each part takes the colour of its own errors. A missing or malformed part, a circular inclusion or an unsupported form (parse="text", xi:fallback, another xpointer scheme) is reported at the line of its xi:include.

References and witnesses

The edition and its parts form a single document: a #id is first looked for in the file that contains it (header included), then in the other parts. F12, the References command and completion take this into account. Only the identifiers of the included element of a part belong to the assembled edition: a witness declared only in the <teiHeader> of a sermon included by xpointer is found by Varians in that sermon, but a tool that reads only the assembled edition will not see it. In a part, Help → Debug the apparatus… uses the witnesses specific to the part: its <listWit>, otherwise the witnesses of the edition whose <locus target="#s01"> points to the part, otherwise those cited by its @wit attributes.

Witness synchronization

When the edition is split into files for convenience (a collection whose texts follow one another as in the pivot witness), the witnesses are synchronized as for an edition in a single file: the pivot lines (<lb edRef="#A"/>) are counted in the order of the assembled edition, from one part to the next, and the alignment files remain those of an edition in a single file, one per witness for the whole edition. The cursor of the edition or of a part makes the witnesses follow; a click or scrolling in the pivot puts the cursor in the part that contains the line and opens its tab, even after “Hide tab”. The structure status (status bar) counts the pivot lines in the whole assembled edition, and saving the edition or a part warns if this number differs from that of the pivot’s alignment. An <lb/> placed in a comment or outside the included element of a part does not count, as in other XML tools.

Condition: the pivot must contain these texts in the order of the edition. Varians checks the number of lines, not their order. The other witnesses may have another order, or lack a text: their alignment already designates lines of the pivot. A witness synchronized by pages follows the last <pb> that concerns it, in the order of the edition, even in a previous part: if this witness has the texts in another order, mark its page at the start of each text.

From a part, “Mark page” inserts the <pb> in the part, at the cursor, and completes the <facsimile> of the edition; “Two-page spread…” writes its zones in the <facsimile> of the edition. The edition is then modified without being displayed: its tab shows “*”. Undoing in the part removes the <pb>, not what was added to the <facsimile>.

Texts synchronized separately

In a corpus whose texts are not transmitted by the same witnesses, nor in the same order, a text can have its own alignments: one JSON per witness, in the usual format, in a folder named after the file of the text, without extension (alignments/s02/B.json for xml/sermons/s02.xml). Nothing has to be declared: a text that has its folder is synchronized separately; the others follow the continuous numbering. The pivot of a text is that of the project, unless an exception is declared in project.xml: <part name="s02" base="B"/>.

When such a text is displayed, the witness panels take its alignments and its pivot; the layout, the zoom and the detached windows do not change. A witness without a JSON for this text keeps its panel, which says “No alignment of this witness for this text.”. The lines are counted in the text alone (for instance “B: 8 lines ✓”); a click in the pivot stays in the text. The witness diagnostics and the refreshing of synchronizations apply to the displayed text.

Witnesses followed by pages. A witness that has no JSON for this text, but does have the text — a <pb edRef="#C"/> in the text, or a <locus target="#s04"> in its <witness> of the <listWit> —, follows its pages there. Before its first <pb> in the text, it shows its starting page: the @from of that locus (<locus from="13r" to="14r" target="#s04">), otherwise the page that precedes the page of this first <pb>, in the page order of the witness. “Mark page” works there too. The witness diagnostics name, for each text, its witnesses followed by pages. The other witnesses without a JSON keep the absence message.

XSLT / CSS view of the assembled edition

The XSLT / CSS view shows the whole edition, parts included, whatever document is displayed, and is used as for an edition in a single file. Switching from the edition to a part does not leave it; only displaying an auxiliary document closes it.

  • Fragment editing. The pencil ✎ of an element opens it in the fragment editor, as it is written in the file that contains it; the label names this file, for example “TEI fragment · <p> 10/16 · s03.xml”. The applied fragment is written into this file, even if it is not displayed or has never been opened: its tab then shows “*”, and a single undo, in the part, removes the change. The file must remain well formed. Ctrl+S in the fragment editor saves this file, then the displayed document if it is modified; before quitting, Varians offers to save an unapplied fragment with its file.
  • Click, table of contents, search. A click on a line places the cursor at this line, in the file that contains it, whose tab opens, without leaving the preview; the witnesses follow, with the own numbering of a text synchronized separately. The table of contents and the search in the preview do the same.
  • Selections. A string selected in the preview is selected, when you return to the XML source tab, in the file that contains the text (a part, or the edition), at the same occurrence of the same paragraph; without a selection, the cursor goes to the displayed line. Conversely, the selection or the position in a part is found again in the preview. Between the preview and the fragment editor, selections follow each other as for an edition in a single file.
  • Limits. A paragraph that itself contains an xi:include is edited in the file of its tag; the included text is edited in its part. As for an edition in a single file, a paragraph or a line that the XSLT does not render shifts the pencils or the line markers that follow it.

Web export of the assembled edition

Generate web viewer exports the whole edition, parts included, with the continuities of the window.

  • Text and lines. The text of the parts is in the viewer, and the pivot lines are counted there from one part to the next, as in the window. A text synchronized separately keeps its pivot and its JSON files (alignments/s02/): when the chosen line enters it, each panel shows its witness in that text, by its lines, by its pages from its starting page, or with “No alignment of this witness for this text.”. The zoom and the frames of each panel are kept from one text to another. The buttons of the header go through all the lines in reading order, from one text to the next.
  • Panel arrows. As in the window, the ← → arrows of every panel lead the text in the manuscript’s own order, from one part or text to the next, and so does the folio list of a witness followed by pages; ⤺ brings the panel back to the linked line. The messages of the window’s status bar (start or end of the manuscript, unlinked line, unplaced page, uncertain place) appear under the title of the viewer.
  • Lacunae. The banners are those of the window (see Witness lacunae): a lacuna continues from one part to the next, and a text synchronized separately starts again without a lacuna.
  • Saving. The export reads the saved files: Varians first saves the edition, each modified part and the unapplied fragment of a part; if one of them cannot be saved, the export is cancelled. A part that cannot be found, or an unsupported inclusion (parse="text", xi:fallback), is reported in the export report: the text concerned is missing from the viewer.
  • Limits. The position used is that of the clicked text fragment. A <pb> or <lb> placed in a reading that is not retained, or in a note, is not seen by the viewer. “Witness diagnostics…”, “Refresh synchronization…”, “Mark page” and “Two-page spread…” remain specific to the window. Generate the viewer again after changing the edition.

Limits

The order of the texts in a manuscript is deduced from its pages; a text that cannot be attached to them keeps its place in the order of the edition (see Following a manuscript in its own order). The web export has its own limits: see Web export of the assembled edition. A project without xi:include is not affected.

Step-by-step guide

This guide describes, step by step, how to organize a project whose edition is split into several files, for instance one file per sermon. Each function is detailed above, in How it works.

1. Organize the files

Keep a single edition file, the one declared in project.xml (for instance xml/edition.xml): it is the master document, with the header, the list of witnesses and the order of the texts. Put the texts in a neighbouring folder, one file per text. Give each file a name that is unique in the whole project: this name, without extension, is also used for the alignment folder of a text synchronized separately (step 4). Paths are relative to the file that contains them: sermons/s01.xml from the edition, ../personnes.xml#augustinus from a sermon.

project.xml
alignments/T1.json, T2.json …
alignments/s02/B.json, D.json
xml/edition.xml
xml/sermons/s01.xml, s02.xml, s03.xml …

2. Write the xi:include elements

Declare the XInclude namespace on the root element of the edition, then put an xi:include where each text goes:

<TEI xmlns="http://www.tei-c.org/ns/1.0" xmlns:xi="http://www.w3.org/2001/XInclude">
  …
  <body>
    <xi:include href="sermons/s01.xml"/>
    <xi:include href="sermons/s02.xml" xpointer="s02"/>
  </body>
</TEI>

A text is either a fragment: the whole file, whose root is the included element and carries the TEI namespace (<div xmlns="http://www.tei-c.org/ns/1.0" xml:id="s01">); or a complete TEI document, of which only one element is included, by its identifier (xpointer="s02") or by its path (xpointer="element(/1/2/1/1)"). A complete document can also be validated on its own; its header does not enter the edition. A text can itself include another one. Use neither parse="text" nor xi:fallback: Varians reports them without supporting them. Save the edition: each text gets its tab.

3. Declare the witnesses

Declare each manuscript only once, in File → Project settings…, with a siglum common to the whole collection. In the TEI, declare the witnesses in the <listWit> of the edition, in that of each text (complete TEI document), or in both. A witness declared only in the header of a text included by xpointer is found by Varians, but a tool that reads only the assembled edition does not see it.

4. Choose the synchronization of each text

  • The texts follow one another as in the pivot, with the same witnesses (a collection split for convenience): continuous numbering. One JSON per witness for the whole edition, as for an edition in a single file, declared in the project settings. The pivot lines are counted from one text to the next, in the order of the edition; the pivot must contain the texts in that order.
  • The witnesses change from one text to another (a corpus): text synchronized separately. Create the folder alignments/<name of the text file>/ and put in it one JSON per witness for this text, in the usual format: alignments/s02/B.json, alignments/s02/D.json. Produce these JSON files with Varians-Synchro on the file of the text. There is nothing to declare: the folder is enough. A witness without a JSON for this text, but that has its <pb edRef> in it or a <locus target> in its <witness>, follows its pages there: see Texts synchronized separately.
  • Both can be mixed: the texts that have their folder are synchronized separately; the others follow the continuous numbering, and the global JSON of each witness contains only their lines.

5. Declare a pivot specific to a text

The pivot of a text synchronized separately is that of the project. If the pivot of the project lacks this text, or if another witness must serve as reference, write the exception by hand in project.xml, before </teiManuscriptProject>, then reopen the project:

<parts>
  <part name="s02" base="B"/>
</parts>

name is the name of the file of the text, without extension; base, the siglum of the pivot. The lines of this text are then its <lb edRef="#B"/> elements, and its folder must contain B.json. Varians keeps this element when the project settings are saved.

6. Check

  • Display each text: the structure status, in the status bar, must be right, for instance “B: 8 lines ✓”; its tooltip says whether the count covers the assembled edition or a text synchronized separately.
  • View → Witness diagnostics… gives the scope (the edition or the displayed text), the texts synchronized separately with their pivot and their witnesses, and the problems: JSON of an undeclared witness, unknown pivot, missing pivot JSON…
  • RELAX NG validation covers the assembled edition; the Document column gives the file of each error.
  • The References command checks the references from one text to another.
  • Another XML tool assembles the project without Varians: xmllint --xinclude --noout xml/edition.xml, or oXygen with XInclude enabled in the validator preferences.
  • View → Witness diagnostics… also gives the order of the texts in each manuscript; an uncertain place is reported there: see Following a manuscript in its own order.

7. Day to day

  • Each text is edited in its tab and saved on its own (Ctrl+S); before quitting, Varians offers to save the modified texts.
  • To add a text: create its file, add its xi:include to the edition, save the edition; its tab appears. For a text synchronized separately, also add its alignment folder, then use View → Refresh synchronization….
  • With many tabs: right-click a tab → Hide tab; a click in the pivot makes the tab of the needed text reappear.
  • Saving the edition in another folder would break its xi:include elements: Varians warns you first.
  • The XSLT / CSS view shows the whole edition: the pencil ✎ opens an element of any text there, and a click there leads to the text that contains the line; see XSLT / CSS view of the assembled edition. The web export contains the whole edition; see Web export of the assembled edition.
  • To read a manuscript from one text to the next, use the arrows of its panel: the edition displays the right text.

11. Web viewer

The web viewer publishes the edition with its facsimiles: the text on the left, the manuscripts on the right, synchronized as in Varians. It is a standalone HTML page, which opens in any browser, with neither server nor Varians, and can be put online as it is.

Generating the viewer

Generate web viewer (toolbar, or File → Generate web viewer) first asks for the text to display (see Choice of the text), then writes the viewer into web_output/ (viewer.html), with the local images it uses (web_output/images/). The folder and the file name are set in File → Project settings….

Before the export, Varians saves the edition, its modified parts and the unapplied fragment of a part; if one of them cannot be saved, the export is cancelled. The viewer publishes the displayed witnesses, in their order (View → Choose displayed witnesses…); a hidden pivot serves there only for synchronization. The export report lists the images that cannot be found and the passages without a reading of the chosen witness. The viewer is a copy: generate it again after changing the edition.

Without opening Varians, drop the project.xml of a project onto generer_viewer_web.bat, or run python -m web_viewer.generator project.xml: the viewer is the same, with the choice of text saved in the project.

The text

Reading text. The viewer reads every text of the edition: <front>, <body> and <back>, and each text of a <group>. A division is titled by its first <head>, otherwise by its @n; its @xml:id is not a title. Untitled front or back matter is titled “Front matter” or “Back matter”. The table of contents lists the titled divisions, indented under the titled division that contains them. Each <lg> is a stanza, each <l> on its own line, with its @n in the margin; a list keeps its sublists; a <table> is a table, with its caption, its header cells (@role="label") and its merged cells (@cols, @rows); a <note> placed between two paragraphs is a marker, hidden with the notes. Each speech (<sp>) is a block, with its speaker (<speaker>) at the top, in small capitals; a stage direction (<stage>) is in parentheses, in italics, as a block between two speeches or within a speech, within the sentence when it is in a paragraph. As in “Critical edition (HTML)”, a <choice> shows one form (correction, regularization, expansion), the other in a tooltip; <del> is struck through, <add> underlined with dots, <supplied> in square brackets, and <gap> gives “[…]”, with its reason and extent in a tooltip. The readings of a <rdgGrp> count like the others. The text takes the language of its @xml:lang, which governs hyphenation. As in “Critical edition (HTML)”, the <ref> of a <cit> with type="bible" follows the quotation in angle brackets; that of another <cit> is a note.

Choice of the text. “Generate web viewer” first asks which text to show: the established text (the <lem>, otherwise the reading of the chosen witness, as in “Critical edition (HTML)”) or the text of the chosen witness, even when it is not the <lem>, which reconstructs its transcription. By default the chosen witness is the pivot of each text. Where it has no reading (no reading of the <app> names it: missing passage, lacuna, incomplete apparatus), the viewer shows the <lem>, otherwise the reading of the pivot, on a grey background framed with dots, with the tooltip “No reading of … here”; “∅” marks such an empty passage. An omission (<rdg wit="#T2"/>) is a reading and is not marked. The header of the viewer and the export report give the number of these passages. Synchronization still follows the lines of the pivot: those of its reading that is not shown are spread over the text shown; when the witness omits the passage, an invisible marker keeps their place. With the established text, the Highlight in yellow the readings that do not come from a <lem> box of the same dialog highlights from the start the readings taken for lack of a <lem>, those that remain to be decided; in the viewer, the reader shows or hides them with the Readings outside <lem> box of the header. The choice is kept in project.xml, <webViewer text="established|witness" textWitness="T2" highlightNonLem="true"/>; generer_viewer_web.bat follows it.

In the text, a purple circle v marks each variant: a click shows the readings and their witnesses. A circle n marks a note. The Variants and Notes boxes of the header hide these markers; the Readings outside <lem> box, in the established text, highlights in yellow the readings that do not come from a <lem>; A− and A+ set the size of the text; Language changes the language of the viewer.

The text and the manuscripts

Each witness has its card, on the right, with the controls of its panel in Varians: arrows, zoom (also with the mouse wheel, and by double-click to return to 100%), Frames, Page ↗ and ⤺. A project without images is published without a facsimile column.

  • By lines. A click on the text chooses the pivot line; each synchronized witness shows its line, cropped, with a blue outline, even when its other frames are hidden. ← line and line →, in the header, go through the lines in reading order.
  • By pages. A click in the text shows, for each witness followed by pages, the page of its last <pb>; without any alignment, the buttons of the header become ← page and page →.
  • In the order of the manuscript. As in Varians, the ← → arrows of every card lead the text: the witness moves forward in its own order, and the text goes to the pivot line that its line designates, or to its <pb> for a witness followed by pages, whose folio list also leads the text; ⤺ brings the card back to the linked line. The messages (start or end of the manuscript, unlinked line…) appear under the title.
  • Lacunae. The lacunae of the witnesses have their banners, as in Varians (see Witness lacunae).

A text without a line marker, or a line missing from the export, is reported: the viewer never infers an uncertain correspondence. For an edition in parts, see Web export of the assembled edition.

Searching

The Search… field of the header searches for a word or a phrase in the whole displayed text: headings, verse, list items, cells, speakers and stage directions included. With no other choice, the search is exact, regardless of case; under Medieval spellings, the u/v, i/j and c/t boxes make these letters equivalent. The results are listed and highlighted; a result leads to its passage and to the lines of the manuscripts.

The images

Local images are copied with the viewer. IIIF images are read from their servers: the viewer requests the useful size each time (IIIF Image services 1, 2 and 3), and falls back on a smaller image, then on the whole image, then on the preview of the manifest if the server refuses. They therefore require Internet access and the necessary rights, except for the pages whose local copy is published (see Local copies of IIIF images). The frames follow the PAGE outlines and the zones of a two-page spread, at the coordinates of the source image.

12. Publishing with XSLT

Beyond the web viewer, Varians publishes the edition through XSLT stylesheets: its own (Critical edition, HTML edition), those of the TEI Consortium (DOCX, ODT, EPUB, HTML, LaTeX…), and yours. Each publication is a scenario, which you can run again with one click.

XSLT transformation scenarios

A transformation scenario applies an XSLT stylesheet to the edition or to another document of the project, and writes the result to a file: HTML edition, index, list of quotations, transformed XML… It is named, saved in the project, and can be run again identically. The web viewer remains a separate publication, which a scenario does not change.

File → Transformation scenarios… shows two groups:

  • Project scenarios, saved in project.xml (<transformations> element): Add…, Edit…, Duplicate… and Delete manage them.
  • Predefined scenarios, provided by Varians: HTML edition (Varians stylesheet), which publishes the edition with the stylesheet and the CSS of the Varians preview in publications/edition.html; Critical edition (HTML), a critical edition with its apparatus, following the pivot witness (see Critical edition); and, in the TEI Stylesheets sub-group, collapsed at first (a click on its arrow expands it), the scenarios of the TEI-C stylesheets (see TEI Stylesheets). In the menu of the Transform button, the latter form a submenu. A predefined scenario can be run as it is, or duplicated into the project to adapt it.

Each row shows the source, the engine and, in red, what prevents the scenario from running (stylesheet not found, Saxon not installed…). Run runs the chosen scenario; Preview runs it in a temporary folder and opens the result, without touching the file of the scenario.

A scenario

  • Source: Edition (the edition of the project, assembled if it has parts: each part keeps its location, and a relative document() finds its files there), Displayed document (the document of the current tab, for example an auxiliary document, see Auxiliary XML documents; the assembled edition if it is the edition) or File (a file read as it is).
  • Engine: XSLT 1.0 (lxml), or XSLT 3.0 (Saxon) for stylesheets in XSLT 2.0 or 3.0. Saxon-HE (saxonche package) is installed with Varians: installer_dependances.bat, or pip install -r requirements.txt.
  • XSLT stylesheet and optional CSS: paths relative to the project; ${varians}/ designates the stylesheets provided with Varians. The CSS is copied next to the result, and its name is passed to the stylesheet through the css parameter (the Varians stylesheet puts it in its <link>). A new scenario offers the stylesheet and the CSS of the preview.
  • Result: the file written, replaced at each run (publications/<name>.html is offered). It cannot be a source of the project (project.xml, the edition and its parts, a document, a stylesheet, a schema, an alignment JSON). With Saxon, a stylesheet may write other files with xsl:result-document (one page per sermon, for example), only in the folder of the result and its subfolders; elsewhere, the run is refused.
  • Output format (with Saxon): A single file, most often; HTML pages (one per division), when the stylesheet writes index.html and its pages with xsl:result-document; DOCX (Word), ODT (LibreOffice) or EPUB, when it writes the files of an archive into the folder whose address it receives, like the TEI-C stylesheets: Varians then builds the archive, which is the result (see TEI Stylesheets).
  • TEI → TEI pre-pass (optional), with Saxon: a stylesheet applied to the source before that of the scenario, with the same parameters. This is how the DOCX and ODT scenarios put the apparatus into footnotes.
  • Parameters: name / value pairs, passed to the stylesheet (<xsl:param name="titre"/>). With Saxon, they are passed untyped, as by its command line: “false” suits an xs:boolean parameter, “3” an xs:integer, and the value stays a string elsewhere; with lxml, they are strings. In a value, ${pivot} becomes the identifier of the project’s pivot witness, and ${tei}/ the address of the folder of the installed TEI Stylesheets.

Running

The Transform button, next to Generate web viewer, runs again the last scenario run in the project (also Ctrl+Shift+T); its arrow gives the list of scenarios. Before running, Varians saves what the scenario reads: the edition, its modified parts and the unapplied fragment, as for the web export, as well as the source document, the stylesheet and the CSS if they are open and modified. The transformation runs in a separate process: Varians remains usable, and Cancel stops it.

The summary gives the files written and the duration; Open opens the result in the default application (the browser, for HTML), Open the folder the folder that contains it. Its details give the log: engine and version, parameters, xsl:message, network reads (with lxml), refused writes. If an error occurs, the message gives the file and line concerned, and the previous result is left intact.

Security: a stylesheet may read any local file, and http or https addresses (the result may then depend on a server); it writes only its result (and, with Saxon, files in its folder). External entities of the sources are not read.

Critical edition

The predefined scenario Critical edition (HTML) publishes the edition (assembled, if it is in parts) as a self-contained HTML page, to read on screen or to print: publications/edition-critique.html. Its stylesheet, edition-critique.xsl (${varians}/, in XSLT 3.0: Saxon engine), comes from a TEI critical-edition stylesheet, adapted for Varians.

  • Established text. The <lem> of an apparatus always prevails (an empty <lem/> is an established omission); otherwise, it is the reading of the witness chosen by the temoin-de-base parameter, set to ${pivot}: the pivot witness of the project. In the box of a duplicated scenario, it is chosen from a list: the pivot witness first (“T1 (pivot)”), the other witnesses of the project and of the <listWit>, then “aucun (lemmas only)”; a value written otherwise (#B) is kept; without a value, it is the first <witness> of <listWit>. With aucun, the text follows the <lem> elements only, and each <app> must have one. An unknown witness, or aucun with an apparatus without a lemma, stops the run with a clear message. An apparatus without a reading of the chosen witness gives “[lecture du témoin non disponible]” (“witness reading not available”). When the established text includes readings that do not come from a <lem>, the page has a Surligner les leçons hors <lem> box (“Highlight the readings outside <lem>”): when ticked, it highlights them in yellow, to show what remains to be decided.
  • Apparatus. After each division, in two series: the Apparat critique (critical apparatus), called in the text by numbers, and the editor’s Notes, fewer, called by letters (a, b… z, aa…). An entry gives the retained reading, “]”, then each other reading followed by its sigla in italics; the readings of a <rdgGrp> count like the others. An empty reading gives om.; when the established text omits the passage, the other readings are additions (add.). A reading that contains only <lacunaStart/> or <lacunaEnd/> gives “lacuna incipit T1” or “lacuna desinit T1” (see Witness lacunae). All the text of the apparatus that does not come from a witness is in italics: sigla, om., add., lacuna incipit and desinit, comments; the readings stay in roman, even a <sic> (followed by “sic” in italics), a quotation or a highlighted word. Calls and entries are linked both ways.
  • Text. A division without <head> takes its @n as title, otherwise has none. Only the <pb> elements of the chosen witness, or without @edRef, are shown (⟨12r⟩), and all of them with aucun (⟨T1 : 12r⟩). Contiguous <lb> elements of several witnesses make a single break, which joins a word if one of them has break="no". Lines of verse and stanzas (<l>, <lg>) keep their structure and their numbers. Each speech (<sp>) is a block, with its speaker (<speaker>) in small capitals; a stage direction (<stage>) is in parentheses, in italics: a block between two speeches or two lines of verse, within the sentence when it is in a paragraph.
  • Parameters (box of the scenario, after Duplicate…; check boxes, except temoin-de-base): montrer-folios and montrer-numeros-de-vers; sauts-lb (ticked: a line break of the chosen witness becomes a line break of the page); surligner-hors-lemme (ticked: the box of the page is ticked from the start; unticked by default).

The same rules put the apparatus into footnotes in the DOCX and ODT scenarios (see TEI Stylesheets). The texts of the page (“Apparat critique”, “Notes”…) are in French: to change them, duplicate the scenario, then use Open stylesheet; the stylesheet is copied into xslt/ with apparat-commun.xsl, which holds its rules (see XSLT transformation scenarios).

TEI Stylesheets

The TEI Stylesheets are the XSLT stylesheets of the TEI Consortium (github.com/TEIC/Stylesheets), also used by Oxygen and other tools. Varians brings them and installs them on first use, once for all projects, in the user’s data folder: they work without network. They are written in XSLT 3.0: their scenarios use Saxon.

Predefined scenarios. In File → Transformation scenarios…, the TEI Stylesheets sub-group of the predefined scenarios gathers eight scenarios that publish the edition (assembled, if it is in parts): TEI: HTML, TEI: HTML in several files, TEI: DOCX (Word), TEI: ODT (LibreOffice), TEI: EPUB, TEI: plain text, TEI: Markdown and TEI: LaTeX. It is collapsed at first, and forms a submenu of the Transform button. Their results are written to publications/tei/ (edition.html, pages/index.html, edition.docx, edition.odt, edition.epub, edition.txt, edition.md, edition.tex). The HTML receives next to it the CSS of the TEI Stylesheets (tei.css), with no link to the TEI-C site; the texts added by the stylesheets (“Table of contents”…) follow the language of the interface, through the parameters lang and documentationLanguage. In a scenario, ${tei}/ designates a file of the installed TEI Stylesheets, for example ${tei}/profiles/default/html/to.xsl; see XSLT transformation scenarios. The log of a run names the version used (“Library: TEI Stylesheets 7.61.0”).

Formats in several files. Four of these scenarios have their own Output format (see XSLT transformation scenarios):

  • TEI: HTML in several files writes publications/tei/pages/index.html, the table of contents, and one page per division and per sub-division (s02.html…, after their @xml:id), with tei.css. The splitLevel parameter sets the splitting: 1, the value of the scenario, splits the divisions and their sub-divisions, which gives one page per piece when the text is a single division that gathers them; 0, the top-level divisions only. Following the rule of the TEI Stylesheets, the first division stays on the page of the table of contents when nothing precedes it (no <front>).
  • TEI: DOCX (Word) and TEI: ODT (LibreOffice) write edition.docx and edition.odt, from the template of the TEI Stylesheets. These would render the apparatus badly (all the readings one after the other, each in its own paragraph), and would turn each <pb> into a page break and each <lb> into a line break: a Varians pre-pass, apparat-en-notes.xsl, first prepares the text following the pivot witness (temoin-de-base parameter, set to ${pivot}). Each <app> becomes its retained reading, followed by a footnote (<note place="foot" type="apparatus">): “reading ] variant sigla; …”, with om., add., lacuna incipit and lacuna desinit, following the rules of the critical edition. An editor’s note without @place becomes an endnote (place="end"): the apparatus and the notes form two series. Only the folios of the pivot witness remain, as ⟨12r⟩ markers in the text, and the line breaks of the witnesses merge into the text.
  • TEI: EPUB writes edition.epub, with the CSS of the installed TEI Stylesheets (${tei}/tei.css), read without network.
  • Local images (<graphic url="…"/>) are put into the DOCX, ODT or EPUB archive, with their dimensions; a remote image is not downloaded, and the log says so.

Customizing a stylesheet. The TEI Stylesheets are not modified: they are overridden in a stylesheet of the project. Duplicate a TEI scenario (Duplicate…), then choose the copy and Open stylesheet: Varians offers to create in xslt/ a customization stylesheet, for example xslt/tei-html.xsl (Create the customization stylesheet), which the scenario then uses. It imports (xsl:import) the TEI-C stylesheet through its official address, http://www.tei-c.org/release/xml/tei/stylesheet/…, which Varians reads from the installed TEI Stylesheets, without network; Oxygen does the same, and the stylesheet remains valid there. The parameters (xsl:param) and templates (xsl:template) you write in it take precedence over those it imports; everything else comes from the TEI Stylesheets. For example:

<xsl:stylesheet version="3.0" xmlns:xsl="http://www.w3.org/1999/XSL/Transform"
    xmlns:tei="http://www.tei-c.org/ns/1.0" xmlns="http://www.w3.org/1999/xhtml"
    exclude-result-prefixes="#all">
  <xsl:import href="http://www.tei-c.org/release/xml/tei/stylesheet/profiles/default/html/to.xsl"/>
  <!-- No numbering of headings. -->
  <xsl:param name="numberHeadings">false</xsl:param>
  <!-- Personal names in bold. -->
  <xsl:template match="tei:persName"><b><xsl:apply-templates/></b></xsl:template>
</xsl:stylesheet>

For an HTML output, xmlns="http://www.w3.org/1999/xhtml" makes the added elements (here <b>) XHTML, like those of the TEI Stylesheets. The customization stylesheet is edited, checked (F8) and completed like any stylesheet: see Editing an XSLT stylesheet. An update of the TEI Stylesheets does not touch it: it still applies.

Updates. The TEI-C publishes about two versions a year. At startup, Varians checks at most once a month, without blocking the window, whether a new version has been published; if there is none, or without network, nothing is said. Otherwise, it offers to install it: Install or Later (the question comes back at the next check). The installation shows its progress and can be cancelled; an incorrect archive or a cancellation keeps the installed version. The new version is used from the next transformation on, for all projects; the old one is removed at the next startup. File → TEI Stylesheets…, or the TEI Stylesheets… button of the list of scenarios, shows the installed version, its origin, its folder, its licence and the date of the last check; Check for an update checks at once. A single version is installed: a publication made again after an update may differ from the previous one, and the log gives the version.

Licence. The TEI Consortium distributes the TEI Stylesheets under either the BSD 2-Clause licence or the CC BY-SA 3.0 licence; the LICENCE file is installed with them (Show the licence).

Limits. LaTeX is compiled to PDF with a TeX installation (xelatex), outside Varians. In plain text and Markdown, the TEI Stylesheets write the lemma and the variant one after the other: a customization stylesheet can change this choice of the TEI-C. In DOCX and ODT, the apparatus is numbered 1, 2, 3 at the foot of the page, and the editor’s notes i, ii… at the end of the document; in Word, the TEI Stylesheets add a space after the call of an endnote. HTML pages do not carry the images: their address remains that of the source.

Editing an XSLT stylesheet

An XSLT stylesheet is an XML document: Varians opens it as a project document, in its own tab (see Auxiliary XML documents), checks it and helps you write it, without any external tool.

  • Adding a stylesheet: File → Project XML / XSLT documents… → Add an XML, XSLT or Schematron document… accepts .xsl and .xslt files. A stylesheet located outside the project folder is copied into it, in the xslt/ folder (at the same level as xml/), never replacing an existing file; a stylesheet already in the project stays where it is.
  • New XSLT stylesheet… (same menu) creates a minimal stylesheet, in XSLT 1.0 (lxml) or in XSLT 3.0 (Saxon), offered in xslt/: TEI namespace declared, HTML output, a template for the root of the document.
  • From the scenarios (see XSLT transformation scenarios): Open stylesheet, in the list of scenarios or in the box of a scenario (which is then saved), shows the stylesheet of a project scenario. A stylesheet supplied with Varians (${varians}/…) is first copied into xslt/; a stylesheet outside the project can be copied too, or opened without copying. After a copy, the scenario uses the copy. For a predefined scenario, first use Duplicate…. A Varians stylesheet that includes or imports others (xsl:include, xsl:import) is copied with them, without replacing a file already there: edition-critique.xsl with apparat-commun.xsl.

Checking. For a stylesheet, Check XSLT stylesheet (F8, instead of Validate RNG) compiles it without running it, with the engine of the project scenarios that use it (both if they differ); a stylesheet that no scenario uses is checked according to its version: version="1.0" by lxml, any other by Saxon. As with RELAX NG validation, the stylesheet is checked when it is first displayed, after each change once F8 has been used, and on saving, which asks for confirmation if it has errors. The validation panel gives each error with its line; a double-click leads to it. An error in an imported (xsl:import) or included (xsl:include) stylesheet names its file in the Document column, and the double-click leads to that stylesheet if it belongs to the project. The status bar shows the result, and the tab of the stylesheet is coloured like that of an invalid document.

Completion. Ctrl+Space offers the XSLT elements and attributes allowed at that place, with the prefix of the stylesheet (xsl:), and the list of attributes opens while you type. In an element of the result (<div>, <tei:p>…), these are the XSLT instructions and the xsl:* attributes. A version="1.0" stylesheet only receives the elements and attributes of XSLT 1.0. The suggestions come from the W3C RELAX NG schema of XSLT 3.0, supplied with Varians (BSD licence); the custom elements of the project (custom-elements.xml) are not offered in a stylesheet.

Related files. Varians only copies the stylesheet itself. The files it needs for the result to be complete (stylesheets imported by xsl:import or included by xsl:include, images, CSS, JavaScript…) must be placed by you in the xslt/ folder of the project, keeping the relative paths that the stylesheet uses. Checking reports an imported or included stylesheet that cannot be found. The CSS of a scenario, on the other hand, is copied automatically next to the result.

Limits: a stylesheet meant to be imported or included is checked on its own, and its references to declarations of the main stylesheet may be reported as errors; an XSLT 2.0 stylesheet receives the suggestions of XSLT 3.0; the names declared in the stylesheet (templates, modes, keys) and XPath expressions are not completed.
